1 · Introduction to REST APIs & Django REST Framework

The opening lecture of a new unit: what an API is, what REST/RESTful actually means, what DRF is and how it relates to plain Django, and the project setup steps needed before any DRF code gets written.

What is an API?

An API (Application Programming Interface) is software that enables communication between two or more applications — one app sends a request, the other sends back a response, without either side needing to know how the other is built internally.

When we are using a mobile application, your application connects to the internet and sends data to a server. Then the server retrieves the data, interprets it, performs the necessary actions, and sends it back to your phone.

Real-world examples given directly in the video: a mobile app (e.g. Flipkart) talking to its servers through an API acting as a middleman/mediator; a travel-reservation website routing a railway booking to IRCTC and a bus booking to a service like RedBus, each through its own API; banking apps, where every transaction is described as an API call under the hood.

Gap‑filled — why this matters before touching any code

Every button tap or page load that shows data from somewhere else is an API call in disguise. DRF doesn't invent this — it gives Django a standard way to expose your project's data as an API, so other applications (a mobile app, a JS front-end, another company's server) can request it in a predictable format instead of scraping HTML meant for humans.

Homogeneous vs. heterogeneous communication

The video draws a specific distinction: homogeneous communication is same-technology-to-same-technology (Java ↔ Java, .NET ↔ .NET); heterogeneous communication is different technologies talking to each other (Python ↔ Java, Java ↔ .NET). APIs are what make heterogeneous communication possible — the whole reason a Django backend can serve an iOS app, an Android app, and another Java-based service without any of them sharing a language.

Example

A Django backend exposing /api/products/ doesn't care whether the requester is a React web app, a Flutter mobile app, a curl command, or another Django project — as long as it can send an HTTP request and parse a JSON response, it can talk to the API.

DRF is an extension of Django, not a separate framework

Django REST framework is not a separate [framework] — it's along with Django only. This is an extension of Django.

Django REST Framework (DRF) — also called "TRF"/"RF" in the (garbled) transcript, correctly expanded as DRF — is a Python package that sits on top of an ordinary Django project and adds API-building tools, while reusing everything Django already provides: the ORM, models, project/app structure, settings.py, and URL routing. The video is explicit that both Python and Django are mandatory prerequisites — "without Python and without Django, we cannot go for REST API."

Gap‑filled — the dependency chain

DRF depends on Django, Django depends on Python. DRF's core building blocks (serializers, views, routers) are Python classes that inherit from or wrap Django's own classes — e.g. DRF's APIView extends Django's own View. This course's earlier project setup, MVT, models, views, and URL lectures are the foundation DRF is built on, not optional background.

What "REST" means

REST stands for Representational State Transfer. It is used for web-based architecture for data communication.

Two clarifications the instructor stresses because they're commonly confused:

  • REST is an architectural style, not a protocol — a set of conventions for designing web-based communication (HTTP, URL-identified resources, standard verbs), not a formal technical standard the way HTTP or TCP/IP is.
  • REST isn't exclusive to Django — Java programmers use "RESTful services," .NET programmers use "web APIs," Django uses "REST API" (via DRF). Different terminology, same underlying idea.
Rest API or RESTful API — don't get confused here. Rest API, RESTful API are not different things, both are the same thing only. When web services use REST architecture, they are called RESTful API or REST API.
Researched — the formal traits of RESTful design

Per the DRF documentation and general REST literature: statelessness (each request carries everything the server needs — no memory of previous requests), resource-based URLs (a URL identifies a "thing," like /api/students/5/, not an action), and using HTTP methods to express the action rather than encoding it into the URL (DELETE /api/students/5/, not /api/deleteStudent?id=5).

What DRF provides

  • Open source, flexible, modular — extend/customize as needed rather than an all-or-nothing black box.
  • Reduces development time — pre-built generic classes handle the repetitive parts of a CRUD API.
  • Testing/debugging support, including a later-covered browsable API — an auto-generated, clickable HTML interface for testing endpoints in a browser.
  • Powerful serialization & deserialization mechanism, compatible with ORM and non-ORM data sources — named here, detailed starting next lecture.
  • Easy customization, validations, and authentication systems (authentication/permissions explored in depth in REST API Sessions 13–17).
  • Generic class-based views for CRUD ("grad operations" in the transcript — a mis-transcription of CRUD: Create, Read, Update, Delete).
Gap‑filled — why "reduces code" matters concretely

Without DRF, a CRUD API in plain Django means manually parsing request.body as JSON, manually converting model instances to dictionaries field-by-field, manually validating input, and manually setting status codes and Content-Type: application/json — for every model. DRF's serializers and generic views absorb almost all of that.

Types of APIs: private, partner, public

  • Private API — usable only within one organization; internal systems talking to each other.
  • Partner API — shared between specific business partners under an agreement; multiple organizations reach the same service through it.
  • Public API — usable by any third-party developer; the most common in consumer-facing, real-time applications, e.g. banking.
Example

An internal tool letting a company's payroll system query its own HR system is a private API. A payment gateway exposing an API specifically to approved merchants is a partner API. A public weather service anyone can sign up for a key and query is a public API.

Researched — this isn't a DRF setting

DRF has no "type" configuration for this. Whether an API ends up private/partner/public is entirely a matter of authentication and permissions (REST API Sessions 13–17) and network/deployment access, not a distinct DRF feature.

The request/response cycle

Client sends HTTP request to API. API will interact with the web application, and web application will interact with the database if it is required. Web application provides the required data to the API. API returns data to the client.
# Client (Python app / Java app / Django app / browser / mobile app)
      │  HTTP request (GET / POST / PUT / PATCH / DELETE)
      ▼
  REST API  ───────────────►  Web application (your Django + DRF project)
      ▲                              │
      │  JSON/XML response           │ queries, if data is needed
      │                              ▼
      └────────────────────────  Database

The API's role throughout is as a middleman/mediator — it carries the client's request to the web application, and carries the web application's (database-backed) response back to the client. In a DRF project, "the web application" in this diagram is your Django project: URLs route the request to a view, the view talks to the database through the ORM (with help from a serializer), and the same view returns the response — DRF doesn't add a separate physical layer, it's the part of Django that formats the response as JSON instead of HTML.

Why JSON/XML instead of HTML templates

DTL can be understood only by a Django application, but a user can interact with any other application, like a Java application, a Python application... DTL cannot be understood by other applications.

A plain Django view renders a response using DTL (Django Template Language) — HTML a browser can display. An API response instead uses JSON or XML — data formats with no visual styling, parseable by any program in any language, not just a browser.

Gap‑filled — the whole reason DRF exists

An HTML page is fine for a human at a browser but useless to a mobile app or another backend trying to consume data programmatically — it would have to scrape text out of <div> tags. JSON/XML carry pure structured data, so any client can parse it and decide for itself how to display it.

JSON (JavaScript Object Notation) is an open, human-readable, text-based data-interchange format built from attribute-value pairs, based on JavaScript object syntax but usable from virtually any language — which is why it's the default format for API responses, including DRF's. XML (eXtensible Markup Language) is an older, tag-based format for structured data; the instructor notes this course will use JSON almost exclusively.

Example — serialized JSON
{
  "id": 1,
  "first_name": "Anita",
  "last_name": "Rao",
  "subject": "Python"
}

A "get all trainers" endpoint wraps multiple such objects in a JSON array — this is the shape DRF's serializers produce; the mechanics of generating it from a model are next lecture's topic.

Researched — JSON vs. XML in practice

DRF supports JSON by default (JSONRenderer) and XML via optional add-ons like djangorestframework-xml. JSON has become the dominant default for new REST APIs — more compact and easier to parse than XML, which now shows up mainly in older enterprise/SOAP-based systems.

HTTP methods ↔ CRUD mapping

  • GET → Read — retrieve/fetch existing data, no server-side change.
  • POST → Create — insert/store new data.
  • PUT → Update (full) — replace an entire existing record.
  • PATCH → Update (partial) — update only some fields, leaving the rest untouched.
  • DELETE → Delete — remove an existing record.
Gap‑filled — PUT vs. PATCH, made concrete

To fix a typo in only a Trainer's subject, send PATCH with just {"subject": "Python"} — only that field changes. Sending the same partial payload as PUT risks wiping the untouched fields, since PUT conventionally expects the entire resource. Use PUT only when sending a complete representation; PATCH when changing a subset of fields.

Researched — idempotency

Per MDN's HTTP methods reference, GET, PUT, and DELETE are expected to be idempotent — repeating them produces the same end state as doing it once. POST is not idempotent by convention — calling it twice creates two records. This isn't enforced automatically by Django/DRF; it's a design convention DRF's generic views assume you'll follow.

API resource anatomy

Number one is the base URL... number two is naming convention — this is optional... number three, very important, is the endpoint or API resource.

A typical API URL has up to three parts: the base URL (the domain, e.g. xyz.com), an optional naming convention segment (e.g. /api, signaling "API endpoints live here"), and the mandatory endpoint/resource (e.g. /trainers) — the actual "thing" being addressed.

Example
# base URL + naming convention + endpoint/resource
GET    /api/trainers/       # list all trainers
GET    /api/trainers/5/     # read trainer 5
POST   /api/trainers/       # create a trainer
PUT    /api/trainers/5/     # fully update trainer 5
PATCH  /api/trainers/5/     # partially update trainer 5
DELETE /api/trainers/5/     # delete trainer 5

The URL barely changes across all six — it's the HTTP method that changes the action, exactly the REST principle above.

Researched — resource naming convention

Per common REST API design guidance and DRF's own tutorial, endpoints are conventionally plural nouns for a collection (/trainers/, not /trainer/ or /getTrainer/), with an individual item addressed by its identifier (/trainers/5/). DRF's DefaultRouter (used with ViewSets, REST API Session 12) generates exactly this pattern automatically.

Serialization & deserialization

A queryset (e.g. Employees.objects.all()) and a model instance (one database row as a Python object) are both described as complex data — shaped by Django's ORM, not something a generic client or even Python's own json module understands directly. A serializer converts that complex data into native Python data types (dict, list, str, int...), which can then be rendered into JSON (or XML). Serialization is that direction; deserialization is the reverse — parsed/incoming data converted back into complex data — deferred to a later session in this unit.

Researched — the DRF docs' own definition

Per the DRF serializers docs: "Serializers allow complex data such as querysets and model instances to be converted to native Python datatypes that can then be easily rendered into JSON, XML or other content types. Serializers also provide deserialization, allowing parsed data to be converted back into complex types, after first validating the incoming data." The video's explanation is close to a verbatim match — note the extra detail that deserialization also validates incoming data before converting it back.

Example — one record, before and after

Before (complex data): an Employees instance in the database. After serialization:

Writing serializers.py — ModelSerializer

Just as a ModelForm auto-builds a form from a model's fields, a ModelSerializer auto-builds a serializer from a model's fields.

# rest_app/serializers.py
from rest_framework import serializers
from .models import Employees

class EmpSerializer(serializers.ModelSerializer):
    class Meta:
        model = Employees   # which model this serializer represents
        fields = '__all__'  # include every field defined on Employees
Researched — '__all__' vs. explicit fields

Per the DRF docs, fields = '__all__' is convenient for prototyping but will silently expose any new model field the moment it's added — no serializer change required. Industry best practice: list fields explicitly once past a first prototype, e.g. fields = ['id', 'emp_name', 'email'].

Writing the view — APIView and Response

# rest_app/views.py
from rest_framework.views import APIView
from rest_framework.response import Response
from .models import Employees
from .serializers import EmpSerializer

class EmpDetails(APIView):
    def get(self, request):
        emp = Employees.objects.all()             # QuerySet: "complex data"
        serializer = EmpSerializer(emp, many=True)  # many=True: MULTIPLE records
        return Response(serializer.data)            # JSON-ready data

APIView is DRF's own base class-based view — the direct equivalent of Django's View, dispatching get()/post()/etc. by HTTP verb. Only get() is written here since this view only reads data; many=True tells the serializer it's converting a collection, not a single instance. Crucially, Response comes from rest_framework.response — not Django's own HttpResponse/JsonResponse.

Gap‑filled — why APIView over a plain Django View

A plain Django View + JsonResponse could return JSON too, but APIView (and DRF generally) provides multi-format request parsing, browsable-API rendering for free, and — in later sessions of this unit — built-in authentication/permission hooks. It's the entry point that unlocks the rest of the framework as the project grows.

Wiring up the URLs

# rest_app/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path('empdetails/', views.EmpDetails.as_view()),
]
# MyRestProject/urls.py

]
Gap‑filled — why .as_view() is required

Same rule as Django's own class-based views: a URL pattern needs a callable function, not a class. EmpDetails.as_view() returns a function that, when called, instantiates EmpDetails and routes the request to the matching method. Writing path('empdetails/', views.EmpDetails) without .as_view() is a common mistake that errors out.

Running it: the browsable API

Visiting the URL in a browser shows DRF's browsable API — a styled HTML page showing the formatted JSON, the available HTTP methods (GET, POST, HEAD, OPTIONS), and a submission form — rather than raw JSON text. Testing writes through it is deferred to a later session.

Researched — how DRF picks HTML vs. JSON

Per the DRF renderers docs, DRF uses content negotiation on the request's Accept header: a browser gets the friendly BrowsableAPIRenderer HTML page; a tool like curl or a mobile app requesting application/json gets plain JSON — from the exact same Response(serializer.data) call, no extra code needed.

Under the hood: QuerySet vs. ReturnList

A live print(type(...)) demonstration confirms the pipeline: Employees.objects.all() is a django.db.models.query.QuerySet; after passing through EmpSerializer, serializer.data is a rest_framework.utils.serializer_helpers.ReturnList — DRF's own list subclass, which behaves like a plain list of dicts for every practical purpose and is what actually gets turned into JSON text.

Example — the same pattern with a Book model

A second worked example beyond the video's Employees case:

class Book(models.Model):
    title = models.CharField(max_length=100)
    author = models.CharField(max_length=100)
    price = models.DecimalField(max_digits=6, decimal_places=2)

class BookSerializer(serializers.ModelSerializer):
    class Meta:
        model = Book
        fields = ['id', 'title', 'author', 'price']  # explicit, not '__all__'

class BookListAPIView(APIView):
    def get(self, request):
        books = Book.objects.all()
        serializer = BookSerializer(books, many=True)
        return Response(serializer.data)

Output — GET /books/:

[
  {"id": 1, "title": "Clean Code", "author": "Robert C. Martin", "price": "34.99"},
  {"id": 2, "title": "Deep Work", "author": "Cal Newport", "price": "18.50"}
]

A mobile reading-tracker app, an Android app, and a web frontend can all call this same endpoint — none of them need Django template rendering, because the response is generic, language-agnostic data.

Industry best practice

List serializer fields explicitly rather than '__all__' past the prototype stage; only implement the HTTP methods a view actually needs (DRF returns 405 automatically for the rest); never forget .as_view() or many=True; and always import Response from rest_framework.response, not Django's HttpResponse/JsonResponse, inside a DRF view.

Gap‑filled — id shouldn't really be a CharField

Retrieving one record: emp_detail

# restapp1/views.py
from django.http import HttpResponse
from rest_framework.renderers import JSONRenderer

from restapp1.models import Employee
from restapp1.serializers import EmpSerializer


def emp_detail(request, pk):
    # fetch exactly ONE Employee row by primary key
    emp = Employee.objects.get(id=pk)

    # wrap the single instance: "serialize one record"
    serializer = EmpSerializer(emp)

    # .data = Python-native serialized dict (not JSON yet)
    # JSONRenderer().render(...) turns that into actual JSON bytes
    json_data = JSONRenderer().render(serializer.data)

    return HttpResponse(json_data, content_type='application/json')

Employee.objects.get(id=pk) returns a single model instance (raising an error if zero or more than one row matches), unlike .filter()/.all() which return a queryset. serializer.data is the serialized representation as plain Python primitives — the "Python type" stage. JSONRenderer is the class whose job is converting that Python-native data into actual application/json bytes — the "Python type → JSON" stage. content_type='application/json' tells the receiving client how to interpret the response body.

Researched — HttpResponse vs. JsonResponse vs. DRF's Response

django.http.HttpResponse is the generic, low-level class used here — you encode the body yourself. django.http.JsonResponse is a Django shortcut that handles the json.dumps(...) + content-type boilerplate for you. rest_framework.response.Response is DRF's own class, used by APIView-based views — it negotiates the renderer automatically and is what produces the browsable API page. This lecture's function-based views manually reproduce, step by step, what Response mostly automates.

Retrieving every record: emp_all_details and many=True

def emp_all_details(request):
    employees = Employee.objects.all()               # a QuerySet: many rows
    serializer = EmpSerializer(employees, many=True)  # many=True: serialize a collection
    json_data = JSONRenderer().render(serializer.data)
    return HttpResponse(json_data, content_type='application/json')

The two views differ only in .get(id=pk) vs. .all(), and in the many=True flag. A plain serializer is built to serialize one object by default; handing it a queryset without many=True would fail, because the serializer wouldn't know to loop over it. many=True switches it into list mode: DRF wraps the serializer in a ListSerializer that iterates the collection, serializes each item, and collects the results into a Python list — which JSONRenderer then turns into a JSON array.

The create_manager view: JSON in, saved row out

# restapp2/views.py
import io
from rest_framework.parsers import JSONParser
from rest_framework.renderers import JSONRenderer
from restapp2.serializers import ManagerSerializer
from django.http import HttpResponse
from django.views.decorators.csrf import csrf_exempt

@csrf_exempt
def create_manager(request):
    if request.method == 'POST':
        stream = io.BytesIO(request.body)            # raw bytes -> file-like object
        py_data = JSONParser().parse(stream)          # JSON bytes -> Python dict

        serializer = ManagerSerializer(data=py_data)  # data= means "validate this input"

        if serializer.is_valid():
            serializer.save()                          # -> calls ManagerSerializer.create()
            result = {'message': 'Data Inserted'}
        else:
            result = serializer.errors                 # dict describing what failed

        json_data = JSONRenderer().render(result)      # Python dict -> JSON bytes
        return HttpResponse(json_data, content_type='application/json')
Gap‑filled — a real bug worth naming

Neither branch sets an explicit HTTP status code, so Django defaults to 200 OK even when the else branch returns validation errors — a client checking only response.status_code would wrongly think the insert succeeded. A corrected version would pass status=201 on success and status=400 on failure, e.g. HttpResponse(json_data, content_type='application/json', status=400).

Why @csrf_exempt is needed here

Django requires a CSRF token on POST requests submitted from an HTML <form>, proving the request really came from your own site's page. test.py is a plain script using requests, not an HTML form — it has no token to send, so without @csrf_exempt the request would be rejected outright.

Researched — a more scalable alternative

Per the Django CSRF docs, sprinkling @csrf_exempt across API views removes a real protection, not just an inconvenience. DRF's own class-based views typically avoid needing it at all once clients authenticate via token authentication (covered later in this course) instead of session cookies — CSRF specifically targets cookie-based auth, so token auth sidesteps the problem rather than exempting it.

Researched — what partial=True actually changes

        return HttpResponse(json_data, content_type='application/json')

Recap — serialization, deserialization, and last session's function-based CRUD

Serialization converts a "complex" Python object — a queryset or model instance straight from the database — into plain Python types, then into JSON, so it can be sent to the end user. Deserialization is the reverse trip: JSON arriving from a client becomes plain Python types, then a validated, savable model instance, so it can be written to the database. Last session's whole CRUD API lived in one view function, branching on request.method (POST = create, GET = read, PUT = update, DELETE = delete).

Gap‑filled — the mental model in one line

Serialization always flows out of Django (database → Python → JSON → client); deserialization always flows in (client → JSON → Python → database) — like translating an outgoing letter into a foreign language versus translating an incoming one back. Every CRUD operation below is just one of those two translations, wired to an HTTP method.

Gap‑filled — why a plain @csrf_exempt above the class won't work

Every request to a class-based view enters through one method, dispatch(), which routes it to the matching get()/post()/put()/delete(). method_decorator adapts an ordinary function decorator so it can be applied to one method of a class; name='dispatch' tells it to wrap dispatch specifically — and since every request passes through dispatch first, that exempts the whole class from CSRF checks in one shot.

Researched — officially documented pattern

This exact method_decorator(csrf_exempt, name='dispatch') pattern is the documented way to apply a function decorator to a class-based view — see the Django docs on decorating class-based views.

    def post(self, request, *args, **kwargs):

What is validation, and DRF's three approaches

Validation is checking whether submitted data is actually correct/acceptable before it's allowed into the database — the same concept as Django form validation, just applied to DRF serializers instead of HTML forms. DRF offers three mechanisms:

TechniqueScopeMechanism
Field-level validationOne specific fieldvalidate_<field_name>(self, value)
Object-level validationMultiple/all fields togethervalidate(self, data)
ValidatorsOne field, reusablya standalone function + validators=[...]

Field-level validation

A method named validate_<field_name> — DRF calls it automatically for that one field, purely from the naming convention.

# serializer.py
class EmployeeSerializer(serializers.Serializer):
    name = serializers.CharField(max_length=50)
    email = serializers.EmailField()
    address = serializers.CharField(max_length=100)
    age = serializers.IntegerField()

    # ---- Field-level validation ----
    def validate_age(self, value):
        if value > 100:
            raise serializers.ValidationError("Age should not exceed 100.")
        return value  # must return the value, or it becomes None
// POST {"name": "Ganesh", "email": "ganesh@gmail.com", "address": "Hyderabad", "age": 102}
{"age": ["Age should not exceed 100."]}
Changing age to 25 and re-posting inserts the record successfully — confirmed in the admin panel.
Example — field-level validation on a different field
def validate_email(self, value):
    if value.endswith("@example.com"):
        raise serializers.ValidationError("Please use a real email address.")
    return value

{"email": "test@example.com"} → rejected. {"email": "test@gmail.com"} → passes through.

Researched — auto-increment IDs are never reused

While re-testing, the video notices the next inserted ID skips a number because of inserts/deletes from the previous session's testing. Per how SQLite/MySQL/PostgreSQL auto-increment fields all work, once an ID is issued it is never reused, even if that row is later deleted — the next insert always gets (highest ID ever issued) + 1. Not a bug; relying on gap-free sequential IDs is a common beginner mistake.

Object-level validation

A method literally named validate, taking the entire dict of submitted field values — for rules that need to compare two or more fields against each other.

    # ---- Object-level validation ----
    def validate(self, data):
        name = data.get('name')
        address = data.get('address')
        # .lower() makes the comparison case-insensitive on both sides
        if name.lower() == 'mohan' and address.lower() != 'hyderabad':
            raise serializers.ValidationError("Address should be Hyderabad only.")
        return data  # must return the (validated) data dict
// POST {"name": "Mohan", "address": "HYD", ...}
{"non_field_errors": ["Address should be Hyderabad only."]}
Correcting address to "Hyderabad" inserts successfully. The error key is non_field_errors, not address — a validate() failure isn't tied to any single field.
Example — a genuine two-field rule
def validate(self, data):
    if data['end_date'] <= data['start_date']:
        raise serializers.ValidationError("end_date must be after start_date.")
    return data

A single field's own validator could never check this — it needs both values at once.

Validators: reusable, standalone functions

A plain function (not a method) that raises serializers.ValidationError on failure, then attached to a specific field via that field's validators=[...] list.

# a standalone, reusable validator function
def starts_with_a(value):
    if value[0].lower() != 'a':
        raise serializers.ValidationError("Name should start with letter A only.")

class EmployeeSerializer(serializers.Serializer):
    name = serializers.CharField(max_length=50, validators=[starts_with_a])
    # ...other fields unchanged...
// POST {"name": "Ganesh", ...}
{"name": ["Name should start with letter A only."]}
Changing name to "Anish" inserts successfully.
Gap‑filled — how this differs from validate_<field>

Both check one field and raise the same exception. The difference is reuse: validate_age only ever exists inside one serializer class; a standalone function like starts_with_a is defined once and can be attached, via validators=[...], to a field on any number of unrelated serializers.

Researched — DRF's own built-in validators

Per the DRF docs, DRF ships ready-made validators for common cases — UniqueValidator (reject a value already used elsewhere, e.g. a unique email), Django's own RegexValidator, and MaxValueValidator/MinValueValidator. Write a custom function like starts_with_a only once a project's own rule isn't already one of these.

Industry best practice

Keep validation logic as narrow as the mechanism that expresses it: a single-field rule belongs in validate_<field> (or a reusable validator); only reach for validate(self, data) when a rule genuinely needs to compare multiple fields. Cramming everything into one validate() also loses the specific field name in error responses — everything becomes a generic non_field_errors entry.

ModelSerializer

A ModelSerializer automatically generates a serializer's fields — and their validators — straight from a model's own field definitions, and provides a default create()/update() implementation, removing the need to hand-write either. It's the exact same idea as Django's own ModelForm, applied to serializers.

# serializer.py — before: everything hand-written
class EmployeeSerializer(serializers.Serializer):
    name = serializers.CharField(max_length=50)
    email = serializers.EmailField()
    address = serializers.CharField(max_length=100)
    age = serializers.IntegerField()

    def create(self, validated_data):
        return Employee.objects.create(**validated_data)

    def update(self, instance, validated_data):
        instance.name = validated_data.get('name', instance.name)
        # ...same pattern for email, address, age...
        instance.save()
        return instance
# serializer.py — after: ModelSerializer
class EmployeeSerializer(serializers.ModelSerializer):
    class Meta:
        model = Employee       # which model this serializer mirrors
        fields = '__all__'     # include every model field

No field declarations, no create(), no update() — posting a new record through this much shorter serializer still inserts successfully, confirmed in the admin panel.

read_only_fields

A class Meta option listing fields that are returned in responses but cannot be written to — any submitted value for them is silently ignored, with no error.

class EmployeeSerializer(serializers.ModelSerializer):
    class Meta:
        model = Employee
        fields = '__all__'
        read_only_fields = ['address', 'age']

// original record: name=Durga, email=durga@gmail.com, address=Hyderabad, age=45

Industry best practice

read_only_fields (or read_only=True on one field) is the standard way to expose data a client should see but never directly set — most commonly a primary key id or a created_at/updated_at timestamp. Never rely on "the frontend just won't send that field" — any API client can send whatever JSON it wants.

Researched — read_only_fields vs. leaving a field out of fields

Per the DRF docs, a read_only_fields field is still included in every response — only writes are blocked. Leaving a field out of fields entirely (or using exclude) means it never appears in responses at all.

Example — a realistic use case
class OrderSerializer(serializers.ModelSerializer):
    class Meta:
        model = Order
        fields = '__all__'
        read_only_fields = ['price', 'status']

A customer can update their shipping address, but a submitted change to price or status is quietly ignored — the server, never the client, controls those.

Researched — custom validation still works on a ModelSerializer

The transcript doesn't re-demonstrate it, but per the DRF docs, validate_<field> and validate(self, data) work identically on a ModelSerializer — switching to it only removes the field/create/update boilerplate, not the ability to add custom business-rule checks like "age should not exceed 100."

class ManagerAPI(APIView):

            return Response(serializer.data)
Gap‑filled — pk=None, format=None and many=True

From APIView to GenericAPIView

The previous topic built full CRUD with plain rest_framework.views.APIView — one class per operation, each manually instantiating a serializer, checking is_valid(), and returning a Response by hand. That still means writing every line of serialization/validation/saving logic yourself, for every model. generics.GenericAPIView is a subclass of APIView built to remove exactly that repetition for the operations almost every model-backed API needs.

What GenericAPIView adds over APIView

  • queryset — the base QuerySet the view operates on, e.g. Customer.objects.all().
  • serializer_class — which serializer converts model instances ↔ JSON for this view.
  • get_queryset() — returns the queryset to use (defaults to self.queryset); override it when the queryset must depend on the request.
  • get_object() — finds a single instance from the queryset using a URL keyword argument (pk by default) — the piece that actually powers retrieve/update/delete.
  • get_serializer() — builds the serializer instance, with request context attached automatically.

On its own GenericAPIView still has no get/post/etc. methods — it only supplies plumbing. That's the whole reason mixins exist: they add the actual list/create/retrieve/update/delete behavior on top of this plumbing.

What is a mixin?

A mixin is a small class that bundles reusable methods and is meant to be combined with other classes via multiple inheritance — never used by itself. Think of it as one bit in a toolbox, like a screwdriver bit: useful only once it's paired with a driver that can hold it and apply force. A DRF mixin supplies one behavior (e.g. "list a queryset as JSON") but has no idea how to receive an HTTP request or send a response — that comes from GenericAPIView/APIView underneath it. Combine the two and you get a working view that also knows how to list/create/retrieve/update/delete.

The five built-in model mixins

Mixin (rest_framework.mixins)Method it addsWhat it does
ListModelMixin.list()Returns every record in the queryset as JSON.
CreateModelMixin.create()Validates incoming data and saves a new record.
RetrieveModelMixin.retrieve()Looks up and returns one specific record via get_object().
UpdateModelMixin.update() / .partial_update()Looks up one record and overwrites its fields.

None of the mixins define get/post/put/delete themselves — wiring HTTP verbs to mixin methods is still written by hand, one line each, as shown below. (DRF's ViewSets, a later topic, automate that wiring.)

Gap‑filled — why five separate mixins?

Splitting behavior this finely lets a view opt into only the operations it should support. A read-only endpoint can mix in just ListModelMixin + RetrieveModelMixin — there is then no create/update/destroy method available at all, making writes structurally impossible rather than merely hidden behind a permission check.

Picking up right after the last session's one-class-per-operation pattern, this session shows how to fold several mixins into one class-based view, then introduces DRF's concrete view classes — ready-made generic views that need no method overrides at all.

Recap — where this picks up

Combining mixins into one view: RetrieveUpdateDelete

A single class handles retrieve, update, and delete for one customer, all through a URL that takes a primary key:

# rest_app5/views.py
from rest_framework import mixins, generics
from .models import Customer
from .serializers import CustomerSerializer

class RetrieveUpdateDelete(
    mixins.RetrieveModelMixin,   # gives .retrieve()
    mixins.UpdateModelMixin,     # gives .update() and .partial_update()
    mixins.DestroyModelMixin,    # gives .destroy()
    generics.GenericAPIView,     # base class every mixin needs
):
    # --- common to every operation on this model ---
    queryset = Customer.objects.all()
    serializer_class = CustomerSerializer

    # --- wire each HTTP verb to the matching mixin method ---
    def get(self, request, *args, **kwargs):
        return self.retrieve(request, *args, **kwargs)

    def put(self, request, *args, **kwargs):
        return self.update(request, *args, **kwargs)

    def delete(self, request, *args, **kwargs):
        return self.destroy(request, *args, **kwargs)

queryset and serializer_class are written once at the top (shared by every mixin); each HTTP method is a one-line handler calling the matching mixin method. Nothing about how the mixin methods work changes from last session — only where they're wired up changes: three handlers now live in one class instead of three separate classes.

Concrete view classes — defined

Having just hand-wired mixins onto GenericAPIView, the instructor introduces DRF's next level of convenience: a concrete view is a ready-made GenericAPIView subclass that DRF itself provides, already mixed with the right mixin(s) and already defining the HTTP method handlers that call them. What is a ViewSet?

ViewSet — a class-based view that groups the logic for all of a resource's related operations into one class, instead of spreading them across separate view classes. "In other frameworks you may find a conceptually similar implementation — something like resources or controllers. But in DRF, we have ViewSets." Crucially: "a ViewSet class is simply a type of class-based view that does not provide method handlers such as a get() method or post() method — instead it provides actions, such as list() and create() methods."

Gap‑filled — why action names instead of HTTP-verb names

With APIView and the mixins, methods are named after HTTP verbs (get(), post()) so the mapping to a request is fixed by convention. A ViewSet's methods are named after what they do (list, retrieve, create, update, partial_update, destroy) — nothing on the class itself says which HTTP verb triggers which method. "The method handlers for a ViewSet are only bound to the corresponding actions at the point of finalizing the view — using .as_view() — typically by registering the ViewSet with a router class." A router builds that verb-to-action mapping for you, generating calls like .as_view({'get': 'list', 'post': 'create'}) behind the scenes for each URL it creates.

Why routers exist

Router — a DRF class that, given a ViewSet, automatically generates every URL pattern that resource needs. "Routers are used with ViewSets to auto-configure the URLs. Routers provide a simple, quick, and consistent way of wiring ViewSet logic to a set of URLs. A router automatically maps the incoming request to the proper ViewSet action based on the request method."

The CustomerViewSet class

# restapp7/views.py
from rest_framework.response import Response
from restapp7.models import Customer
from restapp7.serializers import CustomerSerializer
from rest_framework import status
from rest_framework import viewsets


class CustomerViewSet(viewsets.ViewSet):

    def list(self, request):
        # GET /customer/ — return every row
        queryset = Customer.objects.all()
        serializer = CustomerSerializer(queryset, many=True)  # many=True: a list of objects, not one
        return Response(serializer.data)

    def retrieve(self, request, pk=None):
        # GET /customer/<pk>/ — return a single row by primary key
        customer = Customer.objects.get(id=pk)
        serializer = CustomerSerializer(customer)
        return Response(serializer.data)

    def create(self, request):
        # POST /customer/ — validate incoming data and insert a new row
        serializer = CustomerSerializer(data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response({"message": "data inserted"}, status=status.HTTP_201_CREATED)
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)

    def update(self, request, pk=None):
        # PUT /customer/<pk>/ — replace an existing row's data
        customer = Customer.objects.get(id=pk)
        serializer = CustomerSerializer(customer, data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response({"message": "updated"})
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)

    def destroy(self, request, pk=None):
        # DELETE /customer/<pk>/ — remove a row
        customer = Customer.objects.get(id=pk)
        customer.delete()
        return Response({"message": "record deleted"})

viewsets.ViewSet is the plainest base class — no automatic behavior at all, contrasted with ModelViewSet (next session) which implements all five methods automatically from just queryset and serializer_class. Method names (list, retrieve, create, update, destroy) are conventional — a router relies on exactly these names to wire actions up automatically. pk=None appears only on the three methods that act on a single object; list/create act on the whole collection and take no pk. The video also mentions partial_update (PATCH-style partial edits) as available alongside update (full PUT-style replacement), without writing its body since it mirrors update().

Gap‑filled — a real bug hiding in this code

Customer.objects.get(id=pk) raises Customer.DoesNotExist — an unhandled exception, surfacing as an ugly generic 500 Internal Server Error — if no row with that pk exists. The video never demonstrates this failure case. DRF's own generic views avoid it using get_object_or_404(), which DRF converts into a clean 404 Not Found automatically:

from django.shortcuts import get_object_or_404

def retrieve(self, request, pk=None):
    customer = get_object_or_404(Customer, id=pk)
    serializer = CustomerSerializer(customer)
    return Response(serializer.data)

A common pitfall in any hand-written retrieve/update/destroy — always assume a client might request a pk that doesn't exist.

Example — a custom ViewSet action with @action

The video's demo only covers the five standard actions. A common next question: can a ViewSet expose an endpoint that isn't one of those five? Yes, via @action:

# books/views.py
from rest_framework import viewsets, status
from rest_framework.decorators import action
from rest_framework.response import Response
from .models import Book
from .serializers import BookSerializer


class BookViewSet(viewsets.ViewSet):
    def list(self, request):
        books = Book.objects.all()
        return Response(BookSerializer(books, many=True).data)

    def retrieve(self, request, pk=None):
        book = Book.objects.get(pk=pk)
        return Response(BookSerializer(book).data)

    # detail=True: acts on ONE book, so the URL needs a pk (like retrieve)
    @action(detail=True, methods=['post'])
    def mark_borrowed(self, request, pk=None):
        book = Book.objects.get(pk=pk)
        book.is_available = False
        book.save()
        return Response({"message": f"'{book.title}' marked as borrowed"}, status=status.HTTP_200_OK)
# router.register('books', BookViewSet, basename='book')
# router.urls now automatically includes:
#   POST /books/<pk>/mark_borrowed/  ->  BookViewSet.mark_borrowed

Why ModelViewSet exists

A plain ViewSet still requires writing every action's body by hand — it removes URL-routing boilerplate, not CRUD-logic boilerplate. 13 · Authentication & permissions — basic authentication

Authentication identifies who is making a request; permissions decide what that request is allowed to do. This topic builds a fresh demo app and walks BasicAuthentication through AllowAny, IsAuthenticated, and IsAdminUser — configured per-view and then globally in settings.py.

Authentication vs. permissions

Authentication is the process of checking whether a request's credentials (typically a username and password) are valid, and figuring out who sent the request. It always runs at the very start of a view, before permission checks and before any other view code. Authentication by itself never allows or denies a request — it only identifies the caller, attaching the result to request.user (and request.auth). An unauthenticated request isn't rejected at this stage; it's simply represented as Django's AnonymousUser.

Permissions run immediately after authentication, also before any other view code, and use whatever authentication just determined (request.user / request.auth) to decide whether this specific request should actually be granted or denied.

Gap‑filled — why the order matters

Permissions almost always need to know who the caller is before they can decide anything — a rule like "only admins may delete this" is meaningless until authentication has already determined whether an admin is behind the request. Keeping "identify the caller" and "decide if they may do this" as two separate, sequential steps is a reusable pattern, not something specific to this one API.

DRF's authentication schemes

The video names five approaches DRF supports (badly garbled in the transcript — "connect indications" is reconstructed here as token authentication, matching DRF's actual documented list):

  • BasicAuthentication — username & password sent, base64-encoded, on every request's Authorization header. This topic's focus.
  • TokenAuthentication — a single opaque token sent instead of a username/password (DRF Sessions 15–16).
  • SessionAuthentication — reuses Django's own cookie/session mechanism.
  • RemoteUserAuthentication — trusts an identity already set by the web server/proxy (SSO-style).
  • Custom authentication — a hand-written class implementing authenticate() (DRF Session 17).
Researched — authentication doesn't fail the request

Per the DRF authentication docs, authentication_classes are tried in order and the first one that succeeds wins. If none succeed, request.user becomes AnonymousUser and request.auth becomes None — the request is not rejected here. Only the permission classes decide whether an anonymous request is then allowed to proceed.

DRF's permission classes

  • AllowAny — no restriction; every request is allowed.
  • IsAuthenticated — only logged-in users (staff or not) are allowed; anonymous requests are rejected.
  • IsAdminUser — only users with is_staff=True are allowed; merely being logged in isn't enough.
  • IsAuthenticatedOrReadOnly — anyone can perform safe/read requests; only authenticated users can write. Named in the video, not demonstrated.
Researched — the rest of DRF's built-in permission classes

Per the DRF permissions docs, DRF also ships DjangoModelPermissions (ties access to a user's model-level add/change/delete permissions), DjangoModelPermissionsOrAnonReadOnly, and DjangoObjectPermissions (per-object, needs a backend like django-guardian) — not covered this session, for projects needing finer control than "logged in" vs. "staff."

What HTTP Basic Authentication actually is

The transcript demonstrates using BasicAuthentication but never explains the mechanism, so this is filled in from the DRF docs and RFC 7617.

GET /manager/ HTTP/1.1
Host: 127.0.0.1:8000
Authorization: Basic bW9oYW46bW9oYW5AMTIz

The value after Basic is just username:password run through base64 encoding — reversible by anyone, not encryption. If missing or wrong, DRF replies 401 Unauthorized with a WWW-Authenticate: Basic realm="api" header — the exact header that triggers the browser's native login popup seen in the video.

Industry best practice

Because credentials are only base64-encoded, BasicAuthentication must only ever be used over HTTPS in a real deployment. The DRF docs recommend it mainly for testing and simple server-to-server calls; a browser- or mobile-facing production API should reach for TokenAuthentication (DRF Sessions 15–16) or a session/OAuth scheme instead — resending a raw username/password on every request is a poor fit for anything user-facing in production.

Best practices and pitfalls

  • Don't ship an API relying on the unconfigured AllowAny default — always set an explicit DEFAULT_PERMISSION_CLASSES (or per-view equivalent) before deploying.
  • Prefer configuring authentication/permissions in settings.py for anything project-wide; reserve per-view attributes for genuine exceptions.
  • permission_classes is a list evaluated as an AND, not an OR — every listed class must grant access.
  • Don't lean on is_staff for nuanced business rules ("editors can update but not delete"); that calls for object-level permissions or a custom permission class instead.

DRF Session 14Django REST Framework

14 · Permission classes: from IsAuthenticated to DjangoModelPermissions

Continuing right after basic authentication, this topic tours every built-in DRF permission class — what each one actually allows or blocks — plus a live build-along introducing session authentication and a custom permission class.

Authentication vs. permissions

Authentication answers "who are you?" — it identifies the user making the request (or decides the request is anonymous). Permissions answer "what are you allowed to do, now that we know who you are (or that we don't)?" Every DRF view runs both checks in order: authentication first (attach a request.user, or leave it AnonymousUser), then permissions.

Gap‑filled — why these are always two separate steps

A request can be authenticated and still denied (a logged-in regular user trying to delete something only admins can delete), or fully anonymous and still allowed (a public blog's GET endpoint). "The user can log in but still can't do X" is almost always a permissions problem, not an authentication one — mixing the two up is a common beginner trap.

Configuring authentication & permissions globally

Instead of repeating authentication_classes/permission_classes on every view, DRF reads project-wide defaults from a single REST_FRAMEWORK dictionary in settings.py:

# settings.py
REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'rest_framework.authentication.SessionAuthentication',
    ],
    'DEFAULT_PERMISSION_CLASSES': [
        'rest_framework.permissions.IsAuthenticated',
    ],
}
Optional — setting authentication_classes/permission_classes directly on a view always overrides whatever settings.py says for that one view.
Researched — the pitfall of configuring neither

Per the DRF settings docs, if DEFAULT_PERMISSION_CLASSES is never set at all, DRF's own default is AllowAny — wide open. A fresh DRF project with no permission configuration anywhere lets anyone read and write every exposed model. Setting a sane default (commonly IsAuthenticated) and loosening it per-view is the safer habit.

The built-in permission classes

from rest_framework.permissions import (
    AllowAny,
    IsAuthenticated,
    IsAdminUser,
    IsAuthenticatedOrReadOnly,
    DjangoModelPermissions,
    DjangoModelPermissionsOrAnonReadOnly,
    DjangoObjectPermissions,
)
  • AllowAny — nobody is checked at all, authenticated or not. Fine for genuinely public endpoints.
  • IsAuthenticated — blocks every anonymous request; any logged-in user gets full access.
  • IsAdminUser — only users with is_staff=True get access.
  • IsAuthenticatedOrReadOnly — anonymous requests get read-only (GET/HEAD/OPTIONS); authenticated users get full read+write.
  • DjangoModelPermissions — authenticated users need explicit Django model permissions (add_/change_/delete_) per action; anonymous users are blocked entirely, even for reads.
  • DjangoModelPermissionsOrAnonReadOnly — same as above, but anonymous users get read-only access instead of being blocked.
  • DjangoObjectPermissions — like DjangoModelPermissions but checked per object (row), not just per model.
Gap‑filled — IsAdminUser checks is_staff, not is_superuser

IsAdminUser's real check is bool(request.user and request.user.is_staff). is_staff is the weaker "can log into /admin/" flag, not "has every permission unconditionally" (that's is_superuser). A staff user who isn't a superuser still passes IsAdminUser — if you actually mean "superusers only," this class alone isn't that check.

Researched — DjangoModelPermissions's exact rule

Per the DRF permissions docs, it maps POST→add_<model>, PUT/PATCH→change_<model>, DELETE→delete_<model>, with no permission listed for GET — but a separate authenticated_users_only = True flag still blocks anonymous reads outright. DjangoModelPermissionsOrAnonReadOnly is the same class with that one flag flipped to False.

Researched — why DjangoObjectPermissions needs extra setup

Plain Django tracks permissions per model, not per row — there's no built-in storage for "can user X edit row 42 specifically." Using DjangoObjectPermissions for real requires an object-permission backend added to AUTHENTICATION_BACKENDS, most commonly the third-party package django-guardian. Without one, it behaves the same as DjangoModelPermissions.

401 vs. 403: which status code a denied request gets

The demo consistently shows 403 Forbidden with "Authentication credentials were not provided" for a rejected anonymous request.

Researched — the actual rule depends on the authentication scheme

Per the DRF authentication docs: 401 Unauthorized is returned only when at least one configured authentication class supports a WWW-Authenticate challenge header (e.g. BasicAuthentication, TokenAuthentication). 403 Forbidden covers everything else — an authenticated-but-not-permitted request, or an unauthenticated request under a scheme with no challenge header, like SessionAuthentication (used throughout this demo). Same underlying problem, different code, depending on the scheme.

Session authentication

SessionAuthentication reads request.user straight off Django's own session cookie — the same mechanism behind login()/logout() and the browsable API's own login link — so nothing extra needs to be attached to each request by hand once a browser is logged in.

Good fit when the API is consumed by the same site's own browser-based front end — the session cookie already exists from the normal login flow. Poor fit for a separate client (mobile app, different domain, server-to-server) with no shared browser session — that's what token authentication (next topic) is for.

Custom permission classes

Every built-in class above is itself just a BasePermission subclass — nothing stops writing your own.

# restapp10/custom_permissions.py
from rest_framework.permissions import BasePermission

class CustomPermission(BasePermission):
    def has_permission(self, request, view):
        if request.method == 'GET':
            return True
        return False
Must inherit from BasePermission; DRF calls has_permission() (view-level) and/or has_object_permission() (object-level, only reached for a specific row) and expects True/False back. This version allows only GET — the video also demos flipping it to allow only POST.
Example — a more realistic "owner or read-only" permission
from rest_framework.permissions import BasePermission, SAFE_METHODS

class IsOwnerOrReadOnly(BasePermission):
    def has_object_permission(self, request, view, obj):
        # Reads are always allowed, for anyone.
        if request.method in SAFE_METHODS:
            return True
        # Writes only allowed if this object's author is the requester.
        return obj.author == request.user

Uses has_object_permission (not has_permission) because the check depends on which row is being accessed — it only runs once DRF has a specific object in hand.

Researched — SAFE_METHODS

rest_framework.permissions.SAFE_METHODS is the tuple ('GET', 'HEAD', 'OPTIONS') — the same read-only set IsAuthenticatedOrReadOnly and DjangoModelPermissionsOrAnonReadOnly build their read/write split around. Using the constant is the standard, more maintainable way to write this check rather than hand-listing method strings.

What token authentication is

Token authentication is a simple, token-based HTTP authentication scheme. It's appropriate for client-server setups such as native desktop and mobile clients.

Breaking that down for a beginner:

  • A token here is just a long, random, opaque string (DRF generates a 40-character hex string by default) that stands in for "prove who you are" — instead of sending a username and password with every request, the client sends this one string.
  • "Client-server setups such as native desktop and mobile clients" means: token authentication is the natural fit when the thing calling your API isn't a web browser rendering HTML pages, but a separate program — a mobile app, a desktop app, another backend service, a single-page JavaScript app — that just wants to talk to your API directly over HTTP.
  • The token is obtained once (by logging in, or by an admin creating it), then reused for every request after that, in an Authorization header, until it's revoked or regenerated.
Researched — why not just use session authentication for everything?

Per the DRF authentication docs, session authentication relies on Django's session framework, which is backed by cookies — and cookies are a browser concept. A mobile app or a script calling your API with requests/curl doesn't have a browser's cookie jar, and even if it did, session auth needs a CSRF token for unsafe methods (POST/PUT/DELETE) which adds friction for a non-browser client. Token authentication sidesteps both problems: no cookies, no CSRF token, just one header sent explicitly on every call. That's exactly why it's called out for "native desktop and mobile clients" — those clients can easily store and attach a header, but don't have (or don't want) a browser's session/cookie machinery.

Configuring token authentication in settings.py

Getting TokenAuthentication working needs two separate pieces, and the video is explicit that both are compulsory:

  1. Add 'rest_framework.authtoken' to INSTALLED_APPS — this is a small app that ships inside djangorestframework itself, containing just one model (Token) and its admin registration. Without it, Django has no database table to store tokens in, and the admin panel won't show a "Tokens" section at all.
  2. Add TokenAuthentication to the authentication classes DRF uses — either globally (in a REST_FRAMEWORK settings dict) or per-view.
# settings.py
INSTALLED_APPS = [
    # ...
    'rest_framework',
    'rest_framework.authtoken',   # <- required specifically for token authentication
    'myapp',
]

# Tell DRF, project-wide, to accept tokens as proof of identity
REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'rest_framework.authentication.TokenAuthentication',
    ],
}

Then, because rest_framework.authtoken defines a new model (Token), Django needs to create a table for it in the database — the same migrate step used any time a new model shows up:

python manage.py migrate
Gap‑filled — a common pitfall this step guards against

If you add TokenAuthentication to your settings but forget to add 'rest_framework.authtoken' to INSTALLED_APPS (or forget to run migrate afterward), you'll get errors the moment DRF tries to look up a token — there's no authtoken_token table for it to query. Both halves of this step are required together; skipping either one breaks the feature.

Gap‑filled — DEFAULT_AUTHENTICATION_CLASSES vs. permissions

Setting TokenAuthentication here only controls how DRF figures out who's making a request (by reading the Authorization header). It does not, by itself, block anyone — that's the job of permission classes (REST API Session 14, e.g. IsAuthenticated). Authentication answers "who is this?"; permissions answer "are they allowed to do this?". You typically need both configured for token auth to actually restrict access to anything.

What DRF gives you once a request is authenticated by token

The transcript reads out (garbled) a summary that's actually a direct paraphrase of the DRF docs:

If successfully authenticated, TokenAuthentication provides request.user as a Django User instance, and request.auth as a rest_framework.authtoken.models.Token instance. Unauthenticated responses that fail authentication will result in an HTTP 401 Unauthorized response.
  • request.user — inside any view, once a request carries a valid token, request.user is set to the actual Django User object that token belongs to (so you can do things like request.user.username, or filter a queryset by request.user, exactly as with any other authenticated request).
  • request.auth — is set to the Token object itself (not just the string) — useful if you ever need to inspect the token record, e.g. its created timestamp.
  • A request with no token, or an invalid/unknown token, gets rejected with an HTTP status code in the 401/403 family, instead of request.user being set.
Gap‑filled — the transcript garbled the status code as "404"

404 means Not Found (wrong URL/resource) — that's not what happens here; the URL and view both exist, the request is just not authenticated. The correct code, per the DRF docs, is 401 Unauthorized (with a WWW-Authenticate: Token response header), or 403 Forbidden if that header is suppressed. Option 4 — generating a token via signals

The instructor names this option ("using signals... we can able to expose API endpoints clearly here also we will discuss") but doesn't demonstrate it in this lecture.

Researched

The DRF docs' recommended pattern is a post_save signal on the User model, so that every newly created user automatically gets a token the moment they sign up — no separate step required at all:

# signals.py (or directly in an apps.py AppConfig.ready())
from django.conf import settings
from django.db.models.signals import post_save
from django.dispatch import receiver
from rest_framework.authtoken.models import Token

@receiver(post_save, sender=settings.AUTH_USER_MODEL)
def create_auth_token(sender, instance=None, created=False, **kwargs):
    # `created` is True only on the very first save (i.e. a brand-new user)
    if created:
        Token.objects.create(user=instance)

Actually using the token: the Authorization: Token <key> header

The video is explicit that generating a token is only half the job — "even once we get the tokens, we have to test the API by using the tokens... whether the API is working or not" — but runs out of time before demonstrating an authenticated call (this is what REST API Session 16, "Token authentication in practice," actually walks through). Here's how it works, straight from the DRF docs, so the concept isn't left half-finished.

Once a client has a token (from any of the four methods above), every subsequent request includes it in the HTTP Authorization header, using the keyword Token:

GET /managerview/ HTTP/1.1
Host: 127.0.0.1:8000
Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4
# the same request with curl
curl http://127.0.0.1:8000/managerview/ \
     -H "Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4"
Gap‑filled — contrasting this with REST API Session 13's basic authentication header

Basic authentication's header looks similar in shape but very different in content: Authorization: Basic <base64(username:password)> — literally the account's password, re-encoded (not encrypted — base64 is trivially reversible) and resent on every single request. Token authentication's header, Authorization: Token <key>, never contains the password at all after the initial login — only an opaque key that can be revoked/regenerated independently of the account's actual password. That difference is the main practical reason token authentication is preferred for anything beyond a quick demo: a leaked token can be deleted and reissued without forcing the user to change their password.

Researched — the keyword is case-sensitive and configurable

Per the docs, the header keyword defaults to the literal word Token; a project can change it (e.g. to Bearer, matching common convention for other token schemes like OAuth2/JWT) by subclassing TokenAuthentication and setting its keyword attribute.

Best practices and pitfalls

Industry best practice — token authentication requires HTTPS in production

Because the token is sent as plain text in a header on every request (no encryption of its own), anyone intercepting an unencrypted HTTP connection can read it and impersonate that user until the token is revoked. Django/DRF projects handling real users should always be served over HTTPS; token auth is not "safe by default" over plain HTTP.

Industry best practice — treat a leaked token like a leaked password

Because DRF's token doesn't expire on its own (no built-in time limit) and stays valid until explicitly deleted/regenerated, a compromised token is a standing risk until someone notices and resets it (drf_create_token -r <username>, or deleting the row in the admin). Some teams add their own expiry logic on top (checking the token's created timestamp in custom middleware/authentication) since DRF doesn't do this itself.

Researched — how this compares to JWT (JSON Web Tokens), a very common alternative

DRF's built-in token is intentionally simple: an opaque random string, looked up in the database on every request to find the matching user (one query per request). JWT, a different and very popular token format (not built into DRF itself — it needs a third-party package like djangorestframework-simplejwt), instead encodes the user's identity inside the token itself (cryptographically signed), so the server can verify it without a database lookup, and commonly supports built-in expiry/refresh. DRF's simple TokenAuthentication is a perfectly good, easy starting point (and is what this course teaches); JWT is worth knowing about as the more scalable option many production APIs reach for once they need token expiry or want to avoid a database hit on every request.

Common pitfall — enabling TokenAuthentication without any permission class

As flagged earlier, adding TokenAuthentication to DEFAULT_AUTHENTICATION_CLASSES only tells DRF how to identify a user from a token if one is present — it doesn't require one. Without a permission class like IsAuthenticated (REST API Session 14) on the view, anonymous requests (no Authorization header at all) are still allowed through; request.user just ends up being Django's AnonymousUser instead of a real user.

Recap — the authentication classes so far

In the last session, we discussed token authentication — how to generate tokens, and how to use a token to access your API.

By this point in the course, three built-in DRF authentication schemes have been covered:

  • Basic authentication — username/password sent on every request, base64-encoded in an Authorization header.
  • Session authentication — relies on Django's own login session/cookie (mainly useful for the browsable API and same-site JavaScript clients).
  • Token authentication — a client logs in once, receives a permanent token string, and sends Authorization: Token <token> on every later request.

Today's topic — custom authentication — is presented as the natural fourth option: instead of using one of DRF's ready-made schemes, you write your own authentication class with your own rules for what counts as "authenticated."

What custom authentication is, and why you'd write one

Custom authentication means we can prepare our own authentication system, and we can use that authentication to access the API.

A plain-language way to put it: DRF's three built-in schemes cover the common cases, but real projects sometimes need something else — a signed API key issued to partner companies, a one-time link token, a header format required by an existing mobile app, or (as in this lecture's toy example) a simplified scheme built purely to demonstrate the mechanism.

Gap‑filled

Whenever none of Basic/Session/Token fit your exact requirement, DRF lets you plug in any class that knows how to (a) look at an incoming request and (b) decide who's making it — that's all "authentication" means at the framework level. DRF doesn't care how your class decides; it only cares that your class follows a specific contract, described next.

The authenticate(self, request) contract

You can create your own authentication class, and it should be inherited from BaseAuthentication. The method should return a tuple of user and auth if authentication succeeds. If authentication is not attempted, it should return None. If authentication is attempted but fails, raise an AuthenticationFailed exception.

Every custom authentication class must:

  1. Subclass rest_framework.authentication.BaseAuthentication — the base class that defines the interface DRF expects.
  2. Implement one method: authenticate(self, request). DRF calls this automatically for every incoming request, for every authentication class listed in authentication_classes, until one of them succeeds (or all of them are exhausted).

authenticate() has exactly three possible outcomes, and DRF treats each one differently:

OutcomeWhat you doWhat DRF does next
Success return (user, auth) — a two-item tuple: the authenticated user object, and an optional second value (often None) representing auth-scheme-specific data (e.g. the token used) Sets request.user and request.auth to those values; the request is considered authenticated
Not attempted return None (not a tuple — just the value None) Treats this scheme as "didn't apply" and moves on to check any other authentication classes configured for the view; if none succeed, the request falls back to AnonymousUser

Gap‑filled — why the "not attempted vs. failed" distinction matters

This is easy to get backwards as a beginner, so it's worth restating plainly: return None means "I have nothing to say about this request — maybe some other scheme can identify it, or maybe it should just be anonymous." Raising AuthenticationFailed means "this request DID try to use my scheme, and what it gave me was wrong — stop everything and tell the client immediately." Get this wrong (e.g. always raising instead of returning None when no credentials are present at all) and you'll break any view that's supposed to allow anonymous access alongside your custom scheme, because a raised exception short-circuits everything else.

The class itself

class CustomAuthentication(BaseAuthentication):
    """
    A minimal custom authentication scheme: a request is considered
    authenticated if it supplies a ?username=<name> query parameter
    that matches an existing Django User.
    """

    def authenticate(self, request):
        # Pull the value of the "username" query-string parameter, e.g.
        # /manager/?username=Mohan  ->  username = "Mohan"
        # request.GET.get(...) is a dict-style lookup, but it returns None
        # instead of raising an error if the key isn't present at all.
        username = request.GET.get('username')

        # Case 1: no ?username=... was supplied at all -> nothing to check,
        # so we tell DRF "this scheme wasn't attempted" by returning None.
        if username is None:
            return None

        try:
            # Case 2 (happy path): try to find a matching User row.
            user = User.objects.get(username=username)
        except User.DoesNotExist:
            # Case 3: a username WAS supplied, but it doesn't match any
            # real user -> authentication was attempted and it failed,
            # so we raise, which stops everything immediately.
            raise AuthenticationFailed('User does not exist')

        # Success: return the (user, auth) tuple DRF expects. The second
        # value is for any extra per-request auth data; there isn't any
        # here, so it's just None.
        return (user, None)

This is a direct, cleaned-up transcription of what's typed on screen in the video — the logic (return None / raise AuthenticationFailed / return a tuple) matches the contract above exactly.

Gap‑filled — this scheme has no password check

Gap‑filled — how these two settings cooperate

authentication_classes and permission_classes do two different jobs that are easy to blur together as a beginner:

  • authentication_classes answers "who is this?" — it runs first, tries each listed class's authenticate() in order, and sets request.user (to a real user, or to Django's built-in AnonymousUser if nothing succeeded and nothing raised).
  • permission_classes answers "is that identity allowed to do this?" — it runs after authentication, and looks at whatever request.user ended up being. IsAuthenticated (covered in REST API Session 14's permission classes topic) simply checks request.user.is_authenticated and rejects the request with 403 Forbidden if it's False — which is exactly what AnonymousUser reports.

So in this view: if ?username= is missing entirely, CustomAuthentication.authenticate() returns None, request.user falls back to AnonymousUser, and IsAuthenticated then blocks the request. If ?username= names a real user, request.user becomes that real User object, and IsAuthenticated lets it through. If ?username= names a nonexistent user, AuthenticationFailed is raised straight out of the authentication step, before permission_classes is even consulted.

Security note — query strings vs. headers

Gap‑filled / Researched

The demo scheme reads its credential from a URL query parameter (request.GET.get('username')). That's fine for a five-minute classroom demo of the authenticate() mechanism, but it would be a poor choice for production, for a few concrete reasons:

  • No secret is checked at all — knowing (or guessing) any existing username is enough; there's no password, token, or signature involved, so anyone who can see the auth_user table (or just guess common usernames) can impersonate any user.
  • Query strings leak. URLs get logged by web servers, proxies, and browser history, and get sent in the Referer header to any third-party resource the page loads — a genuinely sensitive value (an API key, a session token) showing up in a URL is a well-known way for it to end up somewhere it shouldn't.
  • Real-world custom schemes almost always read their credential from a request header instead — e.g. request.META.get('HTTP_X_API_KEY') or (in modern DRF/Django) request.headers.get('X-API-Key') — mirroring how Basic and Token authentication both already work (Authorization: <scheme> <credential>), and pairing the identifier with an actual secret value that's checked against a hash, not just an existence check.
Researched — authenticate_header(), and why the demo returns 403 instead of 401

Per the DRF authentication docs, a BaseAuthentication subclass can also override a second method, authenticate_header(self, request), returning a string to use as the WWW-Authenticate header on a 401 Unauthorized response. If a class doesn't implement it (as in this lecture's example), DRF cannot legally send 401 (the HTTP spec requires a WWW-Authenticate header alongside 401), so it falls back to returning 403 Forbidden instead whenever authentication fails or is missing — which is exactly the status the video's browsable-API screenshots would be showing, even though the on-screen JSON body just says "Authentication credentials were not provided."

Example — a header-based custom scheme

Example

To contrast with the query-string version above, here's a small, self-contained example of the more realistic pattern (a shared secret sent in a custom header), demonstrating the same authenticate() contract with a safer credential source:

# A more production-shaped variant: a fixed per-request header, checked
# against a value stored on the User model (e.g. a "api_key" field you'd
# add via a Profile model or similar -- omitted here for brevity).

class ApiKeyAuthentication(BaseAuthentication):
    def authenticate(self, request):
        api_key = request.headers.get('X-Api-Key')  # e.g. "X-Api-Key: abc123"

        if not api_key:
            return None  # no header at all -> let other schemes/anonymous apply

        try:
            user = User.objects.get(profile__api_key=api_key)
        except User.DoesNotExist:
            raise AuthenticationFailed('Invalid API key')

        return (user, api_key)  # api_key is available afterwards as request.auth

    def authenticate_header(self, request):
        return 'X-Api-Key'  # lets DRF return a proper 401 instead of 403

Researched — the difference between queryset and get_queryset()

Per the DRF generic views docs, setting queryset = Student.objects.all() as a class attribute is evaluated once, when the class is defined — it's a single, fixed queryset shared across every request. Any time a queryset needs to vary based on who's asking, get_queryset() is the correct tool; a plain queryset = attribute is only appropriate when the same data should be returned to everyone.

DRF's declarative filter backends let API clients narrow, search, and sort a queryset entirely through the URL's query string, on top of the manual get_queryset() filtering from the previous session.

Recap — manual filtering with get_queryset()

The previous session showed the most basic filtering approach: instead of a generic view's queryset attribute being a fixed Model.objects.all(), override get_queryset() and build the queryset per-request, reading a query parameter off self.request.query_params.

# views.py
from rest_framework import generics
from .models import Student
from .serializers import StudentSerializer

class StudentList(generics.ListAPIView):
    serializer_class = StudentSerializer

    def get_queryset(self):
        # query_params is DRF's read-only wrapper around ?key=value
        queryset = Student.objects.all()
        address = self.request.query_params.get('address')
        if address is not None:
            queryset = queryset.filter(address=address)
        return queryset

get_queryset() is a method, re-run on every request, so — unlike a fixed queryset class attribute — it can inspect self.request and return a different result each time.

Filtering against the current logged-in user

A common real need: an API where each user only ever sees their own rows. Because DRF's authentication classes set self.request.user to the authenticated caller, get_queryset() is exactly the tool for this too — it's identity-based, not something driven by the query string.

class MyStudentRecords(generics.ListAPIView):
    serializer_class = StudentSerializer
    permission_classes = [permissions.IsAuthenticated]

    def get_queryset(self):
        user = self.request.user
        return Student.objects.filter(owner=user)
Gap‑filled — the code for this pattern

The video described this idea without a full listing. This is a different kind of filtering than the rest of the lecture — none of DjangoFilterBackend, SearchFilter, or OrderingFilter below can express "only rows owned by whoever is logged in," since those backends only ever read the URL's query parameters, never request.user. The two techniques combine naturally: scope to the user in get_queryset() first, then let a declarative backend filter/order within that scope.

What "generic filtering backends" means

Writing a get_queryset() override by hand for every filterable field gets repetitive, and none of that logic is visible to the browsable API — a visitor has no way to discover which fields are filterable. DRF instead offers reusable filter backend classes: attach one or more to a view via filter_backends, and DRF runs each on the queryset before serializing — and can render matching controls (a search box, filter fields) right inside the browsable API.

  • DjangoFilterBackend — third-party django-filter package; exact-match filtering on named fields.
  • SearchFilter — built into rest_framework.filters; a single free-text search box across text fields.
  • OrderingFilter — built into rest_framework.filters; lets the client choose sort field(s).

Only DjangoFilterBackend requires installing the separate django-filter package. SearchFilter and OrderingFilter ship with DRF core, per the DRF filtering docs — no extra install needed. The case-sensitive ordering "bug" the video ran into

The video's closing minutes are a live debugging session: a new row named "Anwesh" is added, and ?ordering=name / ?ordering=-name don't sort the way the presenter expects — the video ends mid-investigation, without a clean resolution on camera.

Gap‑filled — reconstructing the likely cause

The most likely explanation, matching the presenter's own comment about "capital letters having the least value": case-sensitive string ordering. SQL's default ORDER BY sorts text by character code, and uppercase letters (codes 65–90) sort before lowercase (97–122) in common collations. A dataset mixing consistently-capitalized names with an inconsistently-entered one (a stray case or space typed into the admin panel) won't sort the way a human expects "alphabetical" to mean, even though the database is doing exactly what it was told.

Researched — the standard fixes

Per the Django QuerySet reference: annotate with Lower() and order by that (.annotate(name_lower=Lower('name')).order_by('name_lower')), or configure a case-insensitive collation at the database level. OrderingFilter itself just passes the client's field straight to .order_by(), so whatever the database's default case-sensitivity is, that's what the client sees.

Best practices & common pitfalls

Industry best practice — prefer declarative backends over hand-rolled filtering

The three filter backends are self-documenting (they surface as browsable-API controls) and far less code than equivalent .filter() chains in get_queryset(). Reserve manual overrides for logic the backends can't express, like scoping to request.user.

Industry best practice — index filtered/ordered columns

Every field in filterset_fields, search_fields, or ordering_fields is a column the database may filter/sort on for arbitrary client requests. Per Django's db_index docs, indexing frequently filtered/ordered fields keeps this fast at scale.

Pitfalls: mixing up the three attribute names (silent no-op, not an error — see the ordering section above); forgetting either the pip install or the INSTALLED_APPS step for django-filter (a ModuleNotFoundError, as the video hits live); confusing DjangoFilterBackend's exact match with SearchFilter's partial match; and the case-sensitive ordering surprise covered above.

19 · Pagination in DRF: PageNumberPagination

Large result sets get slow and unwieldy to return whole, so DRF ships three pagination styles. This topic builds PageNumberPagination end to end — global and per-view settings, a custom pagination class, and the client-facing knobs that control it — while LimitOffsetPagination and CursorPagination are named for next session.

Why pagination exists

A queryset can hold far more rows than it makes sense to return in one response. Returning everything at once means a huge payload to transfer and parse, and a UI the user has to scroll through endlessly to find anything. Pagination splits a large result set into fixed-size "pages" and lets the caller request one page at a time — commonly by clicking page numbers or passing a page number as a parameter.

Gap‑filled — why this matters beyond convenience

For an API, an unpaginated endpoint re-fetches and re-serializes the entire table on every request, with a payload that grows without bound as the table grows — something that works fine with 50 rows in development can time out or exhaust memory in production with 500,000. Pagination caps every request to a predictable, small cost regardless of how large the table gets.

DRF's own framing

The instructor reads this close to verbatim from the official docs: pagination "allows you to modify how large result sets are split into individual pages of data," and pagination links can be provided "as part of the page content, or [as] response headers such as Content-Range or Link."

Researched — the DRF docs, precisely

Per the DRF pagination docs, links can be included either as part of the response body (e.g. next/previous URLs inside the JSON) or via response headers such as Content-Range/Link. DRF's built-in classes default to body-based pagination so the browsable API stays self-contained and clickable without inspecting headers.

Three pagination styles

DRF ships three built-in pagination classes, all importable from rest_framework.pagination: PageNumberPagination (a page number in the query string, e.g. ?page=3), LimitOffsetPagination (a limit and an offset), and CursorPagination (an opaque cursor token). This session covers only PageNumberPagination in full — the other two are named as "next session" (Monday) material.

Researched — a preview of the other two styles

LimitOffsetPagination mirrors SQL's LIMIT/OFFSET — flexible, but like page numbers it can show duplicate or skipped rows if data changes between requests. CursorPagination replaces page numbers with an opaque token tied to an ordering; it can't jump to an arbitrary page, but it stays performant on huge tables and avoids duplicates/gaps when rows are added or removed mid-pagination — the recommended choice for large, frequently-changing datasets like an infinite-scroll feed.

PageNumberPagination: the basic idea

"This pagination style accepts a single number — page number — in the request query parameters," e.g. ?page=4. Once active on a view, that request returns only page 4's rows, not the whole table; omitting the parameter defaults to page 1.

Turning it on: global settings

Two settings are always required together: which pagination class to use, and the page size. Globally, both go in the project's REST_FRAMEWORK settings dict:

# settings.py

REST_FRAMEWORK = {
    'DEFAULT_PAGINATION_CLASS': 'rest_framework.pagination.PageNumberPagination',
    'PAGE_SIZE': 3,   # the video uses 3 so 12 demo records split into 4 pages
}

DEFAULT_PAGINATION_CLASS is a string import path to the class every view uses unless it overrides it; PAGE_SIZE sets how many records land on each page. Setting this applies pagination to every list-returning view in the project (it has no effect on single-object detail responses).

Gap‑filled — why PAGE_SIZE is required, not optional

PageNumberPagination.page_size defaults to None in DRF's own source, and a class with page_size = None performs no pagination at all — it silently returns everything, no error. Setting DEFAULT_PAGINATION_CLASS without also setting PAGE_SIZE looks like it should paginate but doesn't. Always set both together.

Turning it on: per-view settings

To paginate just one view instead of the whole project, set the pagination_class attribute directly on it — the same "override per view, fall back to a project default" pattern already used for authentication and permission classes in earlier topics.

from rest_framework import generics
from rest_framework.pagination import PageNumberPagination

class StudentList(generics.ListAPIView):
    queryset = Student.objects.all()
    serializer_class = StudentSerializer
    pagination_class = PageNumberPagination   # pagination only for this view
Gap‑filled — global vs. per-view

Global settings are right for consistent pagination across the whole API — the common case. Per-view pagination_class is for exceptions: an endpoint that should never paginate (set pagination_class = None directly), or one that needs a different page size than the rest of the API.

A custom, per-view pagination class

Gap‑filled — why subclass instead of using PageNumberPagination bare

A bare pagination_class = PageNumberPagination still needs a page size from somewhere (it falls back to the global PAGE_SIZE, or paginates nothing if that's unset too). Subclassing lets a view carry its own page size — and, as shown next, its own parameter names — without depending on any global setting at all.

Renaming the page parameter

By default PageNumberPagination only recognizes a query parameter literally named page — ?p=2 is silently ignored, defaulting back to page 1, with no error. page_query_param changes which name it listens for.

class MyPagination(PageNumberPagination):
    page_size = 3
    page_query_param = 'p'   # now ?p=2 works; ?page=2 no longer does
Gap‑filled — an easy trap

Because an unrecognized parameter causes no error — just silent fallback to page 1 — this is easy to misdiagnose as "pagination is broken" when client and API simply disagree on the parameter name. Always confirm the exact expected name rather than assuming page is universal.

Letting the client choose the page size

By default the page size is fixed server-side. page_size_query_param opts into letting the client request a different size per request via a query parameter of that name — the video demonstrates ?records=4, ?records=5, and ?records=2 each changing how many rows come back.

class MyPagination(PageNumberPagination):
    page_size = 3
    page_query_param = 'p'
    page_size_query_param = 'records'   # ?records=4 → 4 rows per page instead of 3

Capping the client-requested page size

page_size_query_param alone lets a client ask for an unbounded page size (?records=100000), defeating the point of pagination. max_page_size caps it — requests above the cap are silently clamped, not rejected. The video sets max_page_size = 5 and shows ?records=7 still returning only 5 rows.

class MyPagination(PageNumberPagination):
    page_size = 3
    page_query_param = 'p'
    page_size_query_param = 'records'
    max_page_size = 5   # ?records=7 still only returns 5 rows
Researched — why max_page_size matters

Per the docs, page_size_query_param is None by default specifically so a project must opt in to client-controlled page sizes; once opted in, max_page_size is the recommended safeguard against a client requesting a page large enough to hurt performance — re-introducing the exact problem pagination exists to solve. Always pair the two.

Example — a standalone PageNumberPagination setup

A hypothetical Book API, combining every option in one place:

Industry best practice

Always set a page size alongside a pagination class; always cap page_size_query_param with max_page_size; always order the queryset explicitly; document the actual parameter names an API uses; and prefer CursorPagination over page-number/offset styles for large, frequently-changing datasets, since numeric-position pagination can show duplicate or skipped rows when data changes mid-pagination.

Limit/offset pagination — what it is

The instructor reads directly from the DRF documentation on screen, matching it closely:

This pagination style mirrors the syntax used when looking up multiple database records. The client includes both a limit and an offset query parameter. The limit indicates the maximum number of items to return. The offset indicates the starting position of the query in relation to the complete set of un-paginated items.

In plain language:

  • limit — how many records you want back in one response (like SQL's LIMIT).
  • offset — how many records to skip before starting to collect results (like SQL's OFFSET). "Offset 7" means "skip the first 7 records, then start counting."

So ?limit=4&offset=7 reads as: "skip the first 7 records, then give me the next 4" — i.e. records #8, #9, #10, #11 (1-indexed).

Cursor pagination — what it is and why it's different

Again read closely from the official docs on screen:

The cursor-based pagination presents an opaque "cursor" indicator that the client may use to page through the result set. This pagination style only presents forward and reverse controls — there are no page numbers.

The key distinguishing idea: instead of a page number or a numeric offset, CursorPagination gives the client an opaque cursor token — an encoded string that doesn't mean anything to the client, but that the server can decode to know exactly where the previous page left off. The browsable API for a cursor-paginated view therefore shows only Next and Previous buttons — never a numbered page list, and never a raw ?page=3 you could type in by hand to jump around.

Researched — why cursor pagination exists at all

Per the DRF docs, offset-based pagination styles (LimitOffsetPagination, and to a lesser extent PageNumberPagination) have a real weakness on data that changes between requests: if a new row is inserted near the start of the ordering while a client is paging through results, every subsequent offset shifts by one, causing the client to see a duplicate record or skip one entirely. CursorPagination avoids this because the cursor encodes a position relative to a specific record (per the ordering field) rather than a raw numeric position — so insertions/deletions elsewhere in the table don't desynchronize the client's paging. This is exactly why cursor pagination is the standard choice for things like social media feeds and activity logs, where new rows are constantly being added while users scroll.

Gap‑filled — a caveat the video doesn't mention

The DRF docs recommend ordering by a field that is both unique and effectively immutable — a creation timestamp or auto-incrementing ID are ideal, because they guarantee a strict, stable order with no ties. Ordering by name (as this demo does, for simplicity, since the Student model has no timestamp field) can be unreliable in a real project if two students share the same name — the cursor position could become ambiguous between tied rows. For a production API, prefer ordering = '-id' or an actual created_at field over a non-unique text field like name.

Just like limit_query_param/offset_query_param, the cursor's own query parameter name is customizable:

Gap‑filled — a practical limitation worth knowing

Because there's no numeric page number under the hood, cursor pagination cannot support "jump to page 7" style UI — only "next"/"previous." If a project's UI genuinely needs numbered page links (common in admin dashboards), PageNumberPagination or LimitOffsetPagination are better fits; CursorPagination trades that convenience for stability on frequently-changing data, per the section above.

New topic: HyperlinkedModelSerializer — motivation

With pagination finished, the instructor moves to a related but separate concept:

Hyperlink model serializer means: you have to provide a link, and when the user clicks on that link, then automatically they will access the API. So far, whatever we discussed in the browsable API, records are coming record by record — but now I have to click on the link, and through the link we'll be able to access the record. That is called hyperlink model serializer.

In plain language: a normal ModelSerializer (used everywhere earlier in this course) represents each record's identity with its raw primary key ("id": 3). A HyperlinkedModelSerializer instead represents each record's identity as a clickable URL pointing straight to that record's own detail endpoint ("url": "http://127.0.0.1:8000/studentapi/3/") — clicking it in the browsable API navigates directly to that one record, where it can be viewed, updated, or deleted through the browsable API's own forms.

Gap‑filled — why this matters beyond "it looks nicer"

This is a small taste of a REST design principle called HATEOAS (Hypermedia As The Engine Of Application State) — the idea that an API response shouldn't just hand back raw data and IDs, but should also tell the client where to go next via embedded links, the same way a web page's <a href> links tell a human browser where to go next. A client consuming a hyperlinked API doesn't need to know your URL-building conventions in advance (e.g. "detail URLs are /studentapi/<id>/") — it can just follow the url field it was given.

Researched — why "url" has to be listed explicitly

Per the DRF docs on HyperlinkedModelSerializer, this serializer class behaves like an ordinary ModelSerializer except that record relationships (and the record's own identity) are represented with hyperlinks instead of primary keys — by default it adds a url field, built from a HyperlinkedIdentityField, in place of (or alongside) the model's real primary key. But url is not an actual field on the Student model — it's a serializer-only, computed field. Whenever Meta.fields is set to an explicit list (rather than left out to mean "every model field"), Django REST Framework only includes fields that are in that list — so if 'url' isn't spelled out, it's silently dropped, exactly matching the bug shown in the video.

Gap‑filled — how DRF builds that URL

This is exactly the URL name that a DefaultRouter (next section) generates automatically once a ModelViewSet is registered — which is why the two pieces (serializer + router) have to agree on the same basename.

The final lecture of the DRF unit — throttling, DRF's system for limiting how often a client may call an API, as distinct from authentication (who are you) and permissions (are you allowed at all).

What throttling is, and how it differs from permissions

Throttling concept is similar to permission, but in this throttling concept, so we can able to restrict the users — how many times user can able to send the request to the API? So how many number of times users can able to send the request to the API? We can able to restrict that. That is concept called throttling.

Throttling limits how many times a client can send a request to an API within a given time window — e.g. three times per hour, or three times per day. Once that count is exceeded, further requests are rejected until enough time has passed.

A permission check gives the same yes/no answer for the same user every time. A throttle's answer to the exact same request can flip from allowed to blocked purely because a counter ticked over — that's why the DRF docs describe it as a "temporary state" rather than a fixed rule.

The official DRF definition

Throttling is similar to permissions, in that it determines if a request should be authorized. Throttles indicate a temporary state, and are used to control the rate of requests that clients can make to an API. As with permissions, multiple throttles may be used. Your API might have a restrictive throttle for unauthenticated requests, and a less restrictive throttle for authenticated requests.

Multiple throttles can be attached to the same view — e.g. a tight limit for anonymous requests, a looser limit for authenticated requests. This is exactly what the live demo below builds.

Researched — why you might combine multiple throttles
  • Different constraints for resource-intensive endpoints — a cheap GET /products/ list can allow far more requests than an expensive POST /reports/generate/.
  • Burst rate + sustained rate together — e.g. a maximum of 60 requests/minute and 1000 requests/day on the same view; the request is blocked the moment either limit is exceeded.
# burst + sustained throttling on one view, per the DRF docs
class BurstRateThrottle(UserRateThrottle):
    scope = 'burst'

class SustainedRateThrottle(UserRateThrottle):
    scope = 'sustained'

class ExampleView(APIView):
    throttle_classes = [BurstRateThrottle, SustainedRateThrottle]

The docs also note throttles aren't only for rate limiting — a storage service might throttle against bandwidth, and a paid data service might throttle against a number of records accessed, rather than a raw request count.

Several unrelated views can share one throttle bucket just by giving them the same throttle_scope string — no new Python class needed per bucket, unlike the hand-rolled MohanRateThrottle approach.

Industry best practices & pitfalls

Industry best practice

Set both a burst rate and a sustained rate for anything resource-intensive — one throttle class alone can't catch both "hammering the endpoint in a tight loop" and "slowly draining a daily quota." Document published rate limits clearly so client developers can build retry/backoff logic instead of discovering the limit by trial and error in production.

Pitfall — the default cache backend breaks throttling across multiple workers

Django's default LocMemCache is local to a single process. In a real deployment with multiple Gunicorn/uWSGI workers, each worker keeps its own separate throttle counts, so a client could get up to (rate × worker count) requests through. Configure a shared cache backend (Redis or Memcached) for throttling to enforce a rate accurately in production.

Pitfall — IP-based anonymous throttling punishes shared networks

Every anonymous user behind the same NAT/proxy shares one AnonRateThrottle bucket — a known trade-off, not a bug. Choose anonymous rate limits generously enough to absorb this.

Pitfall — throttling is not a substitute for permissions

A throttle only limits how often; it never blocks an action outright the way IsAuthenticated or a custom permission does. Use permission classes to decide if an endpoint should be public at all — throttling only bounds the frequency of otherwise-permitted access. Also remember throttle_classes on a view replaces, not adds to, the global DEFAULT_THROTTLE_CLASSES — list every throttle a view needs explicitly.
