## 1. What middleware is **[From video]**

> Middleware is something that acts as a mediator. It is a framework related to Django's request and response processing — a lightweight, low-level plugin system for globally altering Django's input and output.

Normally: client sends a request → server processes it → server sends a response. **Middleware sits in between** — every request passes through it on the way to the view, and every response passes through it on the way back to the client. If you need to do something *before* a view runs, or *after* it runs but before the response reaches the browser, that's what middleware is for.

The video's central example: if a server is genuinely unable to process a request (down for maintenance, overloaded), **the server itself never sends a response** — because it can't. What the client actually sees ("Service temporarily unavailable," "Please try again later") is generated by *middleware*, intercepting the request before it ever reaches an unavailable server and responding on the server's behalf.

> **[Gap-filled] — the ATM analogy, made explicit.** The video's own comparison: an out-of-service ATM doesn't silently do nothing — it displays "This ATM is temporarily out of order, please visit the nearest ATM center." That message isn't coming from the (unavailable) banking backend; it's coming from a layer in front of it that knows the backend is unreachable and responds accordingly. Django middleware plays exactly this role for a web request: a layer positioned to intercept and respond independently of whether the "real" view/server logic behind it can run at all.

## 2. Two types of middleware **[From video]**

| Type | What it is |
|---|---|
| **Built-in middleware** | Ships with Django, already configured in `MIDDLEWARE` in every new project's `settings.py`. |
| **Custom middleware** | Middleware you write yourself, for your project's own needs. |

### Built-in middleware already in every project

Opening `settings.py`, the `MIDDLEWARE` list already includes (among others, in a default project):

- `SecurityMiddleware`
- `SessionMiddleware` (from Lecture 24 — this is *why* `request.session` just works)
- `CommonMiddleware`
- `CsrfViewMiddleware` (this is *why* `{% csrf_token %}` gets enforced — Lecture 19)
- `AuthenticationMiddleware` (this is *why* `request.user` just works — Lecture 28)
- `MessageMiddleware` (this is *why* the messages framework — Lecture 20 — just works)
- `XFrameOptionsMiddleware`

> **[Gap-filled] — this reframes a lot of earlier "it just works" behavior.** Several mechanisms taken for granted across this course — `request.session`, `request.user`, CSRF enforcement, the messages framework — aren't special-cased into Django's core; they're each implemented as one entry in this same `MIDDLEWARE` list, following the exact request-in/response-out interception pattern this lecture is about to build from scratch. Custom middleware isn't a niche feature bolted onto the side of Django — it's the same mechanism several already-familiar features are built on.

## 3. Custom middleware, function-based **[From video]**

```bash
python manage.py startapp middleware_app
```

```python
# settings.py
INSTALLED_APPS = [
    # ...
    'middleware_app',
]
```

Middleware doesn't get its own dedicated command or default file (unlike `forms.py`/`models.py`/`urls.py`) — it's just a plain Python file, created manually inside the app:

```python
# middleware_app/middleware.py
def my_middleware(get_response):
    print("one time initialization")   # runs once, when the server starts

    def middleware_function(request):
        print("this is before view calling")
        response = get_response(request)
        print("this is after view calling")
        return response

    return middleware_function
```

- `my_middleware(get_response)` is the **outer function** — it receives `get_response`, a callable representing "the next thing in the chain" (either the actual view, or the next middleware in line). Code at this level (the `print("one time initialization")`) runs **once**, when the server starts — not per request.
- `middleware_function(request)` is the **inner function**, returned by the outer one — this is what actually runs on **every single request**. Anything before `get_response(request)` is called runs *before* the view executes; anything after is *after-view* processing, once the view has already produced its response.
- `get_response(request)` is the call that actually hands the request onward — either to the next middleware, or (if this is the last one) to the matching view itself — and gets back its response.
- Returning `middleware_function` (not calling it) from the outer function is what makes this whole thing work: Django calls `my_middleware(get_response)` once at startup to get back the per-request handler, then calls *that* handler on every request.

```python
# settings.py
MIDDLEWARE = [
    # ...existing built-in middleware...
    'middleware_app.middleware.my_middleware',
]
```

That string is a dotted path: `<app>.<file>.<function name>` — this is how Django is told the middleware exists and should be wired into the chain. Without this line, `middleware.py` is just an inert file; nothing about creating it activates it.

```python
# middleware_app/views.py
from django.http import HttpResponse

def v1(request):
    print("this is the view")
    return HttpResponse("This is my first middleware program.")
```

Running the server and visiting the view's URL, the terminal shows, in order:
```
one time initialization      (printed once, at server startup — not shown again on refresh)
this is before view calling
this is the view
this is after view calling
```

Confirming exactly the flow described above: the middleware wraps the view, running code both before and after it, on every request, while the outer function's own code runs only once.

## 4. Custom middleware, class-based **[From video]**

The same mechanism, expressed as a class instead of nested functions — and put to a genuinely useful purpose: intercepting **every** request to show a "site under construction" message, without the request ever reaching the actual view.

```python
# middleware_app/middleware.py
from django.http import HttpResponse

class SiteUnderConstructionMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        return HttpResponse(
            "<h1>Currently the site is under construction. "
            "Please visit after a few days.</h1>"
        )
```

- `__init__(self, get_response)` — Python's constructor, storing `get_response` on the instance, the class-based equivalent of the function version's outer function.
- `__call__(self, request)` — a special Python method that makes an *instance* of the class itself callable like a function (`some_instance(request)` works exactly like calling a plain function). Django calls this automatically for every incoming request.
- Critically, this version **never calls `self.get_response(request)` at all** — it returns an `HttpResponse` directly. That means the request never reaches the intended view; the middleware short-circuits the chain entirely, exactly what a genuine "site under maintenance" response needs to do.

```python
# settings.py
MIDDLEWARE = [
    # ...
    'middleware_app.middleware.SiteUnderConstructionMiddleware',
]
```

With this activated, **every** URL in the project shows the under-construction message — none of them ever reach their actual view. Commenting the line back out of `MIDDLEWARE` (and restarting the server) restores normal behavior immediately, with no other code changed anywhere.

> **[Gap-filled] — this demonstrates something the function-based example didn't: middleware can refuse to forward the request at all.** Section 3's function-based middleware always calls `get_response(request)` eventually — it observes and wraps the request/response cycle, but never blocks it. This class-based example shows the other half of what middleware can do: because `self.get_response` is just a stored value, calling it is entirely optional. Skipping it is exactly how a real maintenance-mode feature, an IP-based block, or a maintenance banner middleware would work in production — deciding, before the view ever runs, whether the request should proceed at all.

## 5. Handling unhandled exceptions with `process_exception` **[From video]**

Beyond wrapping the request/response cycle, a middleware class can define a special method Django calls automatically whenever a view raises an unhandled exception:

```python
# middleware_app/middleware.py
class ErrorMessageMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        return self.get_response(request)

    def process_exception(self, request, exception):
        return HttpResponse("Currently we are facing some technical issues.")
```

```python
# middleware_app/views.py
def v1(request):
    x = 10 / 0   # deliberately raises ZeroDivisionError, to trigger process_exception
    return HttpResponse("This is homepage.")
```

With `ErrorMessageMiddleware` activated in `MIDDLEWARE`, visiting a view that raises an exception (here, a deliberate division by zero) no longer shows Django's default technical error page — instead, the middleware's `process_exception` catches it and returns the friendly "we are facing some technical issues" message instead. Removing the faulty line (or removing the middleware) restores normal behavior.

> **[Researched] — `process_exception` is one of several optional middleware hooks.** Per the [Django docs](https://docs.djangoproject.com/en/stable/topics/http/middleware/#other-middleware-hooks), `process_exception(request, exception)` is called only when a view raises an exception that isn't otherwise handled, and is expected to return either `None` (let Django's normal error handling continue) or an `HttpResponse` (as here, to replace the default error page entirely). It's one of a few optional hooks beyond the required `__init__`/`__call__` pattern — others include `process_view` (before the view function is called, with access to the view and its arguments) and `process_template_response` (for responses that carry a `render()` method) — none of which this lecture demonstrates, but which follow the same "Django calls this automatically, at this specific point in the cycle, if it's defined" pattern.

> **Industry best practice:** A real production error-handling middleware would typically also **log** the exception (so developers can actually investigate it) before returning a generic message to the user — showing a friendly message without recording what went wrong just hides the problem rather than surfacing it to whoever needs to fix it. This lecture's example is intentionally minimal to demonstrate the mechanism, not a complete error-handling strategy.
