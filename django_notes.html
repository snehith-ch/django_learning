Session 3Getting started

01 · Checking your tools & installing Django

Before you build anything, you check that Python, pip, and Django are actually installed — and if Django isn't there yet, you install it with one command.

What's actually going on

Django is not part of Python itself — it's an extra package you install on top of Python. So the very first thing every Django developer does is confirm three things are in place: Python, pip (Python's package installer — a tool that downloads and manages extra libraries like Django), and Django itself.

# Check which Python version you have
python --version

# Check which pip version you have
pip --version

# Check which Django version you have (only works if Django is installed)
django-admin --version

# Install Django
pip install django
If django-admin --version replies with something like "command not found," that just means Django isn't installed yet — run pip install django and try again.

Why this step

Checking versions first saves you from a very common beginner trap: following a tutorial written for a different Python or Django version and getting confused by errors that have nothing to do with your actual code. It also confirms pip is working, since you'll use pip constantly to install every other package your project needs later (like the REST framework, database drivers, etc.).

Industry best practice

Real projects pin exact versions instead of just "having Django installed" — e.g. a requirements.txt file listing Django==5.0.6. That way, everyone on the team (and the production server) runs the exact same version, instead of "it works on my machine."

Gap‑filled

The video's commands were transcribed a little garbled (e.g. "Django admin admin"). The real commands are exactly python --version, pip --version, and django-admin --version — two dashes before "version", no extra words.

02 · Virtual environments

A virtual environment is a private, isolated copy of Python just for one project, so its packages don't clash with any other project's packages.

What it is

Imagine every Python project on your computer shared one single toolbox. If Project A needs Django 4 and Project B needs Django 5, they'd fight over which version sits in the toolbox. A virtual environment (often shortened to "venv") gives each project its own private toolbox, so Project A and Project B can each have the Django version they need, at the same time, with zero conflict.

# Create a virtual environment named "venv" inside your project folder
python -m venv venv

# Activate it — Windows
venv\Scripts\activate

# Activate it — macOS / Linux
source venv/bin/activate

# Once activated, install packages as normal — they stay inside this venv
pip install django
You'll know it's active because your terminal prompt gets a (venv) prefix. To leave it, type deactivate.

Why this step

Without a virtual environment, every pip install you run installs the package globally on your machine — for every project. Over time this turns into a mess where projects silently break each other. Isolating per project means you can delete a project's venv folder and nothing else on your computer is affected.

Gap‑filled

The video describes installing a separate tool called virtualenvwrapper to create environments. That tool still exists, but it's an older, Windows-command-prompt-era convenience wrapper. Since Python 3.3, Python ships a built-in venv module — python -m venv venv — which does the same job with no extra install. That's the command shown above, and it's what you'll see in almost all current tutorials and the official Django docs.

Industry best practice

Never commit your venv folder to Git — it's large and machine-specific. Instead, commit a requirements.txt (generated with pip freeze > requirements.txt) and add venv/ to your .gitignore. Anyone cloning your project just runs pip install -r requirements.txt inside their own fresh venv.

Session 3–4Getting started

03 · Creating a project and an app

A Django project is the whole website; an app is one self-contained feature inside it. You create the project once, then create as many apps inside it as your site needs.

What it is

This distinction trips up a lot of beginners because the video (like most spoken explanations) uses "project" and "application" almost interchangeably in places. Here's the clean version:

  • Project — the top-level container: overall settings, the main URL map, and the folder that ties everything together. You typically have exactly one per website.
  • App — a smaller, focused module inside the project that handles one piece of functionality (e.g. a blog app, a payments app, an accounts app). A project can contain many apps, and well-designed apps can even be reused across different projects.
# 1. Create the project (run this once)
django-admin startproject myproject

# 2. Move into the project folder
cd myproject

# 3. Create an app inside it (repeat for each app you need)
python manage.py startapp myapp

# 4. Start the development server
python manage.py runserver
After runserver, open http://127.0.0.1:8000/ in a browser (127.0.0.1 and localhost both mean "this computer"). Seeing Django's "install worked" page confirms everything so far is correct.

Why two different commands?

Notice startproject uses django-admin (a general command-line tool that exists outside any project), while startapp uses manage.py (a file that gets generated inside your project and knows about that specific project's settings). That's why you must cd into the project folder before creating an app — manage.py only exists there.

Researched — code editors

The video spends time recommending PyCharm Professional (a paid, 30-day-trial editor) because it auto-generates project files through a UI. That's a convenience, not a requirement — Django itself doesn't care what editor you use. VS Code is free, has excellent Python/Django extensions, and is what the majority of Django developers use day to day. The command-line steps above work identically no matter which editor you open the resulting folder in.

Industry best practice

Name apps after what they do, not generically (blog, orders, accounts — not app1, myapp). It matters because the app name becomes a Python package name used throughout your code and database table names.

04 · The MVT architecture

Django organizes every feature into three cooperating pieces: a Model (data), a View (logic), and a Template (what the user sees) — MVT for short.

What it is

Think of a login page. There's the box the user types into (what they see), the check of whether their password is correct (what the computer does), and the actual stored record of the correct password (where the data lives). Django gives each of those a name and a dedicated place to live:

  • Model — represents your data. Each model is a Python class that Django turns into a database table. This lives in models.py.
  • View — the logic. A Python function (or class) that receives a request, does something (maybe checks the database via a model), and sends back a response. This lives in views.py.
  • Template — the presentation layer, i.e. the HTML the user actually sees in their browser.
Browsersends a request
→
urls.pymatches the address
→
Viewruns the logic
→
Modelreads/writes data
→
Templaterenders HTML

Browsershows the page

Why it matters

Separating these three concerns means you can change how a page looks (template) without touching how it works (view), and change how data is stored (model) without rewriting the page. This separation is what makes a growing Django project stay manageable instead of turning into one giant tangled file.

Researched — MVT vs. MVC

You may have heard of the more common MVC (Model-View-Controller) pattern from other languages. Django's MVT is conceptually the same idea with different naming: Django's "View" is really the controller (the logic that decides what happens), and Django's "Template" is really the view (what's displayed) in classic MVC terms. Django's own FAQ confirms this — the "controller" role is handled by Django's framework itself (the URL dispatcher), which is why there's no separate "C" in MVT.

05 · Project file structure

Running startproject and startapp generates a set of files automatically. Each one has a specific, fixed job — here's what each does and when you'll actually touch it.

Project-level files

These live in the inner folder named after your project (e.g. myproject/myproject/) and control the whole site.

FileWhat it does
manage.pyThe command-line utility for this project — every command (runserver, startapp, makemigrations, etc.) runs through it.
settings.pyGlobal configuration: installed apps, database connection, middleware, templates folder location — one file that affects the entire project.
urls.pyThe site's URL map — decides which view runs for which web address.
wsgi.pyEntry point used by traditional web servers (like Apache) to run your Django app in production. You won't edit this during development.
asgi.pyThe newer, async-capable counterpart to wsgi.py, for servers that support asynchronous features (e.g. WebSockets). Also not touched in normal development.
__init__.pyAn empty file that just tells Python "treat this folder as a package." You never put code in it.

App-level files

These are generated fresh inside every app folder you create with startapp.

FileWhat it does
models.pyDefine this app's data — Python classes that become database tables.
views.pyThis app's logic — functions/classes that handle requests and return responses.
admin.pyRegister models here to manage them through Django's built-in admin panel.
apps.pySmall configuration class for this app; default settings are almost always fine as-is.
migrations/Auto-generated history of every change made to your models, used to keep the database in sync.
tests.pyWhere you write automated tests for this app's code.
Gap‑filled

The video walks through most of these files but never mentions tests.py, which Django generates automatically in every new app. It's where you write code that automatically checks your app still works correctly as you make changes — an important habit once your apps grow beyond a few views.

Industry best practice

Register every new app in INSTALLED_APPS inside settings.py the moment you create it — an app that isn't registered there is invisible to Django (its models won't migrate, its templates won't be found). This is the single most common "why isn't this working" mistake for beginners.

06 · Your first view

A view is just a Python function that takes a web request and returns a web response — the simplest one just sends back a line of text.

Writing the view

# myapp/views.py
from django.http import HttpResponse

def v1(request):
    return HttpResponse("This is my first Django web application.")
  • request — every view function must accept this parameter; Django passes in details of the incoming browser request. You don't have to use it, but it must be there.
  • HttpResponse — a Django class that wraps whatever text/HTML you give it into a proper web response the browser understands. You import it from django.http.

Connecting it to a URL

A view does nothing on its own — Django needs to know which web address should trigger it. That mapping happens in urls.py:

# myproject/urls.py
from django.contrib import admin
from django.urls import path
from myapp import views

urlpatterns = [
    path('admin/', admin.site.urls),
    path('v1/', views.v1),
]
Now visiting http://127.0.0.1:8000/v1/ runs v1() and shows its response. Visiting /v1 without the trailing content will 404 (page not found) since no pattern matches it exactly.

Request/response flow

1. Clientrequests /v1/
→
2. urls.pyfinds matching path
→
3. views.v1()executes
→
4. Responsesent back to browser
Industry best practice

Returning raw HttpResponse text like this is only for learning the request/response cycle. Real views almost always use render() to return a full HTML template instead — you'll see this properly once templates are introduced. Avoid writing HTML directly inside a Python string in real projects; keep HTML in template files.

07 · URL routing: project-level vs. app-level

Once a project has more than one app, cramming every URL into the project's single urls.py becomes messy. The fix: give each app its own urls.py, and have the project file simply hand off to it.

The problem with one big urls.py

If myapp and myapp_one both define a view called v1, and both are imported into the same project-level urls.py, Python's import system only keeps the most recent import of that name — so one app's view silently shadows the other's. This is exactly the confusing bug the video runs into.

The fix: per-app urls.py + include()

# myapp/urls.py  (new file you create yourself)
from django.urls import path
from myapp import views

urlpatterns = [
    path('v1/', views.v1),
    path('v2/', views.v2),
]
# myproject/urls.py  (project-level — just delegates)
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('myapp/', include('myapp.urls')),
    path('myapp-one/', include('myapp_one.urls')),
]
Now /myapp/v1/ and /myapp-one/v1/ are two completely distinct, unambiguous addresses — even though both apps have a view named v1.
Request/myapp/v1/
→
Project urls.pysees "myapp/" prefix
→
include()hands off remaining path
→
myapp/urls.pymatches "v1/"
→
views.v1runs
Industry best practice

Every real Django project uses app-level urls.py + include() — it's considered a firm convention, not optional. It keeps apps self-contained (an app's URLs live with the app) and means the project-level file stays short and readable no matter how many apps you add.

Gap‑filled

The video also mentions optionally giving each URL pattern a name, e.g. path('v1/', views.v1, name='view-one'). This isn't just cosmetic — a named URL lets you reference it elsewhere in your code (templates, redirects) as 'view-one' instead of hardcoding the string '/myapp/v1/'. If you ever change the actual URL path later, every reference using the name still works automatically. This is standard practice in real projects.

08 · Admin panel & superuser

Django gives you a ready-made admin website for managing your data — you just need to create a superuser account to log into it, and register your models so they show up.

Creating a superuser

A superuser is an administrator account with full permissions — it can log into the admin panel, manage other users, and edit any registered data.

python manage.py createsuperuser
# then follow the prompts: username, email (optional), password

With the server running, visit http://127.0.0.1:8000/admin/ and log in with those credentials.

Making a model visible in the admin

Just because a model exists in models.py doesn't mean it appears in the admin panel — you have to register it explicitly:

# myapp/admin.py
from django.contrib import admin
from .models import Student

admin.site.register(Student)

Why this step

The admin panel is one of Django's biggest time-savers — instead of writing your own "add/edit/delete records" pages, Django auto-generates a working management UI for any model you register. It's meant for site administrators/staff, not end users of the public website.

Industry best practice

Never expose the default /admin/ URL as-is on a real production site without extra hardening (strong passwords, limiting who has superuser accounts, and often changing the admin URL path) — it's a well-known target since every Django site has one by default.

09 · Models & migrations

A model is a Python class that describes a database table. Migrations are the mechanism that turns that class into actual tables and columns in your database.

What it is

Instead of writing raw SQL to create tables, you describe your data as a Python class. Django reads that class and generates the equivalent SQL for you.

# myapp/models.py
from django.db import models

class Student(models.Model):
    s_id = models.IntegerField()
    s_name = models.CharField(max_length=100)
    s_address = models.CharField(max_length=200)
    s_location = models.CharField(max_length=100)
  • The class Student becomes a database table named (by default) myapp_student.
  • Each class attribute becomes a column — s_name becomes a column that only accepts text up to 100 characters (CharField(max_length=100)), s_id only accepts whole numbers (IntegerField), and so on.

Turning the class into a real table

# Step 1 — generate a migration file describing what changed
python manage.py makemigrations

# Step 2 — actually apply those changes to the database
python manage.py migrate

makemigrations looks at your models and writes a migration file (inside the app's migrations/ folder) containing the SQL needed to match the database to your models. migrate then runs that SQL against the actual database, creating or updating the real tables.

Gap‑filled

The video describes the concept of migrations in detail but never shows an actual models.py class with real field types. The example above (CharField, IntegerField) fills that gap — these field types are how Django knows what kind of column to create and what validation to apply.

Industry best practice

Run makemigrations every time you change a model, and commit the generated migration files to version control — they're part of your project's history, not throwaway files. Never edit an already-applied migration file by hand; if a model needs to change further, make the change and run makemigrations again to generate a new one.

Researched — the default database

Every new Django project is pre-configured (in settings.py, under DATABASES) to use SQLite — a lightweight, file-based database (your project's db.sqlite3 file) that needs no separate server, which is why it works instantly for learning. Production sites usually switch to PostgreSQL or MySQL by changing this same settings block — the rest of your code (models, views) doesn't need to change.

Session 6–7Front-end foundations

10 · HTML basics

HTML (HyperText Markup Language) is the mandatory foundation of every web page — it describes content and structure, not styling or behavior.

The basic structure

Every HTML page has two main parts: a <head> (metadata — page title, links to CSS/JS files, not visible on the page itself) and a <body> (the actual visible content).

<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>Home Page</title>
</head>
<body>
    <h1>This is heading one</h1>
    <p>This is a paragraph.</p>
</body>
</html>
  • <!DOCTYPE html> — tells the browser this is a modern HTML5 document.
  • <meta charset="UTF-8"> — sets the character encoding so text (including special characters) displays correctly.
  • <title> — the text shown on the browser tab, not on the page itself.
  • <h1> to <h6> — heading levels, from largest/most important (h1) to smallest (h6).
  • <p> — a paragraph of text.

Creating & previewing an HTML file inside a Django project

Outside of Django, writing an HTML page usually means opening a plain text editor, typing the tags by hand, saving the file with a .html extension, then double-clicking it to open it in a browser. Inside a Django project this is smoother: in the templates folder, right-click → New → HTML File, give it a name (e.g. home.html), and the editor auto-generates the boilerplate skeleton for you (<!DOCTYPE html>, <html>, <head> with a charset meta tag, empty <body>) — you don't type that scaffold from scratch every time.

To preview it, most Django-aware editors show browser icons (Chrome, Firefox, Edge) right next to the file — clicking one opens a live preview of that HTML file directly, with no separate "run" step needed.

Gap‑filled

This in-editor preview is just a convenience for *looking at* the static markup while you're learning HTML in isolation. Once this HTML becomes a real Django template, you won't open the .html file directly in a browser anymore — you'll visit a URL that your Django dev server serves (e.g. http://127.0.0.1:8000/), which runs it through a view first. Opening the raw file skips Django entirely and any {{ }} template tags would show up as literal text instead of rendering.

Comments

A comment is text the browser parses but never displays — used to leave notes for yourself or other developers reading the code later.

<!-- This is a comment, it will not show up on the page -->
<h1>This is heading one</h1>

Comments start with <!-- and end with --> — anything in between (even multiple lines) is ignored by the browser.

Lists

HTML has two list types: <ol> (ordered — numbered) and <ul> (unordered — bulleted). Each item inside either one uses <li> (list item).

<ol>
    <li>C</li>
    <li>C++</li>
    <li>Python</li>
</ol>

By default an <ol> numbers items 1, 2, 3…. The type attribute changes the numbering style:

type valueRenders as
11, 2, 3, 4 (default — you can omit type entirely)
AA, B, C, D
aa, b, c, d
II, II, III, IV (uppercase Roman numerals)
ii, ii, iii, iv (lowercase Roman numerals)
Example

An ordered list of the podium finishers, lettered instead of numbered:

<ol type="A">
    <li>Asha</li>
    <li>Ravi</li>
    <li>Meera</li>
</ol>
<!-- Renders as: A. Asha   B. Ravi   C. Meera -->

<ul> has no type-based numbering — it always shows bullets, and ordering the items has no visual effect (they're conceptually "not in a particular order").

Text formatting: use the HTML5 tags, not the legacy ones

WantLegacy tag (avoid)HTML5 tag (use this)
Bold<b><strong>
Italic<i><em>

<strong> and <em> render the same visually (bold/italic) but also carry meaning — "this text matters" / "this text is emphasized" — which screen readers and search engines pick up on. <b> and <i> are purely visual with no semantic meaning.

More text-formatting elements

Beyond bold/italic, HTML has several other inline elements for special-meaning text:

<p>This is <sub>subscripted</sub> and this is <sup>superscripted</sup>.</p>
<p>Please note: <mark>the office is closed on Monday</mark>.</p>
Gap‑filled — <mark> vs. <marquee>

These sound alike (and the video's audio makes them easy to mix up) but they're two completely different tags. <mark>, above, just highlights text in place. <marquee>, below, makes text scroll across the screen — a different, much older tag with a completely different purpose.

Researched — <big> and <strike>

Per MDN, <big> was dropped from the HTML5 standard entirely (it still renders in most browsers for backward compatibility, but you should never use it in new code — use CSS font-size instead). <strike> is officially obsolete too, superseded by <del> (semantically "removed") or <s> (just "no longer accurate/relevant", no removal implied).

The <marquee> tag — and why to avoid it

<marquee> makes its text scroll across the page — historically used for banner-style alerts, e.g. a bank's website scrolling an important notice so it catches the customer's eye.

<marquee>Welcome to Durga Sir</marquee>
<marquee bgcolor="red" direction="right">Welcome to Durga Sir</marquee>
  • bgcolor — background color behind the scrolling text.
  • direction — which way it scrolls (left by default, or right, up, down).
Researched — don't use <marquee> in real projects

<marquee> was never part of any official HTML standard — MDN marks it deprecated and explicitly warns against using it, since browsers aren't required to keep supporting it. It's shown here because it still appears in a lot of tutorials and older sites, and it's useful to recognize. For a scrolling-banner effect in a real project, use a CSS animation instead — it's supported the same way everywhere and doesn't rely on a non-standard element.

Images

<img src="flag.jpg" alt="Country flag">
  • <img> is self-closing (no separate closing tag needed) — unlike <p> or <b>, which need </p> / </b>.
  • src — the image file's location.
  • alt — fallback text shown if the image fails to load. Not optional in real projects — see below.
Gap‑filled

The video frames alt text purely as a "broken image" fallback. Its bigger purpose: screen readers read alt text aloud for visually impaired users, so every meaningful image needs a real, descriptive alt — this is a baseline accessibility requirement, not a nice-to-have.

Tables

<table border="1">
    <tr>
        <th>Employee ID</th>
        <th>Name</th>
    </tr>
    <tr>
        <td>101</td>
        <td>Asha</td>
    </tr>
</table>

<table> is the container, <tr> is one table row, <th> is a header cell (bold, centered by default), and <td> is a normal data cell.

To center content inside a cell, add align="center" to the <th> or <td>:

<td align="center">101</td>
Gap‑filled

align is a presentational HTML attribute — it's old-style, like <b>/<i> were for bold/italic. Modern practice is to keep HTML for structure only and do alignment with CSS instead: text-align: center; on the cell (covered in the CSS topic below). align still works in every browser, so you'll see it in a lot of older tutorials and code, but don't reach for it in a new project.

Tables with images

A table cell can hold any HTML, including an <img> — useful for something like a "country + flag" list.

<table border="1">
    <tr>
        <th>#</th>
        <th>Country</th>
        <th>Flag</th>
    </tr>
    <tr>
        <td align="center">1</td>
        <td align="center">India</td>
        <td align="center"><img src="india.jpg" alt="Flag of India"></td>
    </tr>
    <tr>
        <td align="center">2</td>
        <td align="center">USA</td>
        <td align="center"><img src="usa.png" alt="Flag of USA"></td>
    </tr>
</table>

Each <img> just goes inside its own <td>, exactly like it would anywhere else on the page — a table cell is just another container.

Gap‑filled — HTML is a markup language, not a programming language

Every row above was typed out by hand. In a real Django app, table rows like these usually need to come from a database — e.g. one row per employee — and the number of rows isn't known ahead of time. You can't write a loop in plain HTML to generate rows dynamically, because HTML has no logic: no variables, no if/for, no classes or objects (the "OOP" concepts Django/Python have). HTML only describes structure. Repeating rows for database records is done with the Django Template Language (DTL) — e.g. {% for employee in employees %} — which is covered once templates are connected to views and models.

Hyperlinks

<a href="https://www.djangoproject.com">Go to Django's site</a>

<a> is the anchor tag; href (hyperlink reference) is the destination — either another page on your own site (e.g. href="index.html") or a full external URL.

Industry best practice

Use headings (h1–h6) in order to reflect document structure, not just for font size — skipping from h1 straight to h4 for a smaller look is a common beginner mistake that hurts accessibility and SEO. Use CSS to control size instead.

Session 6Front-end foundations

11 · HTML forms

Forms are how a web page collects input from a user — logins, registrations, search boxes — and every form is built from a <form> wrapping one or more <input> elements.

A basic form

<form action="index.html" method="post">
    <label for="uname">Enter name</label>
    <input type="text" id="uname" name="username" placeholder="Enter name" required>
    <br>
    <input type="password" name="pwd">
    <br>
    <input type="submit" value="Submit">
</form>

The pieces

  • action — where the form's data gets sent when submitted.
  • method — how it's sent (commonly post for data that changes something, get for simple lookups).
  • type on <input> — controls what kind of field it is: text, password (hides typed characters), email, checkbox, radio, submit, and more.
  • name — the identifier used to read this field's value once the form is submitted (in JavaScript or on the server). Without a name, a field's value is never sent — even if the user fills it in.
  • value — its meaning depends on the input type. For text/email/password, it's a pre-filled default the user can overwrite — usually left blank so the user provides it themselves. For checkbox/radio/submit, it's not shown to the user at all — it's the identifier sent to the server for that specific option when checked/clicked.
  • placeholder — greyed-out hint text shown inside an empty field; disappears once the user types.
  • required — the browser won't let the form submit until this field has a value.
  • <label for="uname"> — links descriptive text to the input whose id="uname" matches. This isn't just cosmetic: clicking the label text focuses the input, and screen readers announce the label when the field is focused.
Example — grouping checkboxes and radio buttons

Giving multiple inputs the same name groups them. For checkboxes, any number can be checked, and each checked one's value is sent. For radio buttons, the shared name makes them mutually exclusive — only one can be selected at a time.

<p>Pick your courses:</p>
<input type="checkbox" id="py" name="course" value="python">
<label for="py">Python</label>
<input type="checkbox" id="cs" name="course" value="csharp">
<label for="cs">C#</label>

<p>Preferred contact method:</p>
<input type="radio" id="em" name="contact" value="email" checked>
<label for="em">Email</label>
<input type="radio" id="ph" name="contact" value="phone">
<label for="ph">Phone</label>

If both checkboxes are checked, the server receives course=python and course=csharp. For the radio group, only whichever one is selected is sent — here contact=email is selected by default via the checked attribute.

Industry best practice

Always pair every input with a <label> (via matching for/id), not just a nearby paragraph of text — a paragraph has no programmatic connection to the field, so assistive technology can't associate the two.

Researched — CSRF protection

The forms here are plain HTML with no Django involved yet, so they work as shown. The moment a form like this actions to a real Django view with method="post", Django's CSRF protection will reject the submission unless the form includes {% csrf_token %} inside it. This is a security feature (prevents other sites from silently submitting forms to your app on a logged-in user's behalf) — expect a 403 Forbidden error the first time you wire a POST form into Django and forget it.

12 · CSS basics & the 3 ways to style

CSS (Cascading Style Sheets) controls how HTML looks — colors, fonts, spacing, layout. There are three ways to attach CSS to a page, and only one of them is recommended for real projects.

Basic syntax

selector {
    property: value;
    property: value;
}

/* example */
p {
    color: red;
    font-size: 25px;
}

A selector picks which HTML element(s) to style (here, every <p>); everything inside the curly braces is a list of property: value; pairs.

Example — common properties together
h1 {
    color: crimson;
    font-family: Georgia;
    font-size: 40px;
}

font-family sets the typeface (browsers fall back to a default font if the named one isn't installed — real projects usually list several as fallbacks, e.g. font-family: Georgia, serif;). color sets text color, font-size sets text size (in pixels here).

The three ways to apply CSS

TypeHowScope
Inline<p style="color:red;">Just that one element
Internal<style>...</style> in <head>Just that one HTML page
ExternalSeparate .css file, linked inEvery page that links to it
<!-- linking an external stylesheet -->
<head>
    <link rel="stylesheet" href="style.css">
</head>
Gap‑filled

Inside a Django project, an external stylesheet is created the same way as an HTML template: in the templates folder, right-click → New → Style Sheet, name it with a .css extension (e.g. sample.css). This file should contain only CSS rules — no <html>, <head>, or <body> tags. It can then be linked from any number of HTML pages via <link> — changing one property in this one file updates every page that links to it.

Researched — the rel attribute is not optional

The video calls rel="stylesheet" optional. That's incorrect for linking CSS: per the HTML spec, rel is what tells the browser how to treat the linked file — without rel="stylesheet", the browser has no reason to apply the file's contents as CSS at all, and the styles silently won't load. Always include it.

Which style wins? (priority)

If the same element gets conflicting styles from more than one place, CSS follows a clear order:

  1. Inline style always wins over internal or external, no matter what.
  2. Between internal and external: whichever one appears later (further down) in the HTML file wins. So if your <link> to the external file appears before an internal <style> block, the internal block wins (it's "later"). If the internal block is written first and the external link comes after it, the external file wins.
Researched — the real rule (specificity)

The "whichever comes later wins" rule the video gives is true only when the competing rules have equal specificity (roughly, how precisely a selector targets an element). CSS actually resolves conflicts using a specificity score first, and only falls back to "later wins" when scores are tied. See the next topic for the full, correct version of this — including why ID and class selectors change the outcome.

Industry best practice

External stylesheets are what real projects use almost exclusively — one CSS file styling an entire site means a single edit updates every page. Inline styles are reserved for rare one-off overrides (or dynamic styles set by JavaScript); internal <style> blocks are mostly avoided outside of quick demos, exactly like this video is using them for.

13 · CSS selectors & priority

Selectors are how you tell CSS which elements to target. There are a few main kinds, and when more than one rule could apply to the same element, specificity decides which one wins.

The main selector types

SelectorSyntaxTargets
Elementp { }Every <p> on the page
Class.center { }Any element with class="center"
ID#main { }The one element with id="main" (IDs must be unique per page)
Universal* { }Every element on the page
Groupedh1, h2, p { }All listed selectors, sharing one rule block
.center {
    text-align: center;
}

p.center {
    /* only paragraphs with class="center" — narrower than .center alone */
    color: purple;
}

Specificity: the real priority rules

The video's explanation ("ID beats class beats element") is correct as far as it goes — here's the precise version, which is what you'll find in any CSS reference:

Researched — CSS specificity, precisely

Every selector gets a specificity score. From highest to lowest priority:

  1. Inline styles — always highest (see previous topic).
  2. ID selectors (#main) — very high.
  3. Class, attribute, and pseudo-class selectors (.center, :hover) — medium.
  4. Element and pseudo-element selectors (p, ::first-letter) — lowest.

Only when two rules have the exact same specificity score does "whichever is defined later wins" come into play. Full reference: MDN — CSS Specificity.

Pseudo-elements & link states

Pseudo-elements style a specific part of an element rather than the whole thing:

p::first-letter { color: blue; }
p::first-line   { color: red; }

Links have four special states, styled with pseudo-classes — and their order in your CSS file matters:

a:link    { color: red; }    /* unvisited */
a:visited { color: green; }  /* already visited */
a:hover   { color: yellow; } /* mouse over it */
a:active  { color: blue; }   /* being clicked, right now */
Remember the order with the mnemonic LoVe HAte — Link, Visited, Hover, Active. Writing them in a different order can make :hover or :active silently fail to apply.
Industry best practice

Prefer class selectors over ID selectors for styling in real projects. IDs have such high specificity that they become hard to override later, and since an ID must be unique per page, class-based styles are far more reusable across multiple elements.

14 · Backgrounds, div/span & overflow

Three more CSS building blocks: styling background images, grouping content with div/span, and controlling what happens when content is too big for its box.

Background images

body {
    background-image: url('flag.jpg');
    background-repeat: no-repeat;
    background-position: right top;
    background-attachment: fixed;
    background-size: cover;
}
  • background-repeat: no-repeat — stops the image tiling across the whole page.
  • background-position — where the image sits (e.g. right top, center).
  • background-attachment: fixed — the image stays in place even as the page scrolls.
  • background-size: cover — stretches the image to fill the entire element, cropping if needed.
Example — shorthand

All five properties above can be combined into a single background declaration, in the order image → repeat → position → attachment:

body {
    background: url('flag.jpg') no-repeat right top fixed;
}
Gap‑filled — body vs. html for a true full-page background

Setting the background on body only covers the area the page's content actually occupies — on a short page, the color/image stops where the content ends, leaving a gap below. Setting it on html instead covers the entire browser viewport, since <html> is the outermost element and always spans the full window height. For a background that's guaranteed to fill the whole visible page, target html (or set min-height: 100% on body as an alternative).

<div> vs. <span>

Both are generic containers with no visual style of their own — they exist purely to group content so you can apply CSS or JavaScript to that group.

  • <div> — a block-level element (block-level means it takes up the full width available and starts on a new line). Used to group larger sections — a header, a sidebar, a card.
  • <span> — an inline element (inline means it only takes up as much width as its content, and stays in the flow of surrounding text). Used to style a small piece of text inside a sentence without breaking the line.
<style>
    div { color: red; background-color: lightblue; }
    span { color: green; font-size: 20px; font-family: Georgia; }
</style>

<div>
    <h1>This is heading one</h1>
    <h2>This is heading two</h2>
</div>

<p><b>Welcome to</b> <span>Durga's class</span></p>

Everything inside the <div> (both headings) gets red text on a light-blue background, and starts on its own new block. Only the word wrapped in <span> gets its own styling — the rest of that paragraph's text flows normally around it, on the same line.

Overflow

When content is bigger than the box you've given it (via fixed width/height), overflow decides what happens to the extra content:

ValueEffect
visibleExtra content spills outside the box (the default)
hiddenExtra content is clipped and simply not shown
scrollScrollbars appear so the user can scroll to see the rest
autoScrollbars appear only if needed
p {
    height: 200px;
    width: 400px;
    border: 3px solid red;
    overflow: scroll;
}

Here the paragraph's box is fixed at 400×200 pixels. If the text inside is longer than that box, overflow: scroll keeps it readable by adding scrollbars, rather than letting it spill past the red border (visible) or silently cutting it off (hidden).

Researched — centering content isn't just "align"

The video reaches for a generic "align" property to center content inside a box and finds it doesn't work directly — that's expected. text-align: center centers inline content (text, images) horizontally within its container. align-content/align-items only have an effect inside a display: flex or display: grid container — applying them to an ordinary block element (like a plain <div> or <p>) does nothing, which is exactly the confusion in the video. To center a block element itself (not just its content) horizontally, the standard approach is margin: 0 auto; with a fixed width.

Industry best practice

Prefer overflow: auto over scroll in real layouts — auto only shows scrollbars when content actually overflows, while scroll shows them permanently even when there's nothing to scroll, which looks broken to users.

15 · JavaScript basics

JavaScript adds behavior and interactivity to a web page — things HTML and CSS alone can't do, like reacting to a click or validating a form before it's submitted.

Gap‑filled — what JavaScript actually is

JavaScript is a lightweight, interpreted language (run line-by-line by the browser, like Python — not compiled ahead of time) and dynamic (variable types are figured out at runtime, not declared upfront). It was originally named LiveScript; the rename to "JavaScript" was a marketing decision to ride on Java's popularity at the time — the two languages are otherwise unrelated, despite the similar name. In a Django project, JavaScript's main job is client-side validation: catching obviously-bad form input in the browser, before it's ever sent to the server (HTML provides structure, CSS provides styling, JavaScript provides behavior).

Where JavaScript code lives

Like CSS, JavaScript can be internal (inside a <script> tag on the page) or external (a separate .js file, linked in).

<!-- internal -->
<script>
    console.log("Hello, Durga!");
</script>

<!-- external -->
<script src="script.js"></script>
Convention: place <script> tags in the <head>, same as CSS <link> tags — though for scripts that manipulate content on the page, placing them at the end of <body> is also common so the HTML loads first.

src on <script> works exactly like href did for a CSS <link> — it points to the external file. Unlike the CSS rel attribute, though, the type="text/javascript" attribute really is optional here: modern HTML defaults <script> to JavaScript, so omitting type works correctly in every current browser.

Gap‑filled

Inside a Django project, create an external JavaScript file the same way as an HTML template or a CSS file: in the templates folder, right-click → New → JavaScript File, name it (e.g. sample.js). Link it into a page with <script src="sample.js"></script>.

Comments

// single-line comment

/* multi-line
   comment */

Same purpose as HTML comments: notes for whoever reads the code later. The JavaScript interpreter skips comments entirely — they have no effect on how the script runs.

Displaying output — and which method to actually use

MethodWhat it does
console.log()Prints to the browser's developer console (not visible on the page) — the standard tool for debugging
alert()Shows a popup dialog box the user must dismiss
document.write()Writes directly into the page's HTML
Gap‑filled

The video shows all three as roughly interchangeable options. In real code, document.write() is avoided — if it runs after the page has finished loading, it wipes out the entire existing page content, which causes hard-to-debug bugs. console.log() is the standard for debugging; alert() is reserved for messages that genuinely need to interrupt the user.

Variables

let name = "Durga";
console.log("Your name is " + name);

// getting input at runtime
let userName = prompt("Enter name");
let a = Number(prompt("Enter first number"));
let b = Number(prompt("Enter second number"));
console.log("Sum is " + (a + b));

prompt() is JavaScript's equivalent of Python's input() — but everything it returns is always text. That's why Number(...) wraps it above: without converting, "10" + "20" would produce the text "1020" (stuck together) instead of adding to 30.

Example — even/odd checker

Combining a runtime-entered number with an if/else and the remainder operator %:

let n = Number(prompt("Enter any number"));

if (n % 2 == 0) {
    console.log(n + " is even");
} else {
    console.log(n + " is odd");
}

% gives the remainder of a division — n % 2 is 0 for any even number and 1 for any odd number, which is exactly what the condition checks. Input 7 → output "7 is odd"; input 10 → output "10 is even".

Gap‑filled — var vs. let vs. const

The video only ever declares variables with var. Modern JavaScript (since 2015) prefers let (for values that change) and const (for values that never get reassigned). var has looser, more error-prone scoping rules that let/const were introduced specifically to fix. Current style guides, including MDN's, recommend avoiding var in new code — that's why every example on this page uses let instead.

16 · DOM manipulation & form validation

JavaScript can reach into a loaded page and change it (DOM manipulation), and it's most commonly used in forms to catch bad input before it's ever sent to the server.

Functions & the onclick event

A function is a named, reusable block of code — write it once, then run it whenever you need to by calling its name. In the browser, functions are commonly triggered by events: something the user does, like clicking a button.

<script>
function sayHello() {
    alert("Hello!");
}
</script>

<input type="button" value="Click here" onclick="sayHello()">

function sayHello() { ... } defines the function but doesn't run it — nothing happens until it's called. onclick="sayHello()" on the button is that call: it wires up the click event so the function runs each time the button is clicked. Unlike Python, JavaScript doesn't use indentation to mark a function's body — the curly braces { } do that job.

What "DOM" means

The DOM (Document Object Model) is the browser's live, in-memory representation of your HTML page — a structure JavaScript can read and change after the page has loaded, and the browser instantly reflects those changes on screen.

<p id="msg">This is my first paragraph.</p>

<script>
    document.getElementById("msg").innerHTML = "Welcome, Durga!";
</script>

document.getElementById("msg") finds the one element whose id is "msg"; .innerHTML is the property holding everything inside that element, which you can read or overwrite.

Form validation

<form name="myform" onsubmit="return validateForm()">
    Name: <input type="text" name="username"><br>
    Password: <input type="password" name="pwd"><br>
    <input type="submit" value="Login">
</form>

<script>
function validateForm() {
    let name = document.myform.username.value;
    let pwd  = document.myform.pwd.value;

    if (name == "") {
        alert("Name cannot be blank");
        return false;
    }
    if (pwd.length < 6) {
        alert("Password must be at least 6 characters long");
        return false;
    }
    return true; // only now does the form actually submit
}
</script>

The key mechanic: onsubmit="return validateForm()". If validateForm() returns false, the browser cancels the submission entirely — the form never leaves the page. If it returns true, submission proceeds normally — to wherever the form's action attribute points (e.g. <form action="https://example.com" ...> would send the browser there once validation passes).

Matching two password fields

function matchPwd() {
    let p1 = document.myform.password1.value;
    let p2 = document.myform.password2.value;
    if (p1 != p2) {
        alert("Passwords must be the same");
        return false;
    }
    return true;
}
Gap‑filled — this is an important limitation, not a footnote

Client-side JavaScript validation only improves the user's experience (instant feedback, no round-trip to the server for an obvious mistake). It is not a security boundary — anyone can open their browser's developer tools, disable JavaScript, or send a request directly (bypassing the form entirely) and submit whatever data they want. The video actually mentions this near the end: Django performs its own server-side validation regardless, and that server-side check is the one that actually protects your data. Treat JavaScript validation as a convenience layered on top of — never a replacement for — server-side validation (in Django, this means using Django Forms/ModelForms, covered in later sessions).

17 · jQuery basics

jQuery is a JavaScript library that lets you write much shorter code for common tasks like selecting elements and handling clicks — its own slogan is "write less, do more."

What it is

A library is a pre-written bundle of code you can call into, instead of writing everything from scratch. jQuery specifically wraps a lot of common, repetitive JavaScript (selecting elements, showing/hiding things, handling events, and AJAX — Asynchronous JavaScript and XML, i.e. fetching data from a server without reloading the page) into short one-line methods.

jQuery was created by John Resig in 2006. Its main selling points at the time: it's small and fast, and it smooths over inconsistencies between browsers — the same jQuery code reliably works the same way across Chrome, Firefox, Edge, etc., which plain JavaScript of that era often didn't.

Adding jQuery to a page: two ways

MethodHowNeeds internet each load?
LocalDownload the .js file once, keep it in your project, link to it like any other scriptNo
CDNLink directly to jQuery's file hosted on their serversYes
<!-- Local -->
<script src="jquery-3.6.0.min.js"></script>

<!-- CDN -->
<script src="https://code.jquery.com/jquery-3.6.0.min.js"></script>

jquery.com offers each release as either compressed/production (the .min.js file — all whitespace and comments stripped, so it's one dense unreadable line, but small and fast to download) or uncompressed/development (the same code, readably formatted, larger). For a real site, use the minified build; the unminified one is only useful if you ever need to read jQuery's own source.

Gap‑filled

For the local option, the downloaded jquery-3.6.0.min.js file goes wherever your other static files live — in this project, the templates folder, alongside your CSS/JS files, added via the same right-click → New workflow (or copy-pasted in directly, since it's downloaded rather than authored). Then link it with a normal <script src="jquery-3.6.0.min.js"></script>, exactly like the sample.js file from the previous topic.

Researched — the integrity attribute on a CDN script

jQuery's official CDN snippet includes an integrity attribute (a hash of the file) and crossorigin="anonymous", e.g. <script src="..." integrity="sha256-..." crossorigin="anonymous"></script>. This is Subresource Integrity (SRI): the browser hashes the downloaded file and compares it to the expected hash, refusing to run the script if they don't match. It protects you if the CDN is ever compromised and starts serving tampered code. Always copy the full snippet jQuery's site gives you, integrity attribute included — don't strip it down to just src.

Basic syntax

$(selector).action();

// example: hide every paragraph when a button is clicked
$(document).ready(function() {
    $("button").click(function() {
        $("p").hide();
    });
});
  • $ — shorthand for accessing jQuery.
  • selector — which HTML element(s) to target (same idea as CSS selectors — element, .class, #id).
  • .action() — what to do to them (.hide(), .show(), .click(), etc.).
  • $(document).ready(...) — waits until the whole page has finished loading before running the code inside, so it never tries to act on an element that hasn't appeared yet.
Example — separate hide and show buttons

Using ID selectors to wire up two different buttons to two different actions on the same paragraph:

<script>
$(document).ready(function() {
    $("#hide").click(function() {
        $("p").hide();
    });
    $("#show").click(function() {
        $("p").show();
    });
});
</script>

<p>This is my first paragraph.</p>
<button id="hide">Click here to hide</button>
<button id="show">Click here to show</button>

#hide and #show match the buttons' id attributes, exactly like an ID selector in CSS. Each button's click handler only runs the action wired to its own id.

Common pitfall

It's easy to swap the code inside two handlers by accident — e.g. writing .hide() inside the #show button's click handler — and get no visible error, just a button that silently does the wrong thing (or nothing). If a jQuery action doesn't seem to fire, double-check that the selector in $("#id") actually matches the element you clicked, and that the action inside is the one you meant for that specific handler.

Researched — is jQuery still worth learning?

jQuery was essential a decade ago because plain JavaScript was verbose and inconsistent across browsers. Modern JavaScript has since added most of what jQuery offered directly into the language (e.g. document.querySelector(), fetch()), and modern browsers are far more consistent — so new projects increasingly skip jQuery entirely. It's still worth knowing because a huge number of existing/older sites (and some third-party front-end libraries) still depend on it, but for new Django projects specifically, plain JavaScript or a modern front-end approach is now more common than reaching for jQuery by default. Django itself has no dependency on jQuery at all.
