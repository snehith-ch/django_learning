Session 3Getting started

01 · Checking your tools & installing Django

Before you build anything, you check that Python, pip, and Django are actually installed — and if Django isn't there yet, you install it with one command.

What's actually going on

Django is not part of Python itself — it's an extra package you install on top of Python. So the very first thing every Django developer does is confirm three things are in place: Python, pip (Python's package installer — a tool that downloads and manages extra libraries like Django), and Django itself.

# Check which Python version you have
python --version

# Check which pip version you have
pip --version

# Check which Django version you have (only works if Django is installed)
django-admin --version

# Install Django
pip install django
If django-admin --version replies with something like "command not found," that just means Django isn't installed yet — run pip install django and try again.

Why this step

Checking versions first saves you from a very common beginner trap: following a tutorial written for a different Python or Django version and getting confused by errors that have nothing to do with your actual code. It also confirms pip is working, since you'll use pip constantly to install every other package your project needs later (like the REST framework, database drivers, etc.).

Industry best practice

Real projects pin exact versions instead of just "having Django installed" — e.g. a requirements.txt file listing Django==5.0.6. That way, everyone on the team (and the production server) runs the exact same version, instead of "it works on my machine."

Gap‑filled

The video's commands were transcribed a little garbled (e.g. "Django admin admin"). The real commands are exactly python --version, pip --version, and django-admin --version — two dashes before "version", no extra words.

02 · Virtual environments

A virtual environment is a private, isolated copy of Python just for one project, so its packages don't clash with any other project's packages.

What it is

Imagine every Python project on your computer shared one single toolbox. If Project A needs Django 4 and Project B needs Django 5, they'd fight over which version sits in the toolbox. A virtual environment (often shortened to "venv") gives each project its own private toolbox, so Project A and Project B can each have the Django version they need, at the same time, with zero conflict.

# Create a virtual environment named "venv" inside your project folder
python -m venv venv

# Activate it — Windows
venv\Scripts\activate

# Activate it — macOS / Linux
source venv/bin/activate

# Once activated, install packages as normal — they stay inside this venv
pip install django
You'll know it's active because your terminal prompt gets a (venv) prefix. To leave it, type deactivate.

Why this step

Without a virtual environment, every pip install you run installs the package globally on your machine — for every project. Over time this turns into a mess where projects silently break each other. Isolating per project means you can delete a project's venv folder and nothing else on your computer is affected.

Gap‑filled

The video describes installing a separate tool called virtualenvwrapper to create environments. That tool still exists, but it's an older, Windows-command-prompt-era convenience wrapper. Since Python 3.3, Python ships a built-in venv module — python -m venv venv — which does the same job with no extra install. That's the command shown above, and it's what you'll see in almost all current tutorials and the official Django docs.

Industry best practice

Never commit your venv folder to Git — it's large and machine-specific. Instead, commit a requirements.txt (generated with pip freeze > requirements.txt) and add venv/ to your .gitignore. Anyone cloning your project just runs pip install -r requirements.txt inside their own fresh venv.

03 · Creating a project and an app

A Django project is the whole website; an app is one self-contained feature inside it. You create the project once, then create as many apps inside it as your site needs.

What it is

This distinction trips up a lot of beginners because the video (like most spoken explanations) uses "project" and "application" almost interchangeably in places. Here's the clean version:

  • Project — the top-level container: overall settings, the main URL map, and the folder that ties everything together. You typically have exactly one per website.
  • App — a smaller, focused module inside the project that handles one piece of functionality (e.g. a blog app, a payments app, an accounts app). A project can contain many apps, and well-designed apps can even be reused across different projects.
# 1. Create the project (run this once)
django-admin startproject myproject

# 2. Move into the project folder
cd myproject

# 3. Create an app inside it (repeat for each app you need)
python manage.py startapp myapp

# 4. Start the development server
python manage.py runserver
After runserver, open http://127.0.0.1:8000/ in a browser (127.0.0.1 and localhost both mean "this computer"). Seeing Django's "install worked" page confirms everything so far is correct.

Why two different commands?

Notice startproject uses django-admin (a general command-line tool that exists outside any project), while startapp uses manage.py (a file that gets generated inside your project and knows about that specific project's settings). That's why you must cd into the project folder before creating an app — manage.py only exists there.

Researched — code editors

The video spends time recommending PyCharm Professional (a paid, 30-day-trial editor) because it auto-generates project files through a UI. That's a convenience, not a requirement — Django itself doesn't care what editor you use. VS Code is free, has excellent Python/Django extensions, and is what the majority of Django developers use day to day. The command-line steps above work identically no matter which editor you open the resulting folder in.

Industry best practice

Name apps after what they do, not generically (blog, orders, accounts — not app1, myapp). It matters because the app name becomes a Python package name used throughout your code and database table names.

04 · The MVT architecture

Django organizes every feature into three cooperating pieces: a Model (data), a View (logic), and a Template (what the user sees) — MVT for short.

What it is

Think of a login page. There's the box the user types into (what they see), the check of whether their password is correct (what the computer does), and the actual stored record of the correct password (where the data lives). Django gives each of those a name and a dedicated place to live:

  • Model — represents your data. Each model is a Python class that Django turns into a database table. This lives in models.py.
  • View — the logic. A Python function (or class) that receives a request, does something (maybe checks the database via a model), and sends back a response. This lives in views.py.
  • Template — the presentation layer, i.e. the HTML the user actually sees in their browser.

Why it matters

Separating these three concerns means you can change how a page looks (template) without touching how it works (view), and change how data is stored (model) without rewriting the page. This separation is what makes a growing Django project stay manageable instead of turning into one giant tangled file.

Researched — MVT vs. MVC

You may have heard of the more common MVC (Model-View-Controller) pattern from other languages. Django's MVT is conceptually the same idea with different naming: Django's "View" is really the controller (the logic that decides what happens), and Django's "Template" is really the view (what's displayed) in classic MVC terms. Django's own FAQ confirms this — the "controller" role is handled by Django's framework itself (the URL dispatcher), which is why there's no separate "C" in MVT.

05 · Project file structure

Running startproject and startapp generates a set of files automatically. Each one has a specific, fixed job — here's what each does and when you'll actually touch it.

Project-level files

These live in the inner folder named after your project (e.g. myproject/myproject/) and control the whole site.

FileWhat it does
manage.pyThe command-line utility for this project — every command (runserver, startapp, makemigrations, etc.) runs through it.
settings.pyGlobal configuration: installed apps, database connection, middleware, templates folder location — one file that affects the entire project.
urls.pyThe site's URL map — decides which view runs for which web address.
wsgi.pyEntry point used by traditional web servers (like Apache) to run your Django app in production. You won't edit this during development.
asgi.pyThe newer, async-capable counterpart to wsgi.py, for servers that support asynchronous features (e.g. WebSockets). Also not touched in normal development.
__init__.pyAn empty file that just tells Python "treat this folder as a package." You never put code in it.

App-level files

These are generated fresh inside every app folder you create with startapp.

FileWhat it does
models.pyDefine this app's data — Python classes that become database tables.
views.pyThis app's logic — functions/classes that handle requests and return responses.
admin.pyRegister models here to manage them through Django's built-in admin panel.
apps.pySmall configuration class for this app; default settings are almost always fine as-is.
migrations/Auto-generated history of every change made to your models, used to keep the database in sync.
tests.pyWhere you write automated tests for this app's code.
Gap‑filled

The video walks through most of these files but never mentions tests.py, which Django generates automatically in every new app. It's where you write code that automatically checks your app still works correctly as you make changes — an important habit once your apps grow beyond a few views.

Industry best practice

Register every new app in INSTALLED_APPS inside settings.py the moment you create it — an app that isn't registered there is invisible to Django (its models won't migrate, its templates won't be found). This is the single most common "why isn't this working" mistake for beginners.

06 · Your first view

A view is just a Python function that takes a web request and returns a web response — the simplest one just sends back a line of text.

Writing the view

# myapp/views.py
from django.http import HttpResponse

def v1(request):
    return HttpResponse("This is my first Django web application.")
  • request — every view function must accept this parameter; Django passes in details of the incoming browser request. You don't have to use it, but it must be there.
  • HttpResponse — a Django class that wraps whatever text/HTML you give it into a proper web response the browser understands. You import it from django.http.

Connecting it to a URL

A view does nothing on its own — Django needs to know which web address should trigger it. That mapping happens in urls.py:

# myproject/urls.py
from django.contrib import admin
from django.urls import path
from myapp import views

urlpatterns = [
    path('admin/', admin.site.urls),
    path('v1/', views.v1),
]
Now visiting http://127.0.0.1:8000/v1/ runs v1() and shows its response. Visiting /v1 without the trailing content will 404 (page not found) since no pattern matches it exactly.

Industry best practice

Returning raw HttpResponse text like this is only for learning the request/response cycle. Real views almost always use render() to return a full HTML template instead — you'll see this properly once templates are introduced. Avoid writing HTML directly inside a Python string in real projects; keep HTML in template files.

07 · URL routing: project-level vs. app-level

Once a project has more than one app, cramming every URL into the project's single urls.py becomes messy. The fix: give each app its own urls.py, and have the project file simply hand off to it.

The problem with one big urls.py

If myapp and myapp_one both define a view called v1, and both are imported into the same project-level urls.py, Python's import system only keeps the most recent import of that name — so one app's view silently shadows the other's. This is exactly the confusing bug the video runs into.

The fix: per-app urls.py + include()

# myapp/urls.py  (new file you create yourself)
from django.urls import path
from myapp import views

urlpatterns = [
    path('v1/', views.v1),
    path('v2/', views.v2),
]
# myproject/urls.py  (project-level — just delegates)
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('myapp/', include('myapp.urls')),
    path('myapp-one/', include('myapp_one.urls')),
]
Now /myapp/v1/ and /myapp-one/v1/ are two completely distinct, unambiguous addresses — even though both apps have a view named v1.

Industry best practice

Every real Django project uses app-level urls.py + include() — it's considered a firm convention, not optional. It keeps apps self-contained (an app's URLs live with the app) and means the project-level file stays short and readable no matter how many apps you add.

Gap‑filled

The video also mentions optionally giving each URL pattern a name, e.g. path('v1/', views.v1, name='view-one'). This isn't just cosmetic — a named URL lets you reference it elsewhere in your code (templates, redirects) as 'view-one' instead of hardcoding the string '/myapp/v1/'. If you ever change the actual URL path later, every reference using the name still works automatically. This is standard practice in real projects.

08 · Admin panel & superuser

Django gives you a ready-made admin website for managing your data — you just need to create a superuser account to log into it, and register your models so they show up.

Creating a superuser

A superuser is an administrator account with full permissions — it can log into the admin panel, manage other users, and edit any registered data.

python manage.py createsuperuser
# then follow the prompts: username, email (optional), password

With the server running, visit http://127.0.0.1:8000/admin/ and log in with those credentials.

Making a model visible in the admin

Just because a model exists in models.py doesn't mean it appears in the admin panel — you have to register it explicitly:

# myapp/admin.py
from django.contrib import admin
from .models import Student

admin.site.register(Student)

Why this step

The admin panel is one of Django's biggest time-savers — instead of writing your own "add/edit/delete records" pages, Django auto-generates a working management UI for any model you register. It's meant for site administrators/staff, not end users of the public website.

Industry best practice

Never expose the default /admin/ URL as-is on a real production site without extra hardening (strong passwords, limiting who has superuser accounts, and often changing the admin URL path) — it's a well-known target since every Django site has one by default.

09 · Models & migrations

A model is a Python class that describes a database table. Migrations are the mechanism that turns that class into actual tables and columns in your database.

What it is

Instead of writing raw SQL to create tables, you describe your data as a Python class. Django reads that class and generates the equivalent SQL for you.

# myapp/models.py
from django.db import models

class Student(models.Model):
    s_id = models.IntegerField()
    s_name = models.CharField(max_length=100)
    s_address = models.CharField(max_length=200)
    s_location = models.CharField(max_length=100)
  • The class Student becomes a database table named (by default) myapp_student.
  • Each class attribute becomes a column — s_name becomes a column that only accepts text up to 100 characters (CharField(max_length=100)), s_id only accepts whole numbers (IntegerField), and so on.

Turning the class into a real table

# Step 1 — generate a migration file describing what changed
python manage.py makemigrations

# Step 2 — actually apply those changes to the database
python manage.py migrate

makemigrations looks at your models and writes a migration file (inside the app's migrations/ folder) containing the SQL needed to match the database to your models. migrate then runs that SQL against the actual database, creating or updating the real tables.

Gap‑filled

The video describes the concept of migrations in detail but never shows an actual models.py class with real field types. The example above (CharField, IntegerField) fills that gap — these field types are how Django knows what kind of column to create and what validation to apply.

Industry best practice

Run makemigrations every time you change a model, and commit the generated migration files to version control — they're part of your project's history, not throwaway files. Never edit an already-applied migration file by hand; if a model needs to change further, make the change and run makemigrations again to generate a new one.

Researched — the default database

Every new Django project is pre-configured (in settings.py, under DATABASES) to use SQLite — a lightweight, file-based database (your project's db.sqlite3 file) that needs no separate server, which is why it works instantly for learning. Production sites usually switch to PostgreSQL or MySQL by changing this same settings block — the rest of your code (models, views) doesn't need to change.

10 · HTML basics

HTML (HyperText Markup Language) is the mandatory foundation of every web page — it describes content and structure, not styling or behavior.

The basic structure

Every HTML page has two main parts: a <head> (metadata — page title, links to CSS/JS files, not visible on the page itself) and a <body> (the actual visible content).

<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>Home Page</title>
</head>
<body>
    <h1>This is heading one</h1>
    <p>This is a paragraph.</p>
</body>
</html>
  • <!DOCTYPE html> — tells the browser this is a modern HTML5 document.
  • <meta charset="UTF-8"> — sets the character encoding so text (including special characters) displays correctly.
  • <title> — the text shown on the browser tab, not on the page itself.
  • <h1> to <h6> — heading levels, from largest/most important (h1) to smallest (h6).
  • <p> — a paragraph of text.

Creating & previewing an HTML file inside a Django project

Outside of Django, writing an HTML page usually means opening a plain text editor, typing the tags by hand, saving the file with a .html extension, then double-clicking it to open it in a browser. Inside a Django project this is smoother: in the templates folder, right-click → New → HTML File, give it a name (e.g. home.html), and the editor auto-generates the boilerplate skeleton for you (<!DOCTYPE html>, <html>, <head> with a charset meta tag, empty <body>) — you don't type that scaffold from scratch every time.

To preview it, most Django-aware editors show browser icons (Chrome, Firefox, Edge) right next to the file — clicking one opens a live preview of that HTML file directly, with no separate "run" step needed.

Gap‑filled

This in-editor preview is just a convenience for *looking at* the static markup while you're learning HTML in isolation. Once this HTML becomes a real Django template, you won't open the .html file directly in a browser anymore — you'll visit a URL that your Django dev server serves (e.g. http://127.0.0.1:8000/), which runs it through a view first. Opening the raw file skips Django entirely and any {{ }} template tags would show up as literal text instead of rendering.

Comments

A comment is text the browser parses but never displays — used to leave notes for yourself or other developers reading the code later.

<!-- This is a comment, it will not show up on the page -->
<h1>This is heading one</h1>

Comments start with <!-- and end with --> — anything in between (even multiple lines) is ignored by the browser.

Lists

HTML has two list types: <ol> (ordered — numbered) and <ul> (unordered — bulleted). Each item inside either one uses <li> (list item).

<ol>
    <li>C</li>
    <li>C++</li>
    <li>Python</li>
</ol>

By default an <ol> numbers items 1, 2, 3…. The type attribute changes the numbering style:

type valueRenders as

aa, b, c, d

ii, ii, iii, iv (lowercase Roman numerals)
Example

An ordered list of the podium finishers, lettered instead of numbered:

<ol type="A">
    <li>Asha</li>
    <li>Ravi</li>
    <li>Meera</li>
</ol>
<!-- Renders as: A. Asha   B. Ravi   C. Meera -->

<ul> has no type-based numbering — it always shows bullets, and ordering the items has no visual effect (they're conceptually "not in a particular order").

<strong> and <em> render the same visually (bold/italic) but also carry meaning — "this text matters" / "this text is emphasized" — which screen readers and search engines pick up on. <b> and <i> are purely visual with no semantic meaning.

Gap‑filled — <mark> vs. <marquee>

These sound alike (and the video's audio makes them easy to mix up) but they're two completely different tags. <mark>, above, just highlights text in place. <marquee>, below, makes text scroll across the screen — a different, much older tag with a completely different purpose.

Researched — <big> and <strike>

Per MDN, <big> was dropped from the HTML5 standard entirely (it still renders in most browsers for backward compatibility, but you should never use it in new code — use CSS font-size instead). <strike> is officially obsolete too, superseded by <del> (semantically "removed") or <s> (just "no longer accurate/relevant", no removal implied).

The <marquee> tag — and why to avoid it

<marquee> makes its text scroll across the page — historically used for banner-style alerts, e.g. a bank's website scrolling an important notice so it catches the customer's eye.

<marquee>Welcome to Durga Sir</marquee>
<marquee bgcolor="red" direction="right">Welcome to Durga Sir</marquee>
  • bgcolor — background color behind the scrolling text.
  • direction — which way it scrolls (left by default, or right, up, down).
Researched — don't use <marquee> in real projects

<marquee> was never part of any official HTML standard — MDN marks it deprecated and explicitly warns against using it, since browsers aren't required to keep supporting it. It's shown here because it still appears in a lot of tutorials and older sites, and it's useful to recognize. For a scrolling-banner effect in a real project, use a CSS animation instead — it's supported the same way everywhere and doesn't rely on a non-standard element.

Images

<img src="flag.jpg" alt="Country flag">
  • <img> is self-closing (no separate closing tag needed) — unlike <p> or <b>, which need </p> / </b>.
  • src — the image file's location.
  • alt — fallback text shown if the image fails to load. Not optional in real projects — see below.
Gap‑filled

The video frames alt text purely as a "broken image" fallback. Its bigger purpose: screen readers read alt text aloud for visually impaired users, so every meaningful image needs a real, descriptive alt — this is a baseline accessibility requirement, not a nice-to-have.

Tables

<table border="1">
    <tr>
        <th>Employee ID</th>
        <th>Name</th>
    </tr>
    <tr>
        <td>101</td>
        <td>Asha</td>
    </tr>
</table>

<table> is the container, <tr> is one table row, <th> is a header cell (bold, centered by default), and <td> is a normal data cell.

To center content inside a cell, add align="center" to the <th> or <td>:

<td align="center">101</td>
Gap‑filled

align is a presentational HTML attribute — it's old-style, like <b>/<i> were for bold/italic. Modern practice is to keep HTML for structure only and do alignment with CSS instead: text-align: center; on the cell (covered in the CSS topic below). align still works in every browser, so you'll see it in a lot of older tutorials and code, but don't reach for it in a new project.

Tables with images

A table cell can hold any HTML, including an <img> — useful for something like a "country + flag" list.

<table border="1">
    <tr>
        <th>#</th>
        <th>Country</th>
        <th>Flag</th>
    </tr>
    <tr>
        <td align="center">1</td>
        <td align="center">India</td>
        <td align="center"><img src="india.jpg" alt="Flag of India"></td>
    </tr>
    <tr>
        <td align="center">2</td>
        <td align="center">USA</td>
        <td align="center"><img src="usa.png" alt="Flag of USA"></td>
    </tr>
</table>

Each <img> just goes inside its own <td>, exactly like it would anywhere else on the page — a table cell is just another container.

Gap‑filled — HTML is a markup language, not a programming language

Every row above was typed out by hand. In a real Django app, table rows like these usually need to come from a database — e.g. one row per employee — and the number of rows isn't known ahead of time. You can't write a loop in plain HTML to generate rows dynamically, because HTML has no logic: no variables, no if/for, no classes or objects (the "OOP" concepts Django/Python have). HTML only describes structure. Repeating rows for database records is done with the Django Template Language (DTL) — e.g. {% for employee in employees %} — which is covered once templates are connected to views and models.

Hyperlinks

<a href="https://www.djangoproject.com">Go to Django's site</a>

<a> is the anchor tag; href (hyperlink reference) is the destination — either another page on your own site (e.g. href="index.html") or a full external URL.

Industry best practice

Use headings (h1–h6) in order to reflect document structure, not just for font size — skipping from h1 straight to h4 for a smaller look is a common beginner mistake that hurts accessibility and SEO. Use CSS to control size instead.

11 · HTML forms

Forms are how a web page collects input from a user — logins, registrations, search boxes — and every form is built from a <form> wrapping one or more <input> elements.

A basic form

<form action="index.html" method="post">
    <label for="uname">Enter name</label>
    <input type="text" id="uname" name="username" placeholder="Enter name" required>
    <br>
    <input type="password" name="pwd">
    <br>
    <input type="submit" value="Submit">
</form>

The pieces

  • action — where the form's data gets sent when submitted.
  • method — how it's sent (commonly post for data that changes something, get for simple lookups).
  • type on <input> — controls what kind of field it is: text, password (hides typed characters), email, checkbox, radio, submit, and more.
  • name — the identifier used to read this field's value once the form is submitted (in JavaScript or on the server). Without a name, a field's value is never sent — even if the user fills it in.
  • value — its meaning depends on the input type. For text/email/password, it's a pre-filled default the user can overwrite — usually left blank so the user provides it themselves. For checkbox/radio/submit, it's not shown to the user at all — it's the identifier sent to the server for that specific option when checked/clicked.
  • placeholder — greyed-out hint text shown inside an empty field; disappears once the user types.
  • required — the browser won't let the form submit until this field has a value.
  • <label for="uname"> — links descriptive text to the input whose id="uname" matches. This isn't just cosmetic: clicking the label text focuses the input, and screen readers announce the label when the field is focused.
Example — grouping checkboxes and radio buttons

Giving multiple inputs the same name groups them. For checkboxes, any number can be checked, and each checked one's value is sent. For radio buttons, the shared name makes them mutually exclusive — only one can be selected at a time.

<p>Pick your courses:</p>
<input type="checkbox" id="py" name="course" value="python">
<label for="py">Python</label>
<input type="checkbox" id="cs" name="course" value="csharp">
<label for="cs">C#</label>

<p>Preferred contact method:</p>
<input type="radio" id="em" name="contact" value="email" checked>
<label for="em">Email</label>
<input type="radio" id="ph" name="contact" value="phone">
<label for="ph">Phone</label>

If both checkboxes are checked, the server receives course=python and course=csharp. For the radio group, only whichever one is selected is sent — here contact=email is selected by default via the checked attribute.

Industry best practice

Always pair every input with a <label> (via matching for/id), not just a nearby paragraph of text — a paragraph has no programmatic connection to the field, so assistive technology can't associate the two.

Researched — CSRF protection

The forms here are plain HTML with no Django involved yet, so they work as shown. The moment a form like this actions to a real Django view with method="post", Django's CSRF protection will reject the submission unless the form includes {% csrf_token %} inside it. This is a security feature (prevents other sites from silently submitting forms to your app on a logged-in user's behalf) — expect a 403 Forbidden error the first time you wire a POST form into Django and forget it.

CSS (Cascading Style Sheets) controls how HTML looks — colors, fonts, spacing, layout. There are three ways to attach CSS to a page, and only one of them is recommended for real projects.

Gap‑filled

Inside a Django project, an external stylesheet is created the same way as an HTML template: in the templates folder, right-click → New → Style Sheet, name it with a .css extension (e.g. sample.css). Researched — the rel attribute is not optional

The video calls rel="stylesheet" optional. That's incorrect for linking CSS: per the HTML spec, rel is what tells the browser how to treat the linked file — without rel="stylesheet", the browser has no reason to apply the file's contents as CSS at all, and the styles silently won't load. Which style wins? (priority)

If the same element gets conflicting styles from more than one place, CSS follows a clear order:

  1. Inline style always wins over internal or external, no matter what.
  2. Between internal and external: whichever one appears later (further down) in the HTML file wins. So if your <link> to the external file appears before an internal <style> block, the internal block wins (it's "later"). If the internal block is written first and the external link comes after it, the external file wins.
Researched — the real rule (specificity)

The "whichever comes later wins" rule the video gives is true only when the competing rules have equal specificity (roughly, how precisely a selector targets an element). CSS actually resolves conflicts using a specificity score first, and only falls back to "later wins" when scores are tied. See the next topic for the full, correct version of this — including why ID and class selectors change the outcome.

Industry best practice

External stylesheets are what real projects use almost exclusively — one CSS file styling an entire site means a single edit updates every page. Inline styles are reserved for rare one-off overrides (or dynamic styles set by JavaScript); internal <style> blocks are mostly avoided outside of quick demos, exactly like this video is using them for.

Researched — CSS specificity, precisely

Every selector gets a specificity score. From highest to lowest priority:

  1. Inline styles — always highest (see previous topic).
  2. ID selectors (#main) — very high.
  3. Class, attribute, and pseudo-class selectors (.center, :hover) — medium.
  4. Element and pseudo-element selectors (p, ::first-letter) — lowest.

Pseudo-elements style a specific part of an element rather than the whole thing:

a:hover   { color: yellow; } /* mouse over it */
a:active  { color: blue; }   /* being clicked, right now */
Remember the order with the mnemonic LoVe HAte — Link, Visited, Hover, Active. Writing them in a different order can make :hover or :active silently fail to apply.
Industry best practice

14 · Backgrounds, div/span & overflow

Three more CSS building blocks: styling background images, grouping content with div/span, and controlling what happens when content is too big for its box.

Background images

body {
    background-image: url('flag.jpg');
    background-repeat: no-repeat;
    background-position: right top;
    background-attachment: fixed;
    background-size: cover;
}
  • background-repeat: no-repeat — stops the image tiling across the whole page.
  • background-position — where the image sits (e.g. right top, center).
  • background-attachment: fixed — the image stays in place even as the page scrolls.
  • background-size: cover — stretches the image to fill the entire element, cropping if needed.
Example — shorthand

All five properties above can be combined into a single background declaration, in the order image → repeat → position → attachment:

body {
    background: url('flag.jpg') no-repeat right top fixed;
}
Gap‑filled — body vs. html for a true full-page background

Setting the background on body only covers the area the page's content actually occupies — on a short page, the color/image stops where the content ends, leaving a gap below. Setting it on html instead covers the entire browser viewport, since <html> is the outermost element and always spans the full window height. For a background that's guaranteed to fill the whole visible page, target html (or set min-height: 100% on body as an alternative).

<div> vs. <span>

Both are generic containers with no visual style of their own — they exist purely to group content so you can apply CSS or JavaScript to that group.

  • <div> — a block-level element (block-level means it takes up the full width available and starts on a new line). Used to group larger sections — a header, a sidebar, a card.
  • <span> — an inline element (inline means it only takes up as much width as its content, and stays in the flow of surrounding text). Used to style a small piece of text inside a sentence without breaking the line.
<style>
    div { color: red; background-color: lightblue; }
    span { color: green; font-size: 20px; font-family: Georgia; }
</style>

<div>
    <h1>This is heading one</h1>
    <h2>This is heading two</h2>
</div>

<p><b>Welcome to</b> <span>Durga's class</span></p>

Everything inside the <div> (both headings) gets red text on a light-blue background, and starts on its own new block. Only the word wrapped in <span> gets its own styling — the rest of that paragraph's text flows normally around it, on the same line.

Overflow

When content is bigger than the box you've given it (via fixed width/height), overflow decides what happens to the extra content:

ValueEffect
visibleExtra content spills outside the box (the default)
hiddenExtra content is clipped and simply not shown
scrollScrollbars appear so the user can scroll to see the rest
autoScrollbars appear only if needed
p {
    height: 200px;
    width: 400px;
    border: 3px solid red;
    overflow: scroll;
}

Here the paragraph's box is fixed at 400×200 pixels. If the text inside is longer than that box, overflow: scroll keeps it readable by adding scrollbars, rather than letting it spill past the red border (visible) or silently cutting it off (hidden).

Researched — centering content isn't just "align"

The video reaches for a generic "align" property to center content inside a box and finds it doesn't work directly — that's expected. text-align: center centers inline content (text, images) horizontally within its container. align-content/align-items only have an effect inside a display: flex or display: grid container — applying them to an ordinary block element (like a plain <div> or <p>) does nothing, which is exactly the confusion in the video. To center a block element itself (not just its content) horizontally, the standard approach is margin: 0 auto; with a fixed width.

Industry best practice

Prefer overflow: auto over scroll in real layouts — auto only shows scrollbars when content actually overflows, while scroll shows them permanently even when there's nothing to scroll, which looks broken to users.

15 · JavaScript basics

JavaScript adds behavior and interactivity to a web page — things HTML and CSS alone can't do, like reacting to a click or validating a form before it's submitted.

Gap‑filled — what JavaScript actually is

JavaScript is a lightweight, interpreted language (run line-by-line by the browser, like Python — not compiled ahead of time) and dynamic (variable types are figured out at runtime, not declared upfront). It was originally named LiveScript; the rename to "JavaScript" was a marketing decision to ride on Java's popularity at the time — the two languages are otherwise unrelated, despite the similar name. In a Django project, JavaScript's main job is client-side validation: catching obviously-bad form input in the browser, before it's ever sent to the server (HTML provides structure, CSS provides styling, JavaScript provides behavior).

Where JavaScript code lives

Like CSS, JavaScript can be internal (inside a <script> tag on the page) or external (a separate .js file, linked in).

<!-- internal -->
<script>
    console.log("Hello, Durga!");
</script>

<!-- external -->
<script src="script.js"></script>
Convention: place <script> tags in the <head>, same as CSS <link> tags — though for scripts that manipulate content on the page, placing them at the end of <body> is also common so the HTML loads first.

src on <script> works exactly like href did for a CSS <link> — it points to the external file. Unlike the CSS rel attribute, though, the type="text/javascript" attribute really is optional here: modern HTML defaults <script> to JavaScript, so omitting type works correctly in every current browser.

Gap‑filled

Inside a Django project, create an external JavaScript file the same way as an HTML template or a CSS file: in the templates folder, right-click → New → JavaScript File, name it (e.g. sample.js). Link it into a page with <script src="sample.js"></script>.

Comments

// single-line comment

/* multi-line
   comment */

Same purpose as HTML comments: notes for whoever reads the code later. The JavaScript interpreter skips comments entirely — they have no effect on how the script runs.

Displaying output — and which method to actually use

MethodWhat it does
console.log()Prints to the browser's developer console (not visible on the page) — the standard tool for debugging
alert()Shows a popup dialog box the user must dismiss
document.write()Writes directly into the page's HTML
Gap‑filled

The video shows all three as roughly interchangeable options. In real code, document.write() is avoided — if it runs after the page has finished loading, it wipes out the entire existing page content, which causes hard-to-debug bugs. console.log() is the standard for debugging; alert() is reserved for messages that genuinely need to interrupt the user.

Variables

let name = "Durga";
console.log("Your name is " + name);

// getting input at runtime
let userName = prompt("Enter name");
let a = Number(prompt("Enter first number"));
let b = Number(prompt("Enter second number"));
console.log("Sum is " + (a + b));

prompt() is JavaScript's equivalent of Python's input() — but everything it returns is always text. That's why Number(...) wraps it above: without converting, "10" + "20" would produce the text "1020" (stuck together) instead of adding to 30.

Example — even/odd checker

Combining a runtime-entered number with an if/else and the remainder operator %:

let n = Number(prompt("Enter any number"));

if (n % 2 == 0) {
    console.log(n + " is even");
} else {
    console.log(n + " is odd");
}

% gives the remainder of a division — n % 2 is 0 for any even number and 1 for any odd number, which is exactly what the condition checks. Input 7 → output "7 is odd"; input 10 → output "10 is even".

Gap‑filled — var vs. let vs. const

The video only ever declares variables with var. Modern JavaScript (since 2015) prefers let (for values that change) and const (for values that never get reassigned). var has looser, more error-prone scoping rules that let/const were introduced specifically to fix. Current style guides, including MDN's, recommend avoiding var in new code — that's why every example on this page uses let instead.

16 · DOM manipulation & form validation

JavaScript can reach into a loaded page and change it (DOM manipulation), and it's most commonly used in forms to catch bad input before it's ever sent to the server.

Functions & the onclick event

A function is a named, reusable block of code — write it once, then run it whenever you need to by calling its name. In the browser, functions are commonly triggered by events: something the user does, like clicking a button.

<script>
function sayHello() {
    alert("Hello!");
}
</script>

<input type="button" value="Click here" onclick="sayHello()">

function sayHello() { ... } defines the function but doesn't run it — nothing happens until it's called. onclick="sayHello()" on the button is that call: it wires up the click event so the function runs each time the button is clicked. Unlike Python, JavaScript doesn't use indentation to mark a function's body — the curly braces { } do that job.

What "DOM" means

The DOM (Document Object Model) is the browser's live, in-memory representation of your HTML page — a structure JavaScript can read and change after the page has loaded, and the browser instantly reflects those changes on screen.

<p id="msg">This is my first paragraph.</p>

<script>
    document.getElementById("msg").innerHTML = "Welcome, Durga!";
</script>

document.getElementById("msg") finds the one element whose id is "msg"; .innerHTML is the property holding everything inside that element, which you can read or overwrite.

Form validation

<form name="myform" onsubmit="return validateForm()">
    Name: <input type="text" name="username"><br>
    Password: <input type="password" name="pwd"><br>
    <input type="submit" value="Login">
</form>

<script>
function validateForm() {
    let name = document.myform.username.value;
    let pwd  = document.myform.pwd.value;

    if (name == "") {
        alert("Name cannot be blank");
        return false;
    }
    if (pwd.length < 6) {
        alert("Password must be at least 6 characters long");
        return false;
    }
    return true; // only now does the form actually submit
}
</script>

The key mechanic: onsubmit="return validateForm()". If validateForm() returns false, the browser cancels the submission entirely — the form never leaves the page. If it returns true, submission proceeds normally — to wherever the form's action attribute points (e.g. <form action="https://example.com" ...> would send the browser there once validation passes).

Matching two password fields

function matchPwd() {
    let p1 = document.myform.password1.value;
    let p2 = document.myform.password2.value;
    if (p1 != p2) {
        alert("Passwords must be the same");
        return false;
    }
    return true;
}
Gap‑filled — this is an important limitation, not a footnote

Client-side JavaScript validation only improves the user's experience (instant feedback, no round-trip to the server for an obvious mistake). It is not a security boundary — anyone can open their browser's developer tools, disable JavaScript, or send a request directly (bypassing the form entirely) and submit whatever data they want. The video actually mentions this near the end: Django performs its own server-side validation regardless, and that server-side check is the one that actually protects your data. Treat JavaScript validation as a convenience layered on top of — never a replacement for — server-side validation (in Django, this means using Django Forms/ModelForms, covered in later sessions).

17 · jQuery basics

jQuery is a JavaScript library that lets you write much shorter code for common tasks like selecting elements and handling clicks — its own slogan is "write less, do more."

What it is

A library is a pre-written bundle of code you can call into, instead of writing everything from scratch. jQuery specifically wraps a lot of common, repetitive JavaScript (selecting elements, showing/hiding things, handling events, and AJAX — Asynchronous JavaScript and XML, i.e. fetching data from a server without reloading the page) into short one-line methods.

jQuery was created by John Resig in 2006. Its main selling points at the time: it's small and fast, and it smooths over inconsistencies between browsers — the same jQuery code reliably works the same way across Chrome, Firefox, Edge, etc., which plain JavaScript of that era often didn't.

Example — separate hide and show buttons

Common pitfall

It's easy to swap the code inside two handlers by accident — e.g. writing .hide() inside the #show button's click handler — and get no visible error, just a button that silently does the wrong thing (or nothing). If a jQuery action doesn't seem to fire, double-check that the selector in $("#id") actually matches the element you clicked, and that the action inside is the one you meant for that specific handler.

Researched — is jQuery still worth learning?

jQuery was essential a decade ago because plain JavaScript was verbose and inconsistent across browsers. It's still worth knowing because a huge number of existing/older sites (and some third-party front-end libraries) still depend on it, but for new Django projects specifically, plain JavaScript or a modern front-end approach is now more common than reaching for jQuery by default. Django itself has no dependency on jQuery at all.

18 · Bootstrap basics

Bootstrap is a free front-end framework: a huge, ready-made library of CSS and JavaScript that gives you working, good-looking, mobile-friendly components without writing them from scratch.

What it is, and why "responsive design" matters

A framework here means a large pre-built set of CSS classes (and some JavaScript) for common UI needs — buttons, tables, navigation bars, forms, spinners, pagination — that you apply just by adding a class name, instead of writing the CSS yourself.

Bootstrap's headline feature is responsive design: the same page automatically rearranges itself to fit the screen it's viewed on, from a wide desktop monitor down to a narrow phone screen — without you writing separate mobile and desktop versions.

Gap‑filled — why this used to be a bigger deal

Before responsive frameworks were standard, sites were often built for desktop only, and mobile visitors got a broken, oversized layout — or the site offered a separate link to switch to a stripped-down "mobile view." Bootstrap's grid and components use CSS that adapts continuously to the available width, so one HTML page serves every screen size correctly by default. This is also why Bootstrap saves real development time and gives visual consistency across pages — you're reusing tested components instead of rebuilding the same button or nav bar with custom CSS on every page.

19 · Rendering templates: render(), context & GET vs. POST

Real views don't return raw text — they hand data to an HTML template file with render(). And once a page has a form, you have to choose how that form's data reaches your view: GET or POST.

From HttpResponse to render()

Lecture 6 used HttpResponse to send text straight back to the browser. Writing actual HTML inside a Python string works, but mixes two languages in one file and gets unreadable fast — exactly the problem templates solve.

# myapp/views.py
from django.shortcuts import render

def home(request):
    return render(request, 'home.html', {'name': 'Mohan'})

CSRF protection — required for every POST form

Back in Lecture 6, a note flagged that a plain HTML form POSTing to a real Django view needs a CSRF token, or Django rejects the submission. Here's the full picture: CSRF stands for Cross-Site Request Forgery — an attack where a malicious site tricks a logged-in user's browser into submitting a request to your site without their knowledge. Django blocks this by requiring a secret, per-session token inside every POST form.

<form action="add/" method="post">
    {% csrf_token %}
    ...
</form>

Without this tag inside the <form>, submitting triggers a 403 Forbidden — "CSRF verification failed". It's only required for method="post" forms; GET forms don't need it, since GET is meant to only read data, never change it.

Gap‑filled — the trailing-slash trap

The video also runs into an APPEND_SLASH redirect error: Django, by default, auto-redirects a URL missing its trailing slash (e.g. /myapp/add → /myapp/add/). For a GET request that's invisible and harmless. For a POST, the redirect drops the submitted data entirely, since a redirect is a fresh GET request. The fix is simple but easy to miss: make sure your form's action — and the URL pattern it targets — already has the correct trailing slash, so Django never needs to redirect it.

CSS, JavaScript, images, and other files that don't change per-request are static files — Django serves these through a dedicated system, separate from templates, so your project stays organized as it grows.

Setup, step by step

  1. Confirm django.contrib.staticfiles is in INSTALLED_APPS (in settings.py). PyCharm's project wizard adds it automatically; if you created the project another way, add it yourself.
  2. Create a static folder at the project root (next to manage.py), with subfolders for organization — commonly css/, javascript/, images/. The names are convention, not a Django requirement.
  3. Point Django at that folder, in settings.py:

  4. Load the static-file template tag at the top of any template that uses one: {% load static %}
  5. Reference a file: 
    {% load static %}

Common pitfall

Forgetting {% load static %} produces "Invalid block tag 'static'" — exactly the error the video hits. It must be loaded in every template file that uses {% static ... %}, even ones that {% extends %} another template that already loaded it.

Researched — STATIC_URL vs. STATICFILES_DIRS

The video moves between these without separating them clearly. Per the Django docs: STATIC_URL (already set to '/static/' by default in a new project) is the URL prefix browsers use to request a static file — it's what {% static %} prepends to the path you give it. STATICFILES_DIRS is the list of folders Django actually searches on disk, during development, to find that file. Researched — this setup is development-only

This is a "later" concern, not something to set up yet — but good to know the local setup here isn't the final deployment story.

Gap‑filled

Everything above works whether the file is CSS, JavaScript, or an image — the mechanism ({% load static %}, then {% static 'path/to/file' %}) is identical regardless of file type. This is also exactly where a downloaded Bootstrap or jQuery bundle belongs in a real Django project, instead of sitting loose in templates.

Real sites don't copy-paste the same header, nav bar, and footer into every template. {% extends %} and {% block %} let one shared base template define that structure once — and DTL's if/for add basic branching and looping inside templates.

Template inheritance

Same idea as class inheritance in Python: a child template reuses everything from a parent template, and only overrides the specific pieces it needs to.

<!-- base.html -->
<body style="background-color: orange;">
    <title>{% block title %}Default Title{% endblock %}</title>
    <h1>Welcome to Durga's site</h1>
    {% block content %}
    {% endblock %}
</body>
<!-- emp.html (child) -->

{% block content %}
    <h2>Employee ID: {{ EID }}</h2>
{% endblock %}

base.html defines named "slots" with {% block name %} ... {% endblock %}. emp.html declares {% extends 'base.html' %} and then re-defines the same-named blocks — Django slots that content into the matching spot in base.html, while everything else in base.html (the orange background, the <h1>) comes through unchanged.

Gap‑filled

{% extends %} must be the very first line in a child template — Django requires this; anything (other than a comment) before it is an error. Any block the child template doesn't override just falls back to the parent's default content for that block — which is why giving a block sensible default content in base.html (like Default Title above) is worth doing.

Industry best practice

Nearly every real Django project has one base.html with blocks for things like title, content, and often extra_css/extra_js, and every other page template extends it. This is one of the most-used DTL features in practice — it's how a whole site shares one consistent layout without duplicating markup.

Gap‑filled

23 · The Django ORM & querying models

The model layer of MVT is what actually talks to the database. Django does this through an ORM — write a Python class, and Django handles the SQL for you, both to create the table and to read records back out of it.

What "ORM" means

ORM stands for Object-Relational Mapper. It's the layer that lets your application interact with a database (SQLite, MySQL, Oracle, …) by writing Python — classes, objects, method calls — instead of raw SQL. Django's ORM reads your model classes and automatically generates the matching database schema (tables and columns).

# myapp/models.py
from django.db import models

class Employee(models.Model):
    enumber = models.IntegerField()
    ename = models.CharField(max_length=20)
    esalary = models.IntegerField()
    eaddress = models.CharField(max_length=20)
  • The table name defaults to <app_name>_<modelclassname> (lowercased) — here, myapp_employee.
  • Each field becomes a column, typed and validated according to the field class (IntegerField, CharField(max_length=...), etc.).
Gap‑filled

Since no field above is marked as the primary key, Django automatically adds one: an id column, integer, auto-incrementing, unique per row. You never declare this yourself unless you want a different field to be the primary key.

24 · One record at a time, & customizing the admin

Beyond fetching every row, you'll often need exactly one — and once your admin panel has real data in it, you'll want it to display something more useful than "Employee object (1)."

Getting a single record

emp = Employee.objects.get(pk=1)

pk (primary key) is a fixed, required keyword name here — not a name you choose — and .get() returns a single model instance, not a QuerySet.

Common pitfall

A template written for .all() — with {% for e in emp %} — breaks on a single object returned by .get(), with "Employee object is not iterable." A single model instance isn't a list, so it can't be looped. The fix is a separate template (or a separate block) that accesses fields directly — {{ emp.ename }} — with no {% for %} at all.

Readable admin entries with __str__

By default, the admin panel lists every record of a model as Employee object (1), Employee object (2), … — not useful for telling records apart. Defining __str__ on the model fixes this:

class Employee(models.Model):
    enumber = models.IntegerField()
    ename = models.CharField(max_length=20)
    esalary = models.IntegerField()
    eaddress = models.CharField(max_length=20)

    def __str__(self):
        return str(self.enumber)

__str__ is a standard Python method (not Django-specific) that's called whenever an object needs to be shown as text. Django's admin uses it to label each record. It must return a string — since enumber is an IntegerField, it has to be wrapped in str(...) first, or Django raises a TypeError.

Table-style listings with ModelAdmin

__str__ only shows one field per record. To show every field, in columns, you register a ModelAdmin class instead of the bare model:

# myapp/admin.py
from django.contrib import admin
from .models import Employee

class EmployeeAdmin(admin.ModelAdmin):
    list_display = ('enumber', 'ename', 'esalary', 'eaddress')

admin.site.register(Employee, EmployeeAdmin)

# -- or, equivalently, using the decorator style --
# @admin.register(Employee)
# class EmployeeAdmin(admin.ModelAdmin):
#     list_display = ('enumber', 'ename', 'esalary', 'eaddress')

list_display controls both which fields show as columns and their left-to-right order. Both registration styles do the same thing — admin.site.register(Model, ModelAdmin) is more explicit, @admin.register(Model) is a shorter decorator form.

Gap‑filled — a likely interview question

The video flags this directly: "What is the use of ModelAdmin? What happens if it's missing?" Answer: without a ModelAdmin, the admin panel still works, but every record shows as an opaque Employee object (N) unless you've defined __str__ — and even then, you only see one field, not a full table row per record. ModelAdmin is what makes the admin list view look like an actual table.

25 · Django Forms: building & rendering

Instead of hand-writing a form in HTML, Django's forms.Form lets you describe a form as a Python class — and Django generates the HTML input elements for you.

Why a Django form instead of a plain HTML form

  • Far less code — a form field is one line of Python instead of a full <input> tag with attributes.
  • Built-in validation (covered in Topic 26), instead of relying only on HTML5's required/type checks.
  • A form's fields can mirror a model's fields closely, which becomes fully automatic with ModelForm (Topic 27).

Creating a form

# myapp/forms.py
from django import forms

class StudentForm(forms.Form):
    name = forms.CharField()

Each class attribute (name, marks) becomes one HTML input field, typed by the Django field class used (CharField → text input, IntegerField → number-validated text input, and so on).

26 · Validating & saving form data

Once a form is submitted, a view needs to check whether the data is actually valid, read it back out, and — for the first time here — actually write it into the database.

is_valid() and cleaned_data

def student(request):
    if request.method == 'POST':
        fm = StudentForm(request.POST)
        if fm.is_valid():
            nm = fm.cleaned_data['name']
            mk = fm.cleaned_data['marks']
            print("Student name is", nm)
        else:
            print("Form data is not valid")
    else:
        fm = StudentForm()
    return render(request, 'myform.html', {'form': fm})
  • StudentForm(request.POST) — binds the submitted data to a form instance (an unbound, empty form is created with no arguments, as in the else branch).
  • fm.is_valid() — runs every field's validation and returns True/False.
  • fm.cleaned_data — a dictionary, populated only if the form is valid, keyed by each field's name, holding the validated, type-converted value (e.g. marks comes back as an actual int, not text).

Cross-field validation with clean()

To validate two fields together — like checking a password and a re-typed confirmation match — override clean() on the form:

class StudentForm(forms.Form):
    name = forms.CharField()
    password = forms.CharField(widget=forms.PasswordInput)
    rpassword = forms.CharField(widget=forms.PasswordInput)

    def clean(self):
        super().clean()
        pwd = self.cleaned_data.get('password')
        rpwd = self.cleaned_data.get('rpassword')
        if pwd != rpwd:
            raise forms.ValidationError("Password mismatch")

super().clean() runs Django's normal per-field validation first; only after that do you compare the two already-cleaned values and raise forms.ValidationError if they don't match. This error then causes is_valid() to return False for the whole form.

Single-field validation with clean_<fieldname>()

def clean_name(self):
    name = self.cleaned_data['name']
    if len(name) < 6:
        raise forms.ValidationError("Enter name with 6 or more characters")
    return name

Naming the method clean_<fieldname> (matching a real field name exactly) tells Django to call it automatically while validating that one field. Unlike clean(), this method must return the value — that return value becomes the field's final cleaned value.

Built-in and custom validators

from django.core import validators

def starts_with_s(value):
    if value[0] != 'S':
        raise forms.ValidationError("Name should start with S only")

class StudentForm(forms.Form):
    name = forms.CharField(validators=[validators.MaxLengthValidator(6), starts_with_s])

The validators argument takes a list of callables. Django ships many ready-made ones in django.core.validators (like MaxLengthValidator); you can also pass your own plain function, which just needs to accept the value and raise forms.ValidationError when it's invalid.

Actually saving to the database

Combining everything so far — a model, a form with matching fields, and a view that turns valid cleaned_data into a saved row:

# views.py
from db_app.models import Student
from db_app.forms import StudentForm

def student_view(request):
    if request.method == 'POST':
        fm = StudentForm(request.POST)
        if fm.is_valid():
            nm = fm.cleaned_data['name']
            ml = fm.cleaned_data['email']
            ad = fm.cleaned_data['address']
            pw = fm.cleaned_data['password']
            s = Student(name=nm, email=ml, address=ad, password=pw)
            s.save()
    else:
        fm = StudentForm()
    return render(request, 'student_form.html', {'form': fm})

Student(...) builds a new, unsaved model instance from the cleaned form data; .save() is what actually issues the INSERT and writes the row.

Gap‑filled

This "copy each cleaned field into a new model instance by hand" pattern works, but notice it re-lists every field a second time — first in forms.py, then again here in the view. ModelForm, covered in the next topic, removes this duplication entirely.

A view that saves data and re-renders the same page has no built-in way to say "that worked" — the messages framework is Django's answer: store a short message tied to the current request, then display it once, on the very next page render.

Same .save() call as an insert — the difference is entirely in which instance you're saving. Fetch an existing row by pk, reassign its attributes, then save.

Researched — how Django decides INSERT vs. UPDATE

Per the Django docs, .save() issues an UPDATE if the model instance's primary key already has a matching row in the database, and an INSERT otherwise. That's the entire mechanism — the video shows the "get, modify, save" pattern working without stating explicitly why the same method call does two different SQL operations depending on context.

ModelForm — no more duplicated fields

A ModelForm generates its fields directly from a model, so they're defined in exactly one place.

# forms.py
from django import forms
from db_app.models import Employee

        model = Employee

Named URLs

Every path() in urls.py can carry an optional name= argument. That name becomes a stable label for the URL you can reference elsewhere in your code (templates, redirects) instead of hardcoding the literal path string.

# db_app/urls.py
from django.urls import path
from db_app import views

urlpatterns = [
    path('home/', views.home, name='home'),
]
<!-- home.html -->
<a href="{% url 'home' %}">Back to home</a>

{% url 'home' %} looks up the URL pattern named 'home' and inserts its actual path into the href. The template never hardcodes the address itself.

Gap‑filled — why this indirection matters

If you hardcode href="/db_app/home/" in twenty templates and later move that view to a different path, all twenty links silently break. If every link instead uses {% url 'home' %}, changing the path() in urls.py is the only place you need to edit — every template referencing the name picks up the new address automatically.

Dynamic URL segments

A "dynamic URL" is a URL that carries a value as part of the path itself — the same view responds to /emp/1/, /emp/2/, /emp/6/, etc., and receives whichever number was actually requested as a normal Python argument.

# db_app/urls.py
urlpatterns = [
    path('emp/<int:emp_id>/', views.emp_details, name='details'),
    path('home/', views.home, name='home'),
]
# db_app/views.py
def emp_details(request, emp_id):
    m = {'id': emp_id}
    return render(request, 'display.html', m)

Visiting /db_app/emp/1/ renders "ID: 1"; visiting /db_app/emp/6/ renders "ID: 6" — same view, same template, different value. <int:emp_id> is a path converter: int says "only match digits, and convert them to a Python int before calling the view"; emp_id is the parameter name the view function must accept — the video runs into a live bug here from those two names not matching (unexpected keyword argument).

Introducing state management

Django runs on client–server architecture: the browser (client) sends a request, the server processes it and sends back a response, and — critically — once that response is delivered, the server does not remember anything about that page or user. The next request, even a second later, is treated as brand new. This is because HTTP is a stateless protocol — it has no built-in memory of previous requests.

Gap‑filled — plain-language definition

Think of state management as the answer to: when you click "Buy Now" on Flipkart, add a delivery address, then reach the payment page, how does the payment page still know which item you're paying for? By default it wouldn't — each page is a separate request, and HTTP forgets everything between requests. Something extra has to carry that information forward — that's state management.

The video builds intuition with several everyday examples:

  • Flipkart checkout — product page → login → delivery address → order summary → payment, each a separate request, yet the site "remembers" which item you're buying throughout.
  • Gmail staying logged in — close the browser without signing out, reopen later, still logged in.
  • Exam-result sites on result day — the first check is slow (new request, real work); refreshing minutes later for curiosity is near-instant (the server recognized it already had the answer).
  • Live cricket score sites — the page appears to auto-update without a manual reload, relying on the same family of mechanism (specifically caching).
  • Online banking session timeouts — take too long mid-transfer and you get "Your session has expired" — state management (a session) deliberately forgetting your progress, for security.

The first state-management technique in detail — what a cookie actually is, its limits, the two cookie types, and the Django mechanics for setting, reading, and deleting one.

What a cookie is

A cookie is a small piece of information — up to 4096 bytes (4 KB) — stored as plain text in the browser. A cookie is created by the server but maintained by the client: the server tells the browser "please hold onto this," and from then on the browser physically keeps it. Once created, a cookie travels with every request/response to that site automatically, and cookies are domain-based — one created on gmail.com is only ever sent back to gmail.com.

Gap‑filled — a simple mental model

Think of a cookie as a sticky note the server hands the browser: "when you talk to me again, show me this note so I remember who you are." The browser keeps the note and attaches it to every future request to that site — the server never has to keep asking "who are you again?"

Researched — these are browser conventions, not an HTTP or Django rule

Per-domain and total cookie limits are set by each browser, not by any web standard — different browsers use somewhat different numbers, and modern browsers are often more generous than the video's figures. What matters in practice regardless of the exact number: cookies are for small amounts of non-critical data, not a general-purpose storage mechanism.

Why cookies have no security

Because a cookie's value is plain text, anyone with access to that browser can open its cookie storage and read — or delete — the value directly. This is the core drawback: cookies should never hold sensitive data in plain form.

Gap‑filled

This is exactly why the video's cookie examples never store a real password, and why — once sessions are introduced next topic — the pattern becomes "put a random, meaningless session ID in the cookie, and keep the actual sensitive data on the server."

Why cookies are useful anyway

Cookies solve a real problem: recognizing a returning visitor without re-authenticating every request. Log into Gmail once (no explicit sign-out) → close the browser → reopen later → still logged in. The first login stored a cookie; every later visit sends it along, and the server recognizes the same user.

Giving a cookie a real expiration date, what happens when you re-set a cookie's value vs. its key, a page-view counter built with cookies, and the move to the second state-management technique — sessions.

Making a cookie persistent with max_age

Adding max_age (in seconds) turns an in-memory cookie into a persistent one: it survives closing the browser and only disappears once that many seconds have passed.

def set_cookie(request):
    response = HttpResponse("Cookie is set")
    response.set_cookie('name', 'Durga', max_age=60)   # persists for 60 seconds
    return response

Making a cookie persistent with expires

max_age is a relative duration; expires sets an absolute date/time using Python's datetime module.

from datetime import datetime, timedelta

def set_cookie(request):
    response = HttpResponse("Cookie is set")
    response.set_cookie(
        'name', 'Durga',
        expires=datetime.utcnow() + timedelta(days=3)
    )
    return response

datetime.utcnow() gives the current date/time in UTC (Coordinated Universal Time — the time-zone-independent reference computers use internally). timedelta(days=3) represents "a span of 3 days" (it also accepts hours=, minutes=, seconds=) — added to a datetime, it produces a new one 3 days later.

Researched — max_age vs. expires

Per the Django docs, if both are given, max_age takes precedence. In modern code, max_age (a plain integer) is generally simpler than building a datetime + timedelta by hand — reach for expires only when you need an absolute calendar date/time.

Overriding a cookie's value vs. creating a new cookie

  • Changing the value, same key → the existing cookie is overwritten in place.
  • Changing the key → a brand-new, separate cookie is created alongside the old one.
Gap‑filled

This is really "a cookie is identified by its key, like a dictionary key" — worth stating explicitly, because it explains a common confusion: if a cookie "isn't updating," check whether your code is accidentally using a slightly different key string each time.

A page-view counter using cookies

def count_view(request):
    count = request.COOKIES.get('count')
    if count:
        new_count = int(count) + 1
    else:
        new_count = 1

    response = render(request, 'count.html', {'count': new_count})
    response.set_cookie('count', new_count)
    return response

First visit: no count cookie exists, so new_count starts at 1. Every later visit: the previous count is read out of the cookie, incremented, shown, and written back. Without the cookie, every refresh would show 1 forever.

Gap‑filled — a subtlety worth flagging

Cookie values are always stored and read back as strings — that's why the code does int(count) + 1 rather than count + 1. Forgetting the int() conversion is a realistic bug: '3' + 1 raises a TypeError in Python.

Checking whether the browser supports cookies at all

Since sessions depend entirely on cookies, Django provides a dedicated mechanism to detect whether a visitor's browser is actually accepting them:

def check_session(request):
    request.session.set_test_cookie()
    return render(request, 'check.html')

def confirm_session(request):
    if request.session.test_cookie_worked():
        request.session.delete_test_cookie()
        return HttpResponse("Cookies are working properly")
    else:
        return HttpResponse("Cookies are disabled")

set_test_cookie() sends a throwaway test cookie; test_cookie_worked() — on a later request — checks whether it actually came back; delete_test_cookie() cleans it up. The video confirms both outcomes: with cookies enabled, it returns True; after blocking all cookies in Chrome's settings, it instead fails with a KeyError on delete (no test cookie ever arrived).

Researched — why this needs two separate requests

Per the Django docs, this only works as a set-then-check-on-the-next-request pair — you can't call both in the same request, because the browser hasn't had a chance to send the cookie back yet. This mirrors the general "set on response, read from request" pattern seen with cookies.

Industry best practice

A small but real fraction of visitors browse with cookies blocked. A production app that depends on sessions for anything important should have a plan for what happens when test_cookie_worked() comes back False, rather than failing in confusing ways.

A page-view counter using sessions

def page_count_view(request):
    count = request.session.get('count', 0)
    new_count = count + 1
    request.session['count'] = new_count
    return render(request, 'count.html', {'count': new_count})

Structurally identical to the cookie-based counter, but no manual int() conversion is needed — session values keep their real Python type. request.session.get('count', 0) returns an actual int 0, not the string '0'.

Gap‑filled — a genuine advantage of sessions over cookies

A cookie can only ever store text, so non-string data (numbers, lists, dicts) has to be manually serialized and parsed back. A session, because the data lives server-side and Django encodes it for you, can transparently store whatever Python (JSON-serializable) types you assign — no conversion code required.

Deleting session data properly: flush()

def del_session(request):
    request.session.flush()
    return render(request, 'del.html')

flush() deletes both the session's data from the database and its cookie from the browser, generating a fresh session key for future activity — a more thorough cleanup than deleting individual keys, which leaves the session itself intact.

Researched — flush() is what Django's logout uses

Per the Django docs, this is exactly what django.contrib.auth.logout() calls internally — logging out should invalidate the whole session, so a stolen/reused old session ID can't be replayed afterward.

Removing already-expired sessions: clear_expired()

request.session.clear_expired()

Unlike flush() (acts on the current session), this is maintenance: it removes session rows that have already passed their expiration date from storage.

Researched — normally a scheduled command, not called from a view

Per the Django docs, the standard approach is the management command python manage.py clearsessions, typically run as a periodic cron job. Expired rows aren't automatically deleted just because they're expired — without occasional cleanup, django_session grows forever.

Keeping an active session alive: request.session.modified = True

By default, Django only extends a session's expiration when its data changes. A read-only view like get_session does not push the expiration further out just because it was visited — the video demonstrates this with a 30-second SESSION_COOKIE_AGE: repeated refreshes of a read-only view still expire exactly 30 seconds after the session was first set.

def get_session(request):
    name = request.session.get('name', 'No name set')
    request.session.modified = True   # treat this request as activity, extend expiry
    return render(request, 'get.html', {'name': name})

Setting request.session.modified = True explicitly tells Django "treat this as a change, even though no key was added or removed" — the expiration recalculates forward from this request. With this added, the same 30-second session stays alive indefinitely as long as it's visited at least once every 30 seconds.

Gap‑filled — why this matters for the banking-session example

This is the exact mechanism behind "keep interacting and you won't get logged out, but go idle and you will." Without this flag, a session expires on a fixed timer from its creation, regardless of how actively a user is using the site — a bad (and arguably insecure) experience, since "still logged in" and "silently expired mid-task" become indistinguishable to the user.

File-based sessions instead of the database

# settings.py
SESSION_ENGINE = 'django.contrib.sessions.backends.file'
SESSION_FILE_PATH = os.path.join(BASE_DIR, 'session')

SESSION_ENGINE swaps how Django stores sessions — the file backend uses plain files instead of a database table. SESSION_FILE_PATH says where (BASE_DIR is already defined near the top of every generated settings.py, pointing at the project root). That folder must be created manually first. Each new session then creates a file named after its session key instead of a database row.

Researched — when file-based sessions are actually worth using

Per the Django docs, the database backend is the default and fine for most projects. File-based sessions are a niche option for avoiding database load on very high-traffic sites, or constrained environments without an easy database setup — for a typical project, there's no compelling reason to switch.

Introducing the cache mechanism

Cache is the third state-management technique — like sessions, it's server-side. But where a session remembers a specific user's data, cache avoids repeated, expensive work by temporarily saving the result of a request, so repeat requests (from anyone) can be served instantly instead of recomputed.

  • University exam-result sites — the first request for a result is slow (real work); later requests for the same result are near-instant (served from the cache).
  • A phone's cache folder — recently opened files are kept in a cache folder so reopening them is instant, instead of re-reading and re-processing from scratch. Clearing that folder means the next open goes back to being slow.
Gap‑filled — cache vs. session, side by side

Is the data specific to one visitor (their name, their cart, their login state)? That's a session. Is it the same for anyone who asks and just expensive to redo? That's a cache. A session remembers who you are; a cache remembers what the answer was, regardless of who's asking.

Researched — why middleware order matters here specifically

Per the Django docs, UpdateCacheMiddleware runs during the response phase and needs to run last on the way out while running first on the way in relative to most other middleware — hence its position near the top. FetchFromCacheMiddleware needs other middleware (like CommonMiddleware, which can modify the request path) to have already run before it decides whether a cached response exists — hence its position near the bottom. Getting this order wrong doesn't raise an error; it silently produces caching that doesn't work.

Researched — a practical tradeoff with local-memory caching

Per the Django docs, LocMemCache is fast (no database/file I/O) but private to a single server process — in production, running multiple processes means each has its own separate cache, so an entry from one process might not be found by a request landing on another. Per-view cache

Rather than caching an entire site, @cache_page(seconds) marks just one view:

# views.py
from django.views.decorators.cache import cache_page

@cache_page(30)
def v1(request):
    return render(request, 'cache.html')

def v2(request):
    return render(request, 'cache_one.html')   # not decorated — always fresh

@cache_page(30) is a decorator (a function that wraps another to add behavior) placed directly above the view it applies to; 30 is the duration for that view only. v1 behaves like the per-site examples (edits don't show for 30 seconds); v2 always shows live content — proving the caching is scoped to only the marked view.

Critical setup difference from per-site caching

Per-view caching must not have UpdateCacheMiddleware/FetchFromCacheMiddleware in MIDDLEWARE — those implement per-site caching specifically, and leaving them in place while using @cache_page produces confusing, incorrect results. The CACHES dictionary is still needed (still needs somewhere to store data); only the two middleware lines must be removed.

Example

When per-view caching earns its keep over per-site: one expensive, rarely-changing report page alongside always-fresh pages.

@cache_page(600)   # 10 minutes — expensive to generate, rarely changes
def sales_report(request):
    # ...expensive database aggregation...
    return render(request, 'sales_report.html', {'totals': totals})

def live_notifications(request):
    # cheap, and must always be fresh — never cached
    return render(request, 'notifications.html', {'items': get_latest(request.user)})

Caching the entire site here would be wrong — it would make live_notifications show stale data. Per-view caching gives the slow page a performance boost without affecting the page that must stay current.

Authentication vs. authorization

  • Authentication — checking whether a user's credentials (username + password) are correct. If so, they become an authenticated user.
  • Authorization — checking whether an already-authenticated user has permission to access specific content or perform specific actions.
Gap‑filled — the distinction in one sentence

Every authorized user is authenticated, but not every authenticated user is authorized for everything — a logged-in regular user authenticates fine, but isn't authorized to delete other accounts the way an admin is.

The login view

from django.contrib.auth.forms import AuthenticationForm
from django.contrib.auth import authenticate, login
from django.http import HttpResponseRedirect

def user_login(request):
    if request.method == 'POST':
        fm = AuthenticationForm(request=request, data=request.POST)
        if fm.is_valid():
            uname = fm.cleaned_data['username']
            pwd = fm.cleaned_data['password']
            user = authenticate(username=uname, password=pwd)
            if user is not None:
                login(request, user)
                return HttpResponseRedirect('profile/')
            else:
                messages.info(request, 'Invalid username or password')
        else:
            messages.info(request, 'Invalid username or password')
    else:
        fm = AuthenticationForm()
    return render(request, 'login.html', {'form': fm})
  • AuthenticationForm(request=request, data=request.POST) — needs the request itself internally (e.g. to check the account is active), unlike SignUpForm.
  • fm.cleaned_data[...] — the form's validated field values.
  • authenticate(username=, password=) — checks the pair against the database, returns the matching User or None. This is the real credentials check — is_valid() alone only confirms the fields are well-formed.
  • login(request, user) — establishes the logged-in session for this request, given an already-verified user.
Gap‑filled — why authenticate() and login() are separate

This split lets you verify credentials for reasons other than an interactive login (e.g. in a script) without every check side-effecting a live session — logging in is an explicit, separate action.

Industry best practice / Researched — never reveal which field was wrong

Per the Django docs, the generic "Invalid username or password" (used identically for both failure cases) is a real security practice — a more specific message tells an attacker which half of a guessed pair was correct.

from django.contrib.auth.forms import PasswordChangeForm
from django.contrib.auth import update_session_auth_hash

def user_password_change(request):
    if request.method == 'POST':
        fm = PasswordChangeForm(user=request.user, data=request.POST)
        if fm.is_valid():
            fm.save()
            update_session_auth_hash(request, fm.user)
            messages.success(request, 'Password change successfully')
            return HttpResponseRedirect('/profile/')
        else:
            messages.info(request, 'Please enter valid details')
    else:
        fm = PasswordChangeForm(user=request.user)
    return render(request, 'change_password.html', {'form': fm})

Built for a specific already-known user (user=request.user), rendering old password / new password / confirm fields. update_session_auth_hash(request, fm.user) is the critical, easy-to-miss step — without it, changing the password immediately invalidates the user's own current session, logging them out mid-request.

This is Django's documented way to exclude an inherited field without redeclaring the whole parent form. The updated profile view: GET pre-fills, POST saves

def profile(request):
    if request.user.is_authenticated:
        if request.method == 'POST':
            fm = EditUserProfileForm(request.POST, instance=request.user)
            if fm.is_valid():
                fm.save()
                messages.success(request, 'Profile is updated')
        else:
            fm = EditUserProfileForm(instance=request.user)
        return render(request, 'profile.html', {'user': request.user, 'form': fm})
    else:
        return HttpResponseRedirect('/login/')

instance=request.user is the key mechanic that makes the form edit rather than create — passed on both branches, so GET pre-fills with existing data and POST saves changes back onto that same row instead of creating a new one.

Introducing class-based views (CBVs)

Every view so far has been a function-based view (FBV). Django also supports class-based views (CBVs) — views written as Python classes, introduced in Django 1.3 to implement reusable generic views for common patterns (listing objects, showing one object's details, create/update/delete forms).

  • Internally, a CBV still becomes a function-based view at request time — a CBV's as_view() class method returns a plain function Django's dispatcher calls; a CBV is "a wrapper" around the same FBV mechanism, not a different execution model.
  • Neither style is strictly better. For simple, common shapes (list/detail/CRUD), built-in generic CBVs mean far less code. For custom, multi-form, unusually-branching logic, a plain FBV's full manual control is more powerful and often more readable.
Gap‑filled — resolving an apparent contradiction

"Most powerful" (FBVs) and "most frequently used" (CBVs) describe different things: FBVs give unrestricted control; CBVs give leverage for the specific, very common view shapes Django already models. Use a generic CBV when your view matches one of those shapes; use an FBV when it doesn't.

A minimal class-based view

# class_based_view_app/views.py
from django.views.generic import View
from django.http import HttpResponse

class ClassBasedView(View):
    def get(self, request):
        return HttpResponse("This is my first class-based view.")

Every CBV must inherit from View. Instead of a manual if request.method == 'GET': ... check, a CBV defines one method per HTTP verb — get(self, request), post(self, request) (next topic), etc. — and the inherited View.dispatch() calls the matching one automatically.

# class_based_view_app/urls.py
urlpatterns = [
    path('', views.ClassBasedView.as_view()),
]

.as_view() is not optional — a CBV can't be referenced directly the way an FBV is; it converts the class into the plain callable Django's dispatcher expects.

Passing extra data into a CBV through the URL

class ClassBasedView(View):
    def get(self, request):
        return HttpResponse(self.name)
path('', views.ClassBasedView.as_view(name='Mohan')),

Any extra keyword passed to as_view() becomes an attribute on the view instance, accessible as self.name — a mechanism specific to CBVs, with no FBV equivalent.

Rendering a template and passing context

from django.shortcuts import render

class ClassBasedView(View):
    def get(self, request):
        context = {'message': "Welcome to Durga's Python classes"}
        return render(request, 'class_based.html', context)

Exactly the same render(request, template, context) call an FBV would make — confirming that once inside a CBV's method, everything about rendering and context is unchanged. Only how a CBV is structured and wired up differs, not what it can do once inside.

        fm = MyForm()
    return render(request, 'function_based.html', {'form': fm})

# class-based — same logic, restructured into get()/post()
class ClassBasedView(View):
    def get(self, request):
        fm = MyForm()
        return render(request, 'class_based.html', {'form': fm})

    def post(self, request):
        fm = MyForm(request.POST)
        if fm.is_valid():
            print(fm.cleaned_data['name'])
            return HttpResponse("Form is submitted")
        return render(request, 'class_based.html', {'form': fm})

The FBV uses one method with an if request.method == 'POST' branch; the CBV uses two separate methods, and the inherited View.dispatch() picks which one runs — nothing in the CBV's own code checks request.method directly.

Introducing pagination

Pagination is the process of splitting data across multiple pages instead of rendering every row of a large table onto one. Django provides two built-in classes: Paginator and Page.

# pagination_app/views.py
from django.core.paginator import Paginator
from .models import Book

def page_view(request):
    all_pages = Book.objects.all().order_by('id')
    paginator = Paginator(all_pages, 3)   # 3 records per page
    page_number = request.GET.get('page')
    page_obj = paginator.get_page(page_number)
    return render(request, 'pages.html', {'page_obj': page_obj})

Paginator(queryset, 3) wraps the queryset, 3 records per page. request.GET.get('page') reads the requested page from the URL's query string — a GET parameter, since viewing a page is a safe lookup. paginator.get_page(page_number) returns a Page object holding that page's slice plus navigation info.

Without order_by, records display in whatever order the database happens to return them — inconsistent page contents across visits. Always order a queryset before paginating, for the same reason a shuffled deck makes for confusing page numbers.

Handling a partial last page: orphans

paginator = Paginator(all_pages, 3, orphans=1)

With 10 records at 3-per-page, the last page would have 1 leftover ("orphan") record. orphans=1 folds a last page that small back into the previous page instead — 3 pages of 3 plus one of 4, rather than 3 of 3 plus an awkward final page of 1.

Researched — orphans is cosmetic, not a hard rule

Per the Django docs, orphans sets the minimum items allowed on the last page before folding — defaults to 0 (no folding) unless set. It avoids a jarringly small last page; it doesn't change page count when the last page already has a reasonable size.

Handling an invalid page number

from django.http import Http404

class PageListView(ListView):
    model = Book
    template_name = 'pages.html'
    ordering = 'id'
    paginate_by = 3
    paginate_orphans = 1

    def get_context_data(self, *args, **kwargs):
        try:
            return super().get_context_data(*args, **kwargs)
        except Http404:
            self.kwargs['page'] = 1
            return super().get_context_data(*args, **kwargs)

By default, an out-of-range page number (e.g. ?page=12) raises an HTTP 404. 41 · Middleware

What middleware is and why it exists, Django's built-in middleware already running in every project, and writing custom middleware two ways — as a plain function and as a class.

What middleware is

Middleware is a mediator: every request passes through it on the way to the view, and every response passes through it on the way back. Normally client → server → response, but if a server genuinely can't process a request (down for maintenance, overloaded), the server itself never sends a response — what the client actually sees ("please try again later") is generated by middleware intercepting the request before it ever reaches the unavailable backend.

Gap‑filled — the ATM analogy, made explicit

An out-of-service ATM doesn't do nothing — it displays "temporarily out of order." That message isn't from the unavailable banking backend; it's from a layer in front of it that knows the backend is unreachable. Django middleware plays exactly this role: a layer positioned to intercept and respond independently of whether the "real" logic behind it can run at all.

Two types of middleware

Built-in middleware ships with Django, already configured in MIDDLEWARE in settings.py: SecurityMiddleware, SessionMiddleware, CommonMiddleware, CsrfViewMiddleware, AuthenticationMiddleware, MessageMiddleware, XFrameOptionsMiddleware. Custom middleware is middleware you write yourself.

Gap‑filled — this reframes a lot of earlier "it just works" behavior

request.session, request.user, CSRF enforcement, and the messages framework aren't special-cased into Django's core — each is one entry in this same MIDDLEWARE list, following the exact interception pattern built from scratch below. Custom middleware is the same mechanism several already-familiar features are built on.

Custom middleware, function-based

# middleware_app/middleware.py
def my_middleware(get_response):
    print("one time initialization")   # runs once, when the server starts

    def middleware_function(request):
        print("this is before view calling")
        response = get_response(request)
        print("this is after view calling")
        return response

    return middleware_function

The outer function receives get_response — a callable for "the next thing in the chain." Code at that level runs once, at server startup. The returned inner function runs on every request: anything before get_response(request) is called runs before the view; anything after runs after. Returning the inner function (not calling it) is what makes this work — Django calls the outer function once to get the per-request handler, then calls that handler on every request.

# settings.py
MIDDLEWARE = [
    # ...existing built-in middleware...
    'middleware_app.middleware.my_middleware',
]

That string is a dotted path: <app>.<file>.<function name> — without this line, middleware.py is just an inert file.

Custom middleware, class-based

The same mechanism as a class, put to a genuinely useful purpose: showing a "site under construction" message for every request, without it ever reaching the actual view.

# middleware_app/middleware.py
from django.http import HttpResponse

class SiteUnderConstructionMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        return HttpResponse("<h1>Currently the site is under construction.</h1>")

__init__ stores get_response on the instance. __call__ is a special Python method that makes an instance callable like a function — Django calls it automatically for every request. Critically, this version never calls self.get_response(request) at all — it short-circuits the chain entirely, so the request never reaches the intended view.

Gap‑filled — middleware can refuse to forward the request at all

The function-based example always eventually calls get_response(request) — it observes and wraps, but never blocks. This class-based example shows the other half: because self.get_response is just a stored value, calling it is optional. This is exactly how a real maintenance-mode or IP-block middleware decides, before the view ever runs, whether the request should proceed at all.

Handling unhandled exceptions with process_exception

class ErrorMessageMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        return self.get_response(request)

    def process_exception(self, request, exception):
        return HttpResponse("Currently we are facing some technical issues.")

With this middleware activated, a view that raises an unhandled exception (e.g. a deliberate division by zero) no longer shows Django's default technical error page — process_exception catches it and returns the friendly message instead.

Researched — process_exception is one of several optional hooks

Per the Django docs, process_exception(request, exception) is called only when a view raises an unhandled exception, and should return either None (let normal error handling continue) or an HttpResponse (replace the default error page). Other optional hooks include process_view and process_template_response, following the same "Django calls this automatically at a specific point" pattern.

Industry best practice

A real production error-handling middleware would typically also log the exception before returning a generic message — showing a friendly message without recording what went wrong hides the problem from whoever needs to fix it.

42 · Model inheritance

Applying Python's class-inheritance idea to Django models — sharing common fields without redeclaring them — in its two demonstrated forms: abstract base class and multi-table inheritance.

What model inheritance is

If several model classes share common fields, writing them separately in every model increases code length and reduces usability. Model inheritance works almost the same as class inheritance in plain Python — a base class defines fields once; other models inherit and automatically get them. Django provides three types:

TypeWhat it means
Abstract base classThe base class exists purely to hold shared fields — never becomes a table itself.
Multi-table inheritanceBoth base and child classes become real, separate tables, linked automatically.
Proxy model inheritanceNamed as the third type; not demonstrated in this source material — see the note below.
Gap‑filled — tying this to ordinary Python inheritance

In plain Python, class Dog(Animal): means every Dog automatically has whatever Animal defines. Django model inheritance is that same language feature — a model is still just a Python class — with the added wrinkle that Django must also decide what happens at the database level, which is exactly what distinguishes the three types above.

Abstract base class inheritance

# model_inheritance_app/models.py
class CommonInfo(models.Model):
    name = models.CharField(max_length=20)
    age = models.IntegerField()
    date = models.DateField()

    class Meta:
        abstract = True

class Trainer(CommonInfo):
    address = models.CharField(max_length=20)
    date = None   # this trainer doesn't need the inherited "date" field

class Teacher(CommonInfo):
    date = models.DateTimeField()   # overrides the inherited DateField

class Meta: abstract = True makes CommonInfo just a blueprint — no CommonInfo table is ever created; only Trainer and Teacher get real tables, each inheriting name/age without redeclaring them. date = None on Trainer explicitly removes an inherited field it doesn't need — the same exclusion technique as EditUserProfileForm.password = None from an earlier topic, applied to a model instead of a form. Teacher redeclaring date overrides the inherited field's type for that model only.

Running makemigrations/migrate creates exactly two tables — Trainer and Teacher — confirmed in the admin panel; CommonInfo produces no table at all.

Gap‑filled — the practical payoff

Without this, adding a name/age pair to ten models means ten separate declarations, and changing one later means editing ten files. Abstract base classes turn shared fields into a single, edited-once source of truth — the same DRY motivation behind ModelForm removing field duplication, applied one layer down at the model level.

Industry best practice

Reach for an abstract base class when shared fields don't need independent existence in the database — e.g. a TimestampedModel abstract base with created_at/updated_at, inherited by every model needing that tracking, without a meaningless standalone table.

Multi-table inheritance

class Bank(models.Model):
    bank_name = models.CharField(max_length=20)
    bank_address = models.CharField(max_length=20)

class BankManager(Bank):
    name = models.CharField(max_length=20)
    age = models.IntegerField()

The critical difference: Bank is not marked abstract. Bank gets its own real table; BankManager also gets its own real table, and Django automatically adds a hidden one-to-one relationship linking each BankManager row back to its Bank row — so a BankManager instance can access bank_name/bank_address too, even though those columns physically live in the separate table. Confirmed in the admin panel: adding a BankManager record (whose form shows bank_name/bank_address alongside its own fields) automatically creates/links a matching Bank row.

Gap‑filled — a mental model

In the abstract case, the base class is a stencil: it shapes the child tables but never becomes one itself. In multi-table inheritance, think of two real, separate filing cabinets wired together — every BankManager folder has an automatic cross-reference to exactly one Bank folder. Abstract inheritance shares field definitions; multi-table inheritance shares (and links) actual rows.

Researched — the automatic link is a real OneToOneField

Per the Django docs, the parent link Django creates is an ordinary OneToOneField — queryable and traversable the same way any explicitly-declared one-to-one relationship is (e.g. some_bank.bankmanager). It's not a special hidden mechanism, just a normal field you didn't have to type yourself.

The main use of a proxy model is to override existing behavior. It is a type of model inheritance without creating a new table — it always queries the original model, just with overridden methods/behavior.

    uname = models.CharField(max_length=20)
    ulocation = models.CharField(max_length=20)

class College(University):
    class Meta:
        proxy = True

College(University) inherits normally, but class Meta: proxy = True means it shares the exact same table as University — no new table is ever created for it. Because both classes point at the literal same table, adding or editing a record through either model reflects in both, confirmed directly in the admin panel.

Gap‑filled — how this differs from the other two inheritance types

Abstract base classes are about not repeating field definitions across genuinely separate tables. Multi-table inheritance is about linking genuinely separate tables. A proxy model isn't about the data at all — it's the same table — it exists purely to attach different Python-level behavior (ordering, custom methods, a different admin registration) to what is, at the database level, one and the same table.

Industry best practice

Reach for a proxy model when you want to change behavior for a subset of use cases without touching the schema — e.g. an ActiveUser proxy of User with a custom manager that only returns active accounts. Use multi-table (or abstract) inheritance instead when you actually need different fields.

Introducing model relationships

Model relationships are database relationships. There are three types: one-to-one, many-to-one, and many-to-many.

One-to-one relationships

A one-to-one relationship is where both tables can have only one record on either side — like husband and wife: one husband, one wife. Defined with OneToOneField.

# model_relationship_app/models.py
from django.contrib.auth.models import User

class Book(models.Model):
    user = models.OneToOneField(User, on_delete=models.CASCADE, primary_key=True)
    book_name = models.CharField(max_length=20)
    book_author = models.CharField(max_length=20)
    book_published_date = models.DateField()
  • on_delete= is a required argument on any relationship field — it says what happens to this row if the row it points to is deleted. models.CASCADE deletes this row too.
  • primary_key=True on the OneToOneField makes the relationship itself the table's primary key — a given User can be linked to at most one Book. A second attempt fails with a uniqueness error.

Restricting the choices offered for a relationship field

user = models.OneToOneField(
    User, on_delete=models.CASCADE, primary_key=True,
    limit_choices_to={'is_staff': True}
)

limit_choices_to filters which related objects appear as options in the admin's dropdown — here, only staff users. The video confirms non-staff users disappear from the dropdown once this is added.

Researched — limit_choices_to is a UI convenience, not a data constraint

Per the Django docs, this only constrains the admin form's choices — it is not database-level validation. A Book could still be created programmatically pointing at a non-staff user; this only narrows the admin's dropdown.

Many-to-one relationships

A many-to-one relationship is where the first table can have one or many records related to the second, but the second is related to only one record in the first — like you and your parents. Defined with ForeignKey.

class Post(models.Model):
    user = models.ForeignKey(User, on_delete=models.CASCADE)
    post_title = models.CharField(max_length=20)
    post_category = models.CharField(max_length=20)
    post_published_date = models.DateField()

No primary_key=True here, so — unlike Book above — one User can have many Post rows, confirmed by creating multiple posts for the same user without error.

Gap‑filled — why ForeignKey is "the" standard relationship

OneToOneField and ManyToManyField are useful but comparatively rare. ForeignKey — one row on the "many" side pointing at one row on the "one" side — is by far the most common relationship in real schemas (an order belongs to one customer, a comment belongs to one post).

The on_delete=PROTECT confusion

Deleting a Book/Post itself is never affected by on_delete at all. PROTECT means: deleting the User that a book/post still points to gets blocked. Resolving the on_delete confusion

Gap‑filled — the one-sentence fix

on_delete is entirely about what happens on the "one" side when it's deleted, never about restricting deletion of the "many" side. A child row can always be deleted on its own — the setting only activates when someone tries to delete the parent it points to.

Researched — the other on_delete options

Per the Django docs, beyond CASCADE/PROTECT: SET_NULL (requires null=True), SET_DEFAULT, SET() (a callable/value you supply), DO_NOTHING (dangerous — no Django-level action), and RESTRICT (similar to PROTECT but allows cascading deletes from elsewhere in the same operation). on_delete has no default — it must always be specified.

Each record of the first table can relate to many of the second, and vice versa. Defined with ManyToManyField.

        return ", ".join(str(u) for u in self.user.all())

45 · QuerySet values/values_list, set operations & field lookups

Two alternative return formats for a queryset, combining two querysets with set-style operators, and the start of Django's field lookup system — the double-underscore syntax behind precise filtering.

.values() and .values_list()

emp_data = Employee.objects.values()
# each row: {'id': 1, 'name': 'Mohan', 'address': 'Hyderabad', ...}

emp_data = Employee.objects.values_list()
# each row: (1, 'Mohan', 'Hyderabad', ...)

.values() returns a queryset yielding dictionaries rather than model instances. .values_list() is the same idea but returns tuples.

Gap‑filled — when either is actually useful

Full model instances are right for most view code (method calls, autocomplete). .values()/.values_list() earn their keep for a lighter-weight, serializable shape — json.dumps(), a CSV export, or feeding a charting library — and are slightly cheaper since Django skips building full model instances.

Researched — values_list(flat=True)

Per the Django docs, when limited to a single field, flat=True returns a flat list of just that field's values instead of one-tuples — e.g. Employee.objects.values_list('name', flat=True) gives ['Mohan', 'Rajesh', ...] directly.

Combining querysets: union, intersection, difference

qs1 = Employee.objects.values_list('id', 'name')

emp_data = qs2.intersection(qs1)   # only rows common to both
emp_data = qs1.difference(qs2)     # only rows in qs1, not also in qs2

MiniBlog — architecture

  • One model: Post (title, description).
  • Static assets included directly (local Bootstrap/jQuery files) rather than CDN — the local-file approach from Topic 18, contrasted with the CDN approach used in the previous two project topics.
  • A navigation.html partial builds its links entirely from named URLs ({% url 'dashboard' %}, {% url 'login' %}, etc.) — the named-URL pattern from Topic 28, applied to an entire nav bar.
  • Views: home (Post.objects.all()), about, contact (doesn't persist submissions — a deliberately unfinished placeholder), dashboard (authenticated-only), sign-up, login, logout, add-post, update-post, delete-post.

Industry best practice

Reading a complete, working codebase end-to-end — even one you didn't write — is a genuinely valuable exercise distinct from following tutorials, because real projects combine many small decisions (which permission model, where shared templates live, app-level vs. project-level URLs) that a single-concept lesson never has to make.
